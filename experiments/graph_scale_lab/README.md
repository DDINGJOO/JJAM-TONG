# 버전별 코드 그래프의 크기를 늘려 비교한다

메서드가 많고 호출 관계가 복잡해졌을 때 PostgreSQL과 Neo4j 중 어떤 조회 방식이 유리한지 확인하는 실험이다. 실제 Java 프로젝트에서 추출한 코드 대신, 같은 규칙으로 재생성할 수 있는 합성 그래프를 사용한다. 제품 DB를 채택하거나 엔터프라이즈 수용량을 인증하는 실험은 아니다.

## 실행

기존 DB 비교 실험의 Python 가상 환경과 Psycopg(PostgreSQL 클라이언트)를 사용한다. 새 라이브러리는 추가하지 않는다.

```bash
.local/storage-lab/venv/bin/python -m unittest discover -s experiments/graph_scale_lab -t .
docker compose -p jjamtong-graph-scale-lab -f experiments/graph_scale_lab/compose.yaml config --quiet
# 측정 소스와 테스트를 먼저 커밋한다. 이미 있는 결과 파일은 덮어쓰지 않는다.
.local/storage-lab/venv/bin/python -m experiments.graph_scale_lab.run run
.local/storage-lab/venv/bin/python -m experiments.graph_scale_lab.run validate
```

Docker가 필요하다. 전용 Compose 프로젝트에서 PostgreSQL과 Neo4j를 하나씩 실행한다. loopback 포트는 각각 29532·29574이며, 두 서버 모두 CPU 1개·메모리 1 GiB로 제한한다. 기존 서비스의 컨테이너는 관리하지 않는다. 종료 시 실험 컨테이너와 네트워크를 제거하고 전용 볼륨은 남긴다. 재실행은 전용 데이터만 지우므로 과거 DB 자체를 보존하려면 별도로 복제해야 한다.

## 입력과 질문

빌드당 메서드 1만·10만 개에, 메서드별 기본 정적 호출 2개·6개를 조합한다. 각 조합에 이전·새 빌드를 모두 저장한다. 256개 메서드의 순환 구간, 구간 사이 연결, 최대 128개 목적지로 연결되는 진입점도 넣는다. 여러 모듈과 다른 저장소·분석 설정·동일 커밋/빌드의 다른 artifact(빌드 산출물)를 구분한다.

`STATIC`은 코드상 호출 가능 관계를 나타내는 합성 행이다. `OBSERVED`도 별도 합성 행이며 실제 요청을 계측한 결과가 아니다. 저장소·커밋·빌드·산출물·분석기·스키마·설정·모듈 목록과 합성 입력의 크기·밀도·생성기 버전을 해시한 `scope`가 분석 범위를 식별한다. 서로 다른 범위의 간선은 만들지 않는다. 권한 검증이나 제품의 분석 ID 규약을 구현한 것은 아니다.

조회는 1·3·6·12단계의 순방향 관계, 역방향 영향, 관측 관계를 대상으로 한다. 결과는 시작점을 제외한 고유 메서드 ID 목록이며, 별도 메모리 BFS(가까운 노드부터 찾는 탐색) 결과와 대조한다. 경로 목록 전체를 반환하는 비용과는 구분한다.

## 두 조회 방식을 구분한다

- `native`: PostgreSQL은 재귀 CTE(이전 단계의 결과를 다시 사용하는 SQL)에서 `(깊이, 메서드)`의 중복을 제거한다. Neo4j는 경로 자체를 반환하지 않고 가변 길이 관계의 고유 목적지만 반환한다. 실행 계획에서 중복 탐색을 줄이는 연산자가 선택되는지 확인한다.
- `frontier`: 두 DB 모두 한 단계씩 조회하고 애플리케이션에서 방문한 메서드를 제거한다. DB 왕복 횟수와 애플리케이션 탐색 비용을 포함한다. 이를 DB의 직접 다단계 탐색으로 표현하지 않는다.

기본 워밍업 2회 뒤 20회 측정한다. 워밍업에서 시간 예산을 초과하면 측정은 1회만 추가하고 실패를 그대로 기록한다. 두 조회 방식 각각에서 클라이언트 1·4·8개가 연결을 준비한 뒤 동시에 출발하며, 클라이언트마다 여섯 질문을 한 번씩 실행한다. 짧은 동시 조회로 지속 수용량이나 오토스케일 효과를 입증하지 않는다.

서버의 쿼리 시간 제한은 10초다. HTTP 클라이언트 제한은 서버 취소 결과를 받을 수 있도록 더 길게 둔다. 애플리케이션 탐색은 전체 10초 예산도 확인한다. 서버 감시 주기나 진행 중인 왕복 때문에 실제 취소 시점은 제한을 넘을 수 있다. 알려진 취소 코드만 `budget_exceeded`로 기록하며, 구문 오류·전송 오류 등은 실행 실패로 남긴다. 지연 백분위에는 성공한 표본만 포함하고 예산 초과 건수를 별도로 표시한다.

## 결과를 읽는 조건

원시 JSON에는 입력·측정 소스 해시, 커밋, 이미지 ID/다이제스트, 실행 계획, 개별 시간·정확성 표본, 적재 시간·저장량과 Docker 자원 표본을 남긴다. 검증기는 빠진 규모·질문·표본, 바뀐 입력과 커밋/소스 불일치를 거부한다. 실패한 실행을 다음 실행과 합치지 않는다.

PostgreSQL은 Psycopg, Neo4j는 요청별 HTTP 연결을 쓴다. 쿼리 지연에는 직렬화·전송·응답 처리 비용이 들어가며, 두 프로토콜의 차이를 제거한 엔진 내부 시간은 아니다. PostgreSQL은 깊이별로, Neo4j는 실행 계획의 pruning(중복 목적지로 가는 탐색을 줄이는 처리) 연산자로 중복 탐색을 줄인다. 내부 알고리즘까지 같게 만든 비교가 아니므로 결과는 각 DB의 해당 질의 구현에 한정한다.

공유 호스트에서 서버를 순서대로 실행하며 캐시를 통제하지 않는다. 규모마다 전용 볼륨을 재사용하므로 기록한 할당량에는 이전 실행의 파일 공간과 트랜잭션 로그도 남을 수 있다. 이 수치를 현재 그래프의 순수 저장량이나 압축 효율로 비교하지 않는다. 완전한 빌드를 적재한 뒤 조회하며 부분 적재·증분 갱신·동시 쓰기는 앞으로 검증한다.

상세 결과는 [규모별 비교 문서](../../docs/experiments/GRAPH-SCALE-COMPARISON.md)에 연결한다. 이 실험은 #43·#44의 모든 인수 조건을 완료 처리하지 않는다.
