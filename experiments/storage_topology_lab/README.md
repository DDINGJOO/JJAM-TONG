# 원본 DB를 바꿔 보는 저장 구성 실험

PostgreSQL을 필수 원장으로 두지 않고 PostgreSQL·Neo4j·Elasticsearch(이하 ES)·ClickHouse가 각각 원본을 맡는 구성을 실행한다. 네 DB의 단독 구성 4개와 서로 다른 두 DB의 방향별 조합 12개가 대상이다. `ES → PostgreSQL`에서는 ES가 복구 기준 원본을, PostgreSQL이 지워도 복원할 수 있는 조회용 데이터를 맡는다. 반대 방향이면 두 책임도 바뀐다.

이 코드는 제품 어댑터가 아니라 작은 합성 입력을 사용하는 비교 실험이다. 새 DB나 라이브러리를 제품 의존성으로 채택하지 않는다. 기존 [조회 엔진 비교](../storage_lab/README.md)의 소스를 바꾸지 않고 어댑터와 입력을 재사용한다.

## 실행

```bash
python3 -m venv .local/storage-lab/venv
.local/storage-lab/venv/bin/pip install -r experiments/storage_lab/requirements.txt
.local/storage-lab/venv/bin/python -m unittest experiments.storage_topology_lab.test_contract
# 측정 소스를 먼저 커밋한다. 기본 출력 파일이 있으면 다른 경로를 지정한다.
.local/storage-lab/venv/bin/python -m experiments.storage_topology_lab.run run
.local/storage-lab/venv/bin/python -m experiments.storage_topology_lab.run validate
```

Docker가 필요하다. 기존 Compose 파일을 `jjamtong-topology-lab`이라는 별도 프로젝트로 실행하고 한 번에 DB를 최대 두 개만 띄운다. 기존 실험과 같은 loopback 포트를 사용하므로 두 실험을 동시에 실행하지 않는다. 해당 포트를 쓰는 다른 서비스가 있으면 실행을 중단하고 포트를 조정한다. 실행 종료 시 이 프로젝트의 컨테이너·네트워크를 제거하고 전용 볼륨은 보존한다. 기존 MSA·관측 도구·Kubernetes 서비스는 관리하지 않는다.

## 무엇을 비교하는가

원본 DB는 가져온 근거 묶음을 변경하지 않는 스냅샷으로 저장한다. 스냅샷은 100행 이하의 조각으로 나누고 각 조각의 SHA-256 해시를 키로 쓴다. 발행 목록인 매니페스트에는 조각 목록·전체 해시·행 수·저장소/커밋/빌드/artifact(빌드 산출물)/모듈/분석 설정의 식별 정보를 보관한다. 조각만 저장하고 목록을 발행하지 않으면 조회는 `missing`이다.

카탈로그 ID는 **가져온 근거 묶음의 개정 식별자**다. 같은 ID를 같은 내용으로 재시도할 수 있지만 다른 내용으로 덮어쓸 수 없다. 이벤트 추가·삭제 표시는 새 개정으로 발행한다. 제품의 분석 ID 규약이나 모든 빌드의 현재 버전을 정하는 전역 포인터를 구현한 것은 아니다.

조회용 데이터가 덜 반영됐거나 artifact가 다르면 `partial`, 원본 또는 조회 DB가 중단되면 `unavailable`이다. 원본과 조회 데이터가 일치한 경우만 `ready`로 표시한다. 판정할 때마다 원본과 관련 범위의 조회 데이터를 모두 읽어 비교한다. 따라서 정확성 대조 비용이 포함되며 운영용 조회 경로의 성능을 나타내지 않는다. 전역·분산 트랜잭션이나 동시 갱신 중의 스냅샷 격리를 제공하지 않는다.

HTTP로 접속하는 세 DB는 요청마다 연결을 닫는다. 다른 DB를 중단·재시작하는 동안 유휴 연결이 만료돼 복구 시험을 방해하는 경우를 피하기 위한 실험 클라이언트 설정이다. 연결이 끊긴 요청을 자동 재시도하지 않으며, 시간 표본에는 새 연결 비용도 포함된다. PostgreSQL은 기존 Psycopg 연결을 사용한다.

각 구성에서 다음을 실행한다.

- 발행 전 조각, 빈 조회 모델, 일부 반영, 전체 반영의 상태를 구분한다.
- 같은 ID의 재시도와 상충한 내용의 거부, 알 수 없는 개정의 최신 버전 대체 금지를 확인한다.
- 다른 artifact가 조회 모델에 섞이면 완전한 결과로 반환하지 않는다.
- 실제 자식 프로세스를 반영 직후 종료 코드 73으로 끊고 재처리한다. 별도 ACK(처리 완료 확인) 저장소는 없으며, 종료 결과를 잃은 뒤의 재실행을 검증한다.
- 원본 DB를 실제로 중단·재시작하고, 조회 모델을 지운 뒤 DB에 보관한 원본만으로 복원한다.
- 삭제 표시 뒤 이전 행을 재생해도 조회에서 되살아나지 않는지 확인한다. 원본의 과거 조각까지 물리적으로 삭제하는 검증과는 구분한다.
- 두 DB 구성에서는 조회 DB 중단 중에도 새 원본을 발행하고 재시작 후 반영한다.
- 코드 호출·역방향 영향·인프라 관계·검색·집계·테넌트/빌드/설정 분리에 대한 기존 정확성 질문을 적용한다.

동시 발행은 연결 두 개를 동시에 출발시켜 별도로 시험한다. PostgreSQL은 고유 키와 `ON CONFLICT`, Neo4j는 고유 제약과 `MERGE`, ES는 `_create`를 사용한다. ClickHouse의 현재 일반 MergeTree(ClickHouse의 테이블 엔진) 어댑터에는 동일 ID를 한 번만 생성하는 원자적 연산이 없으므로 `unsupported`로 기록한다. 상충한 두 내용이 실제로 함께 저장되는 반례도 실행한다. 단일 발행자로 기능 시험을 통과해도 이 제한이 사라지지 않는다.

## 판정과 증거

원시 JSON에는 실행 ID·커밋·실험 소스 해시·이미지 ID/다이제스트·구성별 판정·짧은 시간 표본을 남긴다. `validate`는 16개 구성과 필수 판정·입력·소스/커밋 일치를 검사한다. 실패한 실행을 성공 결과에 합치지 않는다.

합성 입력은 `dataset(25, 20)`으로 고정한다. 한 저장소·모듈, 두 테넌트·빌드와 별도 분석 설정을 쓴다. 삭제 검증은 이벤트 한 행을 대상으로 한다. 여러 저장소/모듈의 키 충돌, 계속 증가하는 변경 이력, 실제 권한, 보존 정책, 지속 수용량, 장애 조치·백업 복구·자동 확장은 앞으로 검증한다. 서버를 정상 중단한 뒤 같은 볼륨으로 재시작하며, 강제 장애나 별도 장비 복구를 입증하지 않는다.

상세 비교와 결과는 [원본 책임별 구성 비교](../../docs/experiments/STORAGE-TOPOLOGY-COMPARISON.md)에 정리한다. 이 실험은 기존 #43·#44의 모든 인수 조건을 완료 처리하지 않는다.
