# 화면 사용성·프론트엔드 리뷰

사람이 필요한 근거를 찾고 판단할 수 있는지, 화면이 실제 데이터와 상태를 정확하게 표현하는지 검토한다. 전문가 페르소나는 AI의 검토 관점이며 실제 전문가의 참여나 사용자 실험을 뜻하지 않는다.

## 범위와 자료

- 저장소의 `AGENTS.md`를 읽고 대상 화면·사용자 목적·데이터 모드·비교 자료를 정한다. 질문이나 리뷰 요청은 읽기 전용으로 수행하며 화면 수정은 요청 범위에 포함될 때 진행한다.
- 현재 프론트엔드는 `tools/evidence_web/static/`, 조회 서버는 `tools/evidence_web/server.py`에 있다. 위치나 기술이 바뀌면 실제 구현을 기준으로 삼는다. 리뷰를 위해 프레임워크나 의존성을 도입하지 않는다.
- 필요한 화면 코드·조회 계약·관련 QA와 브라우저를 확인한다. Orca 브라우저를 사용할 때는 설치된 `orca-cli` 스킬을 따른다. 브라우저를 쓸 수 없으면 소스 검토와 이전 캡처의 범위를 밝힌다.
- 기존 HTML은 사용 흐름과 시각적 위계를 비교할 자료다. 픽셀 일치나 기존 구성의 보존 자체를 합격 기준으로 삼지 않는다. 합성 데모와 실제 조회 화면의 데이터 양 차이도 결함으로 단정하지 않는다.

## 두 관점의 독립 검토

가능하면 UX와 개발 검토를 별도 에이전트에서 수행한다. 설치된 `designer`와 `code-reviewer` 역할을 확인하고 환경의 호출 규칙을 따른다. 두 검토자에게 같은 사용자 목적과 원본 자료를 전달하되 서로의 결론이나 작성자가 기대하는 답은 전달하지 않는다. 역할에 구현 지침이 있어도 이번 검토는 읽기 전용이다.

분리 실행이 불가능하면 한 에이전트가 두 관점으로 검토하고, 독립 검토를 수행하지 못했다고 표시한다. 검토자는 맡은 범위에서 영향이 큰 지적을 우선 보고하고, 추가 역할이 필요하면 진행자에게 알린다.

### UX 전문가

- 사용자가 무엇을 조사하며 어디에서 시작하는지 살핀다. 검색·목록·직접 링크에서 대상과 다음 행동을 알아볼 수 있는가?
- 서비스와 API별 구조를 탐색하는 시나리오에서는 서비스·환경·작업의 맥락을 유지하는가? 이벤트 소비자·배치 등 HTTP API가 아닌 진입점도 고려한다. 모든 플랫폼 화면을 API 중심으로 바꾸지는 않는다.
- AI가 조회할 상세 데이터와 사람이 당장 판단할 정보를 구분한다. 해시·분석 실행 ID·원시 JSON·분석기 설정은 필요할 때 열 수 있게 하고, 선택한 대상·버전·중요한 불확실성은 쉽게 알아볼 수 있게 한다. 화면을 줄이기 위해 원본 근거를 버리지는 않는다.
- 그래프가 첫 화면의 질문에 답하는지 살핀다. 서비스·클래스·메서드 묶음, 관심 경로, 점진적 펼침, 확대 수준에 따른 상세 표시로 복잡도를 줄일 수 있는가? 숨긴 노드나 접힌 경계를 관계의 부재처럼 표현하지 않는가?
- 반복되는 제목·배너·경고, 첫 화면에서 그래프가 차지하는 공간, 작은 글자·잘림·선 겹침을 실제 화면으로 확인한다. 경고를 합치더라도 현재 판단에 영향을 주는 정보는 남긴다.

### 프론트엔드 개발자

- 선택한 서비스·작업·환경·빌드가 목록·그래프·Trace 상세에서 일관적인지 확인한다. 빠른 버전 전환이나 검색으로 늦게 도착한 응답이 현재 화면을 덮지 않는가?
- 검색이 서버 검색인지 현재 목록 필터인지, 페이지가 더 있는지, 결과가 없는지 구분한다. 라우트와 진입 메서드의 연결 근거가 없는데 API를 추측해 만들지 않는다.
- 정적 호출 후보, 여러 요청의 실행 패턴, 특정 Trace의 실행을 구분한다. 빌드·모듈·분석기와 메서드의 오버로드 식별을 보존하고 다른 버전의 데이터를 묵시적으로 합치지 않는다.
- 저장된 Trace와 지속 수집 중인 Trace를 구분한다. Git 분석 동기화만으로 실시간 실행 수집이나 화면 자동 갱신이 동작한다고 표현하지 않는다.
- 변경 범위에 맞춰 로딩·빈 결과·실패·부분 수집·버전 불일치와 복구를 확인한다. 키보드 탐색·초점·접근 가능한 이름, 화면 크기 변화, 그래프의 표시량 상한도 살핀다.
- API 시험, 브라우저 조작, 실제 사용자 실험, 대규모 성능 검증의 근거를 구분한다. 작은 합성 그래프의 동작을 기업 환경의 성능 보장으로 확대하지 않는다.

## 통합과 검증

진행자가 중복 지적을 합치고 관찰한 문제와 개선 제안을 나눈다. 근거가 충돌하면 작은 재현으로 확인하고, 판단할 수 없으면 확인할 조건을 남긴다. 취향의 차이를 결함으로 승격하지 않는다.

영향이 큰 항목부터 다음 내용을 간결하게 보고한다.

- 사용자 시나리오와 막히는 단계.
- 화면 위치 또는 파일·행, 사용한 데이터 모드·버전과 관찰 근거.
- 영향에 따른 우선순위: P0는 잘못된 근거로 판단하거나 정보가 노출되는 문제, P1은 핵심 조사 흐름의 방해, P2는 탐색 비용·가독성 문제, P3는 작은 표현 문제다.
- 최소 개선안과 사용자가 확인할 수 있는 재검증 시나리오.
- 실제 확인한 범위와 아직 확인하지 못한 범위.

수정을 요청받으면 합의된 범위의 지적을 반영하고 해당 시나리오를 다시 확인한다. 읽기 전용 리뷰는 근거와 개선 우선순위를 제시하면 마친다. 지적 수를 0으로 만들기 위한 무한 반복이나 근거 없는 합격 선언은 하지 않는다. 결과를 저장·게시할 때는 저장소의 문서·검토·공개 범위 규칙을 따른다.
