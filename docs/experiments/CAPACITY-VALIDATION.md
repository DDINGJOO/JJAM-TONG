# 수용량·과부하·복구 검증 계획

날짜: 2026-11-12. 상태: **요구사항·검증 계획 Draft / 수용량 미측정**.

[비용·상한 요구 T10 #19](https://github.com/DDINGJOO/JJAM-TONG/issues/19) · [라이브러리 적용 T25 #44](https://github.com/DDINGJOO/JJAM-TONG/issues/44) · [BDD-SRE-005~008](../../specs/features/05-sre-analysis.feature).

관측 기능을 켠 뒤 요청당 비용이 늘어난 정도와 서비스가 감당할 수 있는 부하는 별도로 확인해야 한다. 앞선 [27회 적용 전후 비교](EXECUTION-PERFORMANCE-RESULTS.md)는 동시성 1·4의 비용을 측정했다. 최대 수용량·안전한 운영 부하·플랫폼 전체의 처리 한계를 검증한 결과는 아니다.

여기서는 **고정한 업무·데이터·자원 조건에서 정확성, 지연, 오류, 처리 지연과 자원 예산을 정해진 시간 동안 함께 만족하는 부하 범위**를 수용량으로 정의한다. SLO는 그 판정에 사용할 서비스 수준 목표다. 수치 목표가 없으면 관측값을 보고하며, 수용량 합격 판정은 보류한다.

기업 운영의 비교 조건은 [엔터프라이즈 요구](../requirements/ENTERPRISE.md)에 있다. 조직·팀·계정·클러스터·사이트별 규모와 부하 분포, 할당량, 인증·정책 검사·암호화·감사, 장애·업그레이드·복구 중 부하를 고정한다. 조직별 지연·적체·신선도를 전체 평균과 나누며, 격리·권한 위반을 성능과 교환하지 않는다. 이 조건을 포함한 수용량은 아직 미측정이다.

## 요청 속도와 처리 속도를 함께 기록한다

수용량 실험은 **응답 완료와 독립적으로 요청을 시작하는 도착률 부하**를 기본 비교 대상으로 삼는다. 실제 부하 도구·구현은 아직 선택하지 않았다. 이전의 동시성 고정 방식은 같은 동시성의 비용을 재현하는 별도 비교로 유지한다. 이 구분은 [공식 부하 모델 설명](https://grafana.com/docs/k6/latest/using-k6/scenarios/concepts/open-vs-closed/)에 근거하며, 참고 도구의 채택을 뜻하지 않는다.

1. 낮은 도착률에서 시작해 단계별로 높인다. 단계마다 정해진 시간과 표본을 확보하고 정상 상태 여부를 판정한다.
2. 예정한 요청 수·실제로 시작한 수·시작 지연·발행하지 못한 수·실행 중인 수를 기록한다. 부하 발생기가 CPU·연결·동시 작업 한도에 걸리면 **그 구간으로 서비스 한계를 판정하지 않는다**.
3. 성공·의도한 부하 거절·서버 오류·타임아웃·취소·미완료를 따로 집계한다. 거절이나 기록 누락을 성공 처리량에 넣지 않는다. 타임아웃 뒤 업무가 저장됐는지도 고유 ID로 대조한다.
4. 예정 시점부터의 지연, 실제 발행부터 응답까지의 지연, 비동기 업무 완료 지연을 나누어 남긴다. 단계 말에 미완료인 입력과 뒤늦게 완료된 입력도 원래 단계의 ID에 연결한다.
5. 같은 요청·데이터·자원에서 미적용·기본 추적·메서드 추적을 반복한다. 초기 데이터·캐시·적체와 실행 순서를 기록하고 구성 간 비교 조건을 맞춘다.

부하를 높일 때 큐가 계속 늘면 짧은 HTTP 성공 구간만으로 지속 수용량을 인정하지 않는다. Kafka 적체는 건수·시간과 파티션별 분포, 소비 완료를 함께 보고, DB 연결 풀 대기와 앱/수집기 큐의 최고 대기 시간도 나누어 확인한다.

도착률 기반 도구도 실행 슬롯 부족으로 예정한 작업을 발행하지 못할 수 있다. 발생기 설정 부족과 서비스 지연의 영향을 구분해야 하므로 미발행 요청을 따로 남긴다. [공식 미발행 작업 설명](https://grafana.com/docs/k6/latest/using-k6/scenarios/concepts/dropped-iterations/).

CAP-06의 서비스별 격리는 제품 요구다. 실행 형태와 자원 할당 정책을 정해 검증하며, 현재 다중 사용자·서비스 격리가 구현됐다는 의미는 아니다. 장애 주입은 소유한 별도 로컬 실험 자원에서 수행한다. 기존 공유 컨테이너를 멈추거나 데이터를 삭제하는 계획으로 해석하지 않는다.

CAP-07은 단일 실행과 다중 복제본을 비교할 수 있는 구성부터 검증한다. 개별 자원 제한과 전체 자원 합계를 함께 고정·기록한다. 복제본을 늘린 비율만큼 처리량이 늘거나, 하나가 빠져도 기존 수용량을 유지한다고 가정하지 않는다. Kubernetes 자동 확장이나 장애 전환이 현재 구현됐다는 뜻도 아니다.

[자동 확장·축소 명세](../requirements/AUTOSCALING.md)는 CAP-01~07을 고정 용량과 부하 반응형·사전 확보 구성으로 비교할 후속 조건이다. 같은 입력·목표·기업 정책과 공통 자원/비용 상한에서 판단부터 실제 처리·회복까지의 지연, 지표 오류·배치 실패·후속 포화·축소 중 인계·재균형·조직별 영향을 검증한다. BDD-ASC-001~009는 실행 전 Draft이며 CAP-07의 복제본 변경 계획을 자동 확장 구현 완료로 바꾸지 않는다.

각 경계에서 가능한 경우 수신·수락·재시도·거절·영속 보관·조회 가능·삭제를 입력 ID와 대조한다. 의도한 샘플링, 재시도 가능한 일시 거절, 영구 유실, 측정 불가를 분리한다. 생성한 입력 수를 독립적으로 확인할 수 없으면 실제 유실률을 확정하지 않는다. 서비스 요청당 span 수와 이벤트 크기도 기록해 요청/초를 수집량으로 변환한 가정을 드러낸다.

[OTel SDK 명세](https://opentelemetry.io/docs/specs/otel/trace/sdk/#batching-processor)의 용량 제한 큐(bounded queue)는 용량이 가득 차면 span을 버릴 수 있다. [Collector 확장 지침](https://opentelemetry.io/docs/collector/scaling/)도 처리 단계별 적체와 후속 처리 단계의 병목을 구분한다. 이를 근거로 전송 거절을 곧바로 영구 유실로 합산하거나 수집기 증설만으로 전체 수용량이 늘었다고 판단하지 않는다. 실제 지표 이름·단위·집계 범위는 실행할 버전에서 확인한다.

## 과부하 이후에도 확인한다

부하를 낮춘 시점부터 큐·적체가 기준 범위에 돌아오고, 데이터 신선도·지연·오류가 목표를 다시 만족할 때까지의 시간을 측정한다. 수신 재개와 전체 복구를 구분한다. 보관되지 않은 trace나 보안 사건을 현재 관계 그래프 재조회만으로 복원했다고 표시하지 않는다.

복구 중에도 새 요청과 오래된 재처리를 구분하고 업무 중복·예외·버전 연결을 다시 대조한다. 자원 상한·실험 시간·디스크 예산 또는 기존 환경 보호 조건을 위반하면 부하를 중단하고 미완료·잔여 적체·정리 결과를 보존한다. 중단한 실행을 정상 복구로 집계하지 않는다.

점진 부하·폭주·한계 초과와 정상 부하로 돌아온 뒤의 회복을 함께 시험하는 방향은 [Google SRE의 과부하 시험 지침](https://sre.google/sre-book/addressing-cascading-failures/#test-until-failure-and-beyond)에 근거한다. 위 시나리오와 판정 계약은 이를 이 프로젝트에 적용한 검증 제안이다.

## 결과를 어떻게 판정하고 남길 것인가

- **목표를 만족한 최고 검증 부하**: 실행한 부하 단계 중 미리 정한 모든 조건을 유지 시간 동안 만족한 가장 높은 단계. 첫 위반 단계와 반복별 범위를 함께 남긴다. 더 높은 부하를 시험하지 않았다면 최대 한계를 확인한 것으로 표시하지 않는다.
- **운영 부하 제안**: 위 결과와 장애·배포·성장·편차에 필요한 여유를 근거로 제안한다. 안전 여유율은 미정이며 최고 검증 부하와 구분한다.
- **계측으로 줄어든 수용량**: 같은 조건에서 `1 − 계측 구성의 목표 충족 부하 / 미적용 구성의 목표 충족 부하`. 비교 가능한 두 결과가 없거나 목표가 미정이면 비율 판정을 보류한다.
- **플랫폼의 수용량**: 이벤트/초·bytes/초·메서드/관계/버전 규모·갱신 시간·조회 부하·보존 기간을 묶은 조건부 결과다. 자원·데이터 크기가 다른 측정을 하나의 RPS로 축약하지 않는다.

원시 입력·예정/실제 시각·상태·지연·자원 counter·적체와 버전/설정 해시를 보존한다. 미완료·측정 누락·불안정한 부하 구간은 제외 이유와 원시값을 남긴다. 정상 상태의 반복별 목표 충족 여부, 최초 위반, 과부하 중 업무·수집 결과, 정상화 시간과 비용을 같은 보고서에 연결한다.
