# 정확 입력 재사용과 대규모 Java 분석 결과

2026-11-14 로컬 실험에서 **10만 줄의 동일 입력은 전체 결과를 재사용했고, 30만 줄 단일 입력은 기존 1 GiB JVM 힙 제한에서 실패했다.** 재사용은 변경되지 않은 입력의 반복 비용을 줄인다. 큰 공통 모듈 내부가 바뀌었을 때의 분석 비용과 메서드 단위 증분 분석은 다음 검증 과제다.

관련 작업은 [#61](https://github.com/DDINGJOO/JJAM-TONG/issues/61)과 상위 [#44](https://github.com/DDINGJOO/JJAM-TONG/issues/44)다. [ADR 0008](../decisions/0008-exact-input-analysis-reuse.md), [복잡 구조 요구](../requirements/CODE-ANALYSIS-SCALE.md), [재현 CLI](../../tools/analysis_reuse/README.md), [구조화한 실측값](analysis-reuse-results.json)을 연결한다.

## 입력과 측정 조건

macOS arm64, 논리 CPU 15개, Python 3.9.6, Corretto 21.0.11에서 실행했다. 대상 바이트코드는 Java 17로 컴파일했다. 기존 JavaParser·SymbolSolver 3.28.2와 WALA 1.9.0의 실제 분석기를 사용했으며 JVM 힙 1 GiB·실행 60초·출력 10 MiB 제한을 유지했다. 컴파일 시간과 분석 시간은 나누어 기록했다.

규모 입력은 20개 메서드가 서로 호출하는 클래스들을 생성하고 각 메서드 안에 42개의 산술문을 넣었다. 공백·주석으로 줄 수를 채우지 않았으나, 실제 프레임워크·거대한 클래스 계층·복잡한 의존 관계의 밀도를 재현하는 입력은 아니다. 별도의 작은 구조 예제에서 다형성·순환·오버로드·리플렉션 등을 검증한다. 빌드·revision은 합성 명세의 식별자이며 실제 Git 커밋이나 서명된 출처 증명이 아니다.

각 단계는 한 번 실행했다. 표의 시간은 CLI 전체의 벽시계 시간이다. 최대 RSS는 `/usr/bin/time`이 보고한 명령의 최대 프로세스 상주 메모리이며, JVM 힙이나 여러 프로세스의 메모리 합계와 다르다. 다른 프로세스와 OS 캐시를 통제한 반복 성능 비교나 운영 수용량 검증으로 해석하지 않는다.

## 10만 줄과 30만 줄

| 입력과 단계 | 실제 줄 수 | 시간 | 최대 RSS | 판정 |
| --- | ---: | ---: | ---: | --- |
| 10만 줄 최초 분석 | 100,723 | 5.361초 | 1,299.25 MiB | 새 전체 분석 |
| 같은 입력과 새 빌드 명세 | 100,723 | 0.229초 | 52.80 MiB | 재사용, 현재 빌드 명세로 발행 |
| 메서드 이름 변경 후 분석 | 100,723 | 5.642초 | 1,311.69 MiB | 전체 재분석 |
| 변경 입력의 독립 전체 분석 | 100,723 | 5.084초 | 1,320.72 MiB | 재분석 결과와 의미상 동일 |
| 30만 줄 최초 분석 | 301,231 | 5.312초 | 1,177.45 MiB | `OutOfMemoryError`, 새 출력 없음 |

10만 줄 입력은 소스 110개, 원본 JAR 746,863바이트였다. JavaParser 선언은 2,181개, WALA 메서드는 생성자를 포함해 2,291개였으며 각 호출 관계는 2,180개였다. 최초 결과는 3,361,126바이트였다. 새 빌드 명세를 붙이면서 출력 바이트 수는 달라질 수 있다. 메타데이터와 그 입력 해시만 제외한 나머지 결과 전체를 대조했다.

30만 줄 입력은 소스 327개, 원본 JAR 2,379,114바이트였다. 힙 부족으로 첫 분석이 실패했으므로 재사용·변경·독립 전체 분석을 이어서 성공한 것으로 기록하지 않았다. 제한을 올리거나 실패한 결과를 빈 성공으로 대체하지 않았다. 이 결과는 현재 예산이 해당 합성 단일 입력을 감당하지 못한다는 근거다.

## 독립 입력 세 개의 비교

각각 100,723줄인 **독립 분석 입력** 세 개를 순차 실행했다. 이들은 클래스패스가 서로 얽힌 실제 모듈이 아니다. 세 입력의 합이 약 30만 줄이라는 이유로 원래 단일 그래프를 안전하게 분할했다고 주장하지 않는다.

| 단위 | 최초 분석 | 동일 입력 재사용 | 다음 빌드 |
| --- | ---: | ---: | --- |
| module-0 | 5.312초 | 0.223초 | 메서드 변경으로 재분석, 5.560초 |
| module-1 | 5.303초 | 0.227초 | 재사용, 0.229초 |
| module-2 | 5.522초 | 0.237초 | 재사용, 0.235초 |

다음 빌드에서는 세 단위 중 두 개를 재사용했다. 변경 단위의 결과는 같은 입력의 독립 전체 분석과 일치했고, 변경되지 않은 단위는 이전과 같은 의미의 결과를 현재 빌드 명세로 발행했다. 교차 단위 그래프 결합·실제 의존 모듈 변경 전파·작업 큐는 구현하지 않았다.

## 복잡 구조의 실제 판정

작은 합성 예제는 소스 12개, 물리적 43줄로 구성했다. 큰 입력의 비용 측정과 구분하여 관계의 의미를 확인한다. JDK 17.0.19와 21.0.11에서 각각 최초·재사용·변경·독립 전체 분석을 수행했다.

| 검증 | 결과 |
| --- | --- |
| 인터페이스 선언과 구현체 후보 | JavaParser는 인터페이스 선언을, WALA는 두 구현체 후보를 반환했다 |
| 패키지 경계를 넘는 호출 | 공통 규칙 패키지로 연결된 후보를 보존했다 |
| 순환 호출 | A→B와 B→A 후보를 모두 보존했다 |
| 오버로드 | 두 정적 descriptor를 구분했다. 실제 span의 overload 확정과는 별개다 |
| 컴파일러 브리지 | 소스 구현과 WALA의 Object/String descriptor를 구분했다 |
| 리플렉션 | JavaParser가 미해결 이유를 반환했다. WALA는 숨은 대상을 임의 호출로 연결하지 않았다 |
| 람다와 메서드 참조 | JavaParser가 각각의 해석 공백을 반환했다 |
| 메서드 삭제 | 새 버전에서 삭제된 메서드가 두 분석기의 목록에서 제거됐다 |
| 재사용과 변경 후 대조 | 메타데이터를 제외한 완전한 본문이 각 독립 전체 분석과 일치했다 |

이 예제는 Spring DI·프록시·Lombok·QueryDSL·이벤트 브로커의 정밀한 해석을 검증하지 않는다. 해당 구조와 누락된 클래스패스·생성 입력을 다루는 요구는 [구조별 검증표](../requirements/CODE-ANALYSIS-SCALE.md)에 남긴다. 회사 소스와 내부 식별자는 공개 예제에 포함하지 않는다.

## 실패 경계와 후속 검증

단위 검사는 입력·도구 변경, 현재 빌드 명세, 손상·부분 결과, 실행 실패, 입력 변경, 출력 충돌, 동시 요청에서 분석이 한 번만 실행되는지 확인한다. 실제 재사용 통합은 일반 JAR에서 검증했다. 기존 Boot 분석기·GitHub 수집기·DB·화면이 이 재사용 도구를 자동으로 쓰는 상태는 아니다.

큰 공통 모듈에는 의존 클래스패스와 생성 입력을 보존하는 분석 경계가 필요하다. 다음 검증에서는 구현체·상속·공유 라이브러리의 추가와 삭제가 다른 호출부에 미치는 영향을 추적하고, 전체 분석과 관계 집합을 대조한다. 실제 운영 부하·동시 작업 수·조직별 격리·보존·원격 캐시의 신뢰 경계는 [수용량 검증 계획](CAPACITY-VALIDATION.md)과 함께 검증한다.

## 최종 검증

새 단위 검사 12개와 기존 메서드 근거·저장 계약의 회귀 검사 21개가 통과했다. 실제 동시 CLI 두 개는 하나가 분석하고 하나가 재사용했으며, 완전한 본문이 같았다. 재사용한 결과는 현재 빌드의 메서드 색인 28개로 변환됐고 저장 계약의 입력 검증도 통과했다. DB에 새 결과를 저장하거나 화면을 변경하지는 않았다.

독립 코드 검토의 지적 3건을 수정한 뒤 재검에서 차단 지적 0건을 확인했다. 재검 판정은 검토 환경의 테스트·진단 실행 제한 때문에 `COMMENT`였으며, 위 테스트는 주 작업 환경에서 별도로 실행했다. LSP 진단 서비스는 없어 실행하지 못했다. 별도 AI의 국문 편집 지적 3건을 수정하고 재검 `APPROVE`·0건을 확인했다. Python 구문, 상대 링크 221개, 기능 파일 12개·고유 시나리오 75개의 구조와 위키 원본 8개의 내보내기를 검증했다. BDD 실행기 없는 명세와 실제 CLI 검증은 구분한다.
