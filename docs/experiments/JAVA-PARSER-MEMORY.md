# Java 파서 메모리와 소스 위치 보존 결과

2026-11-14 로컬 검증에서 **분석기 0.2.1은 301,231줄 합성 입력을 기존 1 GiB JVM 힙에서 완료했다.** 선언·호출의 소스 위치를 보존했고 이전 분석기의 기준 결과와 일치했다. 401,023줄 입력은 10 MiB 출력 제한으로 발행되지 않았다. 특정 합성 입력의 결과이며 기업 코드의 수용량을 입증한 것은 아니다.

작업은 [#63](https://github.com/DDINGJOO/JJAM-TONG/issues/63), 상위 [#44](https://github.com/DDINGJOO/JJAM-TONG/issues/44)다. [ADR 0009](../decisions/0009-java-parser-retention.md), [기존 실패 결과](ANALYSIS-REUSE-RESULTS.md), [구조화한 실측값](java-parser-memory-results.json), [범용성 요구](../requirements/CODE-ANALYSIS-SCALE.md)를 연결한다.

## 입력과 실행 조건

macOS arm64, 논리 CPU 15개, Python 3.9.6, Corretto 21.0.11에서 규모 비교를 실행했다. 기존 생성기의 합성 소스를 Java 17 바이트코드로 컴파일했고 JavaParser·SymbolSolver 3.28.2와 WALA 1.9.0을 사용했다. 현재 CLI의 힙 1 GiB·60초·출력 10 MiB 제한과 두 분석기가 모두 성공한 뒤 발행하는 정책은 유지했다.

각 메서드의 산술문을 늘린 규모 입력과 다형성·순환·오버로드·간접 호출을 다루는 작은 구조 예제를 구분한다. 실제 프레임워크·의존성·상속 계층의 밀도를 재현한 입력은 아니다. 같은 입력을 다시 쓰는 단계는 새 빌드 명세를 받으며, 변경 단계에서는 메서드 하나의 이름과 호출부를 바꾼다. 빌드 명세는 합성 식별자이며 서명된 출처 증명이 아니다.

표의 시간은 각 명령을 한 번 실행한 벽시계 시간이다. 최대 RSS는 `/usr/bin/time`이 보고한 명령의 최대 프로세스 상주 메모리다. JVM 힙 제한과 프로세스 전체 메모리 상한은 다르며, 여러 프로세스의 메모리 합계도 아니다. OS 캐시와 다른 작업을 통제한 반복 성능 비교는 수행하지 않았다.

## 정책 비교와 규모 결과

이전 분석기 0.2.0의 조회 캐시에만 32개 제한을 둔 실험은 같은 힙에서 실패했다. 모든 파서의 토큰 보관을 끈 실험은 완료됐지만 소스 줄 번호가 `-1`이 되어 제외했다. 채택한 설정은 직접 파싱의 소스 위치를 유지하고 타입 조회용 파서의 토큰·주석 보관과 캐시를 제한한다.

**32개는 타입 조회 캐시의 항목 수 제한이다.** 전체 구문 트리(AST)·힙·프로세스 메모리를 32개 또는 특정 바이트로 제한한다는 뜻이 아니다. 캐시별 참조가 보유하는 메모리 비중을 힙 덤프로 분석하지 않았고, 최적의 캐시 크기도 결정하지 않았다.

| 입력과 정책 | 힙 | 시간 | 최대 RSS | 결과 |
| --- | ---: | ---: | ---: | --- |
| 100,723줄, 이전 분석기 | 1 GiB | 4.952초 | 1,334.80 MiB | 완료, 현재 결과와 본문 일치 |
| 100,723줄, 현재 최초 분석 | 1 GiB | 6.317초 | 1,289.97 MiB | 완료 |
| 301,231줄, 이전 분석기 | 1 GiB | 4.922초 | 1,159.75 MiB | 힙 초과, 새 결과 없음 |
| 301,231줄, 현재 최초 분석 | 1 GiB | 17.453초 | 1,259.17 MiB | 완료, 출력 10,045,343바이트 |
| 301,231줄, 이전 분석기의 진단 실행 | 2 GiB | 25.736초 | 2,389.75 MiB | 완료, 현재 결과와 본문 일치 |
| 401,023줄, 현재 최초 분석 | 1 GiB | 30.042초 | 1,307.03 MiB | 출력 상한 초과, 새 결과 없음 |

2 GiB 진단 실행은 이전 분석기의 정확성 기준을 얻기 위한 것이다. 같은 자원 예산의 속도 비교에 사용하지 않는다. 10만 줄에서는 현재 최초 분석 시간이 이번 표본에서 더 길었다. 캐시 축소의 재파싱 비용·성능 분산은 별도 검증해야 한다.

## 재사용·변경·기준 결과의 대조

| 입력 | 재사용 | 변경 후 전체 분석 | 변경 입력의 독립 전체 분석 | 판정 |
| --- | ---: | ---: | ---: | --- |
| 100,723줄 | 0.225초 | 6.279초 | 6.033초 | 같은 입력의 재사용, 변경 입력의 새 분석과 독립 결과가 각각 일치 |
| 301,231줄 | 0.390초 | 18.118초 | 18.101초 | 같은 입력의 재사용, 변경 입력의 새 분석과 독립 결과가 각각 일치 |

이전 분석기와의 비교에서는 Git commit `c447c2c`의 분석기 소스를 다시 컴파일했다. 같은 소스·원본 JAR·타입 해석 조건에서 전체 본문을 비교했고, 빌드 메타데이터와 그 해시, `adapterVersion`만 제외했다. 소스 경로·줄 번호·메서드 키·관계·미해결 이유는 비교에 포함했다. 30만 줄의 선언 메서드는 JavaParser 6,521개, WALA 6,848개였고 호출 관계는 각각 6,520개였다. 소스 선언과 바이트코드 생성 메서드의 차이는 유지한다.

작은 구조 예제의 최초·재사용·변경·독립 전체 분석과 기존 구조 판정 11개가 통과했다. 메모리 변경을 언어·프레임워크의 해석 범위 확대로 표현하지 않는다.

## 경로·위치·소비자 회귀 검사

새 `SourceLocationOracle`은 패키지와 소스 루트가 다른 두 입력을 만든다. 각 입력은 48개 타입을 여러 패키지에서 참조하며 조회 캐시의 설정값보다 많은 타입을 포함한다. 독립적으로 정한 선언 51개·호출 97개의 메서드 키·descriptor·상대 파일·정확한 줄 번호를 비교하고, 중복·누락·미해결과 출력 비결정성을 검사한다. 변경 전 분석기로 먼저 통과시켜 기존 동작을 고정했다.

JDK 17.0.21과 21.0.11에서 기존 호출·Boot 경계·새 소스 위치 검사 세 개를 각각 실행했다. 새 의존성은 추가하지 않았고, JDK 17 검증용 도구는 [공식 배포 목록](https://docs.aws.amazon.com/corretto/latest/corretto-17-ug/downloads-list.html)의 압축 파일을 SHA-256으로 확인해 로컬에서 사용했다.

기존 소비자 검사 46개가 통과했다. 첫 기본 Python 실행은 이미 설치된 `psycopg`를 찾지 못해 1개가 실행되지 않았고, 프로젝트의 기존 가상환경에서 46개를 다시 실행했다. 실제 10만 줄의 이전·현재 결과는 각각 메서드 색인 2,291개로 변환해 저장 입력 검증을 통과했다. 메서드 집합은 같고 분석 설정 해시는 버전 변경에 따라 달랐다. 30만 줄도 메서드 6,848개·인코딩된 색인 6,917,389바이트로 저장 입력 검증을 통과했다. 새 DB 쓰기나 화면 변경은 수행하지 않았다.

## 재현

저장소 루트에서 기존 고정 도구로 빌드한 뒤 실행한다. 출력 디렉터리는 매번 새 경로여야 한다. JDK 경로는 설치한 JDK 17 또는 21의 경로로 바꾼다.

```sh
python3 tools/java-call-analysis/build.py
python3 tools/java-call-analysis/verify.py --java-home /path/to/jdk17
python3 tools/java-call-analysis/verify.py --java-home /path/to/jdk21
python3 -m experiments.analysis_reuse.run --java-home /path/to/jdk21 --output .local/parser-memory-scale
python3 -m experiments.analysis_memory.run --java-home /path/to/jdk21 --fixture-dir .local/parser-memory-scale --baseline-revision c447c2c --output .local/parser-memory-reference
python3 -m experiments.analysis_reuse.run --java-home /path/to/jdk21 --output .local/parser-memory-output-cap --sizes 400000
```

기준 비교 도구는 이 저장소의 지정한 Git revision에서 분석기 소스만 컴파일·실행한다. 신뢰하는 분석기 revision을 전달해야 한다. 대상 앱의 빌드 스크립트·업무 코드는 실행하지 않는다. 2 GiB 진단 실행을 별도 표시하고 모든 기준 실행에도 60초 상한을 적용한다. 현재 분석기의 제한을 변경하지 않는다. 플랫폼의 테스트 대상 앱을 저장소에 복사하지 않으며 예제는 합성 소스뿐이다.

## 다음 검증

출력 직전에 10 MiB를 넘으면 결과를 발행하지 않는다. 현재는 전체 결과를 문자열·바이트로 만든 뒤 크기를 검사하므로, 출력 상한이 직렬화 중 메모리 사용까지 미리 제한하지는 않는다. [#64](https://github.com/DDINGJOO/JJAM-TONG/issues/64)에서 표현 크기·분할 저장·작업 완료 명세·실패 원인과 자원 예산을 함께 비교한다.

의존성이 많은 입력, 높은 다형성·호출 밀도·큰 단일 클래스, 생성 코드·불완전한 빌드, 동시 분석·조직별 자원 격리, 실제 프레임워크의 지원 수준은 앞으로 검증한다. [#65](https://github.com/DDINGJOO/JJAM-TONG/issues/65)·[#66](https://github.com/DDINGJOO/JJAM-TONG/issues/66)과 [수용량 계획](CAPACITY-VALIDATION.md)을 연결한다. BDD-UPD-011·012는 실행기 없는 Draft 명세이며 위의 실제 Java·CLI 검증과 구분한다.
