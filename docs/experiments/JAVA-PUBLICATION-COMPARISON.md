# 실제 Java 결과의 저장 표현과 소비자 상한 비교

2026-11-14 · [#72](https://github.com/DDINGJOO/JJAM-TONG/issues/72), 상위 [#68](https://github.com/DDINGJOO/JJAM-TONG/issues/68).

40만 줄 합성 Java 분석은 출력 파일의 10 MiB 상한에서 실패했다. 분석 파일의 상한만 늘리면 후속 단계도 수용할 수 있는지, 같은 JSON의 공백을 줄이거나 결과를 여러 파일로 나누면 어디까지 해결되는지 비교한다. 1 MiB는 1,048,576바이트다.

## 입력과 비교 방법

공개 생성기로 만든 401,023줄의 Java 소스와 일반 JAR 하나를 사용한다. JavaParser와 WALA를 실제로 실행한 결과이며 임의의 관계 목록을 대신 넣지 않는다. 실제 기업 소스나 복잡한 서비스 전체를 대표하는 입력은 아니다.

기존 분석기 `0.2.2`의 소스를 격리해 출력 상한만 32 MiB로 바꾸고, 출처의 분석기 버전을 `0.2.2-probe32`로 구별했다. 제품의 기본 상한과 소비자는 수정하지 않았다. JDK 21·힙 상한 1 GiB에서 한 번 실행해 30.748초, 최대 상주 메모리(RSS) 1,357,447,168바이트를 기록했다. RSS에는 힙 이외의 메모리도 포함된다.

세 저장 표현을 다시 읽어 원본 JSON 전체와 대조한다. 목록의 순서, 소스 위치, 미해결·제외 항목과 선택 필드도 비교 대상이다. 같은 분석 실행 ID로 만든 색인 해시도 같아야 한다. 소스·JAR·입력 명세는 기존 `create_index`로 검증한다. 결과와 재현 명령은 [실험실](../../experiments/java_publication_lab/README.md)에 있다.

## 실제로 확인한 바이트 경계

| 단계 | 들여쓰기 | 공백을 줄인 JSON | 기존 상한·판정 |
| --- | ---: | ---: | --- |
| 실제 Java 분석 결과 | 13,372,075바이트 | 7,647,618바이트 | 10 MiB. 기존 표현은 초과하며 공백을 줄인 표현은 이하 |
| 같은 분석의 메서드 색인 | 14,526,183바이트 | 8,433,407바이트 | `save_index`의 10 MiB. 기존 저장은 거부 |
| DB 입력 검증용 직렬화 | 해당 없음 | 기본 공백을 포함하면 9,207,855바이트 | `prepare`의 10 MiB. 기존 검증에서 수락 |

위 색인 크기는 최초 탐색의 실행 ID `actual-400k`를 사용한 값이다. 재현 실험의 실행 ID가 다르면 그 문자열 길이만큼 색인 크기와 해시가 달라질 수 있다. 분석 결과의 고유 메서드는 9,116개다.

DB 입력 검증의 통과는 실제 DB 저장의 성공을 뜻하지 않는다. 분석 결과·색인 파일·DB 검증은 서로 다른 자료구조와 직렬화 규칙을 사용한다. 앞 단계의 상한을 늘렸다는 이유로 뒤 단계의 수용을 가정하지 않는다.

## 세 대안의 비용

| 대안 | 해결하는 경계 | 변경·재처리 비용 | 남는 한계 |
| --- | --- | --- | --- |
| 들여쓰기 단일 파일의 상한 확대 | 격리된 32 MiB 생산자가 실제 결과를 발행했다 | 생산자·색인 저장·수집·DB 검증의 예산을 각각 검토해야 한다. 실패하면 전체 파일을 다시 발행한다 | 생산자만 바꾸면 색인에서 다시 실패한다. 수신 시 전체 결과를 읽는 비용도 남는다 |
| 같은 v1 JSON의 공백 제거 | 이번 실제 결과와 색인이 기존 10 MiB 이하가 된다 | 생산자·파일 색인·CI 포장의 출력 설정을 맞춘다. 기존 JSON 독자는 그대로 사용하며 전체 파일을 재발행한다 | 분석 결과 Map과 소비자의 전체 자료구조는 남는다. 더 큰 입력은 여전히 상한에서 거부된다 |
| 불변 조각과 완료 명세 | 파일당 예산을 유지하며 하나의 논리 결과를 나눌 수 있다 | 모든 조각의 해시·입력·시도·단계와 완료 명세를 검증한다. 재시도는 같은 내용을 재사용하되 시도가 바뀌면 헤더·해시도 달라진다 | 현재 어댑터는 전체 결과를 다시 조립한다. 기존 색인·DB의 단일 결과 예산을 자동으로 해결하지 않는다 |

분할 비교는 [#64의 계약](ANALYSIS-JOB-CONTRACT.md)을 재사용한다. 상위 메타데이터 한 단계와 두 분석기의 메서드·호출·미해결·제외 목록 여덟 단계로 나눈다. 빈 목록도 명시적인 단계로 보존한다. 기본 예산은 조각당 1 MiB, 레코드당 128 KiB, 전체 64 MiB이며 완료 명세도 전체 바이트에 포함한다. 입력 명세 자체가 한 레코드보다 크면 분석 레코드 수와 무관하게 실패할 수 있다.

파일을 중간 상태 없이 교체하는 방식도 다르다. 단일 파일은 같은 디렉터리의 임시 파일을 끝까지 쓴 뒤 이름을 교체한다. 분할 방식은 조각을 불변 파일로 먼저 저장하고 마지막 완료 명세를 공개한다. 명세가 없으면 완료가 아니며, 명세가 있어도 조각 검증에 실패하면 소비하지 않는다. 기존 DB 발행은 검증을 마친 색인과 관계를 하나의 트랜잭션으로 저장한다. 어느 방식도 이 로컬 비교만으로 분산 발행자 제어나 전원 장애 내구성을 입증하지 않는다.

## GitHub 수집 경로와 구분한다

현재 CI 발행자는 `method-fixture`와 정확한 GitHub 실행 문맥만 지원한다. 40만 줄 합성 입력의 저장소·모듈을 바꿔서 실제 Actions 근거로 취급하지 않는다. 수집기의 제한은 ZIP 전체 12 MiB, 색인 10 MiB, 명세 16 KiB이며 두 파일만 허용한다. 이 비교의 분할 표현은 현재 수집 규격이 아니다.

공백을 줄여도 파일 바이트 해시는 달라진다. CI 명세의 파일 해시는 실제 발행한 바이트로 다시 계산해야 한다. 반면 같은 논리 색인의 정규화 해시는 저장 공백에 영향을 받지 않는다. 분석기 버전이 바뀌면 설정 해시도 달라지므로 이전 분석으로 묵시적으로 재사용하지 않는다.

## 판정과 다음 검증

실제 결과의 분할 표현은 완료 명세를 포함해 8,039,654바이트, 조각 15개였다. 세 표현의 JSON 전체와 파생 색인 해시가 일치했다. 같은 분할 결과를 다시 발행해 기존 완료 명세를 재사용하고, 다른 입력·시도, 조각 누락·손상, 작은 전체 수신 예산을 각각 거부했다. 동일 계약의 단위 검사는 중단·전체 발행 예산 초과·동시 발행도 다룬다. [원시 결과](java-publication-comparison-results.json)에 실제 판정을 기록한다.

한 프로세스에서 표현을 순서대로 비교한 시간은 각 표현의 독립적인 성능 순위로 해석하지 않는다. 비교 프로세스의 최대 RSS는 측정하지 않았다. 앞의 Java 실행 RSS는 분석 전체의 단일 표본이다.

[ADR 0011](../decisions/0011-java-compact-publication.md)에 다음 로컬 구현의 선택과 조건을 기록한다. 실제 생산자·색인 전환, 이전·새 빌드의 DB 발행과 브라우저 QA는 [#73](https://github.com/DDINGJOO/JJAM-TONG/issues/73)에서 이어간다. 이번 비교에서는 지속 수용량, 임의 크기 지원, Boot 전체 CI 발행, 실제 런타임 수집을 검증하지 않았다.
