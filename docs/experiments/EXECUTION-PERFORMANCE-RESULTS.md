# 관측 에이전트 적용 전후의 HTTP 성능 비교

날짜: 2026-11-12. 상태: **로컬 비교 결과**.

[T25 #44](https://github.com/DDINGJOO/JJAM-TONG/issues/44) · [앞선 메서드 검증](METHOD-OBSERVABILITY-RESULTS.md) · [ADR 0004](../decisions/0004-method-evidence-comparison.md) · [구조화한 결과](execution-performance-results.json).

관측 기능을 넣어도 업무 요청이 얼마나 느려지는지 확인해야 한다. 앞선 순수 Java 입력은 기준 호출 시간이 너무 짧아 성능 비율을 판정하지 못했다. 이번에는 별도 Boot 앱이 실제 Redis·PostgreSQL·Kafka를 사용하는 조건에서 에이전트 적용 전후를 비교했다.

세 구성에 기존 빌드 식별 계약 JAR과 수동 검증 코드는 동일하게 들어 있다. 아래 결과는 **OTel 에이전트와 메서드 추적을 추가한 비용**이며, JJAM-TONG의 모든 기능을 제거한 앱과의 차이는 아니다. 프로파일러·CMDB·SIEM 수집 비용은 이 비교에 포함하지 않았다. 별도 프로세스에서 수행하는 정적 분석의 비용은 [앞선 결과](METHOD-OBSERVABILITY-RESULTS.md#비용과-제한)에 있다.

동시성 4에서 미적용 대비 메서드 추적의 p50 증가는 +0.9~1.4%, p99 증가는 +5.8~53.0%였다. 요청당 HTTP 구간 CPU는 +21.8~29.1%, 최대 표본 RSS는 +37.9~38.8%였고, 성공 처리량은 0.7~5.2% 감소했다. 모두 모델별 3개 반복 쌍의 증감률 중앙값 범위이며, 일부 지표만으로 비용이 작다고 판정하지 않는다.

## 같은 앱에서 무엇을 바꾸었나

MVC 일반 스레드·MVC 가상 스레드·Netty를 각각 비교했다. 앱 모델마다 구성의 실행 순서를 바꾸어 새 JVM으로 3회 반복했다. 같은 모델·동시성 안에서 비교하며 서로 다른 서버의 성능 순위를 정하지 않는다.

- 대상: Boot 4.1.2·컨테이너 JDK 21.0.13+9-LTS, 대상 revision `1707e7c9e01e19d52bb90fbf13cb70414d5d7a6d`, 빌드 `method-agent-b1`.
- OTel Java agent 2.33.1. JAR·Docker 이미지·설정의 SHA-256은 구조화한 결과에 고정했다.
- 앱마다 1 CPU·512MiB 제한, 같은 JVM `-Xms64m -Xmx192m`, DB 연결 풀의 최대 연결 수 2개, 앱 작업 상한 4개.
- 새 JVM마다 사전 업무 검증 1건·warmup 100건 후 동시성 1에서 300건, 동시성 4에서 600건. 요청의 DB 대기는 5ms로 같게 고정했다.
- 총 측정 요청 24,300건·warmup 2,700건·사전 검증 27건. 앞선 짧은 pilot 3회는 본 결과에서 제외했다.
- 에이전트 구성의 수집은 `always_on`, exporter는 `logging-otlp`, metrics/log exporter는 `none`. SDK 큐 용량은 span 8,192개, 전송 묶음은 최대 span 512개, 주기 설정은 100ms로 동일하게 두었다. 메서드 구성만 선택 계측을 추가했다.
- Docker Desktop 29.5.3의 Linux aarch64·cgroup v2. VM에 보이는 자원은 15 vCPU·약 7.75GiB이며 앱마다 할당한 1 CPU와 구분한다.

각 요청은 고유한 합성 ID를 사용해 Redis 저장·조회, DB 관측 행과 outbox 저장을 실행한다. outbox는 DB에 보관한 발행 대기 기록이며, 별도 예약 작업이 Kafka로 보내고 소비자가 이벤트 처리 결과를 DB 행으로 남긴다. 이하 이 행을 ‘효과 행’이라 부른다. HTTP 응답 뒤에 완료될 수 있으므로 응답시간과 후속 처리 완료를 구분한다.

p50·p95·p99는 요청의 각각 50%·95%·99%가 그 시간 안에 완료됐다는 뜻이다. 성공 응답의 원시값을 정렬해 nearest-rank 방식(정렬한 값에서 `올림(비율 × 표본 수)`번째 선택)으로 구하고, 표에는 독립 실행 3개의 분위수 중앙값을 표시했다. 오류·거절·타임아웃 표본과 분모는 구조화한 결과에 따로 남긴다. 실패 응답으로 응답시간이 짧아진 경우를 낮은 적용 비용으로 판정하지 않는다.

한 작업자가 응답을 받은 뒤 다음 요청을 보내는 closed-loop 부하를 썼다. **같은 동시성에서의 지연·처리량**이며, 동일 도착률이나 최대 수용량·운영 SLO를 검증한 결과는 아니다. 응답이 느려지면 다음 요청의 시작도 늦어진다. [부하 모델의 차이](https://grafana.com/docs/k6/latest/using-k6/scenarios/concepts/open-vs-closed/).

CPU는 앱 컨테이너의 누적 사용 시간인 `cpu.stat/usage_usec`의 구간 차이로 계산했다. `CPU ms/성공 요청 = CPU 사용 증가분(µs) / 1,000 / 성공 요청 수`다. HTTP 부하 구간과 후속 처리·고정 대기를 포함한 완료 구간을 구분한다. CPU quota로 실행이 제한된 시간과 횟수도 기록한다. 표의 마지막 열은 HTTP 부하 구간의 `throttled_usec` 증가분을 초로 바꾼 3회 중앙값이다. [Linux cgroup CPU 정의](https://docs.kernel.org/admin-guide/cgroup-v2.html#cpu-interface-files).

RSS는 실제 메모리에 올라온 Java 프로세스의 메모리이며 Java heap과 다르다. PID 1이 Java인지 확인하고 주기적으로 읽은 `VmRSS`의 최대값과 프로세스 생애의 `VmHWM`을 구분했다. `memory.current`는 페이지 캐시 등을 포함한 컨테이너 전체의 메모리다. 앱 cgroup 값은 별도 DB·Redis·Kafka와 Docker VM 전체의 비용을 포함하지 않는다. [프로세스 메모리 정의](https://docs.kernel.org/filesystems/proc.html#process-specific-subdirectories), [cgroup 메모리 정의](https://docs.kernel.org/admin-guide/cgroup-v2.html#memory-interface-files).

기존 문서의 지연 20% 예산 제안을 이번 p50 증감률 중앙값에 참고선으로 대입하면, 미적용 대비 12개 비교 중 0개가 초과했다. 이는 이번 입력의 지연 판정이며 CPU·메모리·p95의 허용 기준이나 운영 도입 승인은 아니다. 구성별 반복 편차는 구조화한 결과의 `pairedDeltas`에서 함께 확인해야 한다.

## 정확성과 측정 경계

27회 모두 비교 조건을 충족했다. 측정 요청 24,300건은 모두 성공했고, warmup·사전 검증을 포함한 27,027개 입력의 발행·효과 행을 확인했다. 중복·재시도 결과와 자원 샘플링 오류는 없었다. 에이전트 두 구성에서 성공 입력에 대응하는 HTTP 추적 18,018개를 확인했으며, 메서드 구성에서는 선택한 `create` 실행 9,009개를 확인했다. 미적용 구성의 에이전트 span과 기본 구성의 선택 메서드 span은 각각 0개였다.

HTTP 성공 ID만 검사하면 타임아웃 뒤 커밋된 요청을 놓칠 수 있다. 전송한 모든 고유 ID와 해당 실행의 DB 상태를 대조했다. 각 구간 사이에는 이전 요청의 발행·효과 처리가 끝나기를 기다려 다음 구간의 업무 부하와 구분했다. 효과 행 각 1개는 이번 입력의 결과이며 분산 시스템의 exactly-once 보장은 아니다.

DB 후속 처리 완료는 비동기 exporter의 작업 완료를 뜻하지 않는다. 모든 구성에 같은 고정 후속 대기를 적용하고 그 CPU를 따로 남겼다. 큐가 비었다는 증명이나 JVM 종료 때의 최종 전송 비용으로 표현하지 않는다. 로그에서 확인한 span은 전송 결과이며 SDK 생성량이나 실제 유실 0건을 보장하지 않는다.

macOS Docker Desktop의 Linux VM에서 측정했다. 공유 DB·Kafka·Redis, VM 자원 경쟁, 누적된 합성 데이터·캐시와 짧은 warmup이 결과에 영향을 줄 수 있다. 자원 샘플링 명령의 비용도 앱 cgroup에 포함된다. 검증용 관측 행의 DB 쓰기까지 포함한 합성 요청이므로 실제 게시판 운영 트래픽과 구분한다. 동일한 warmup 횟수만으로 JVM의 실행 중 코드 최적화(JIT)가 안정됐다고 보장하지 않는다. [Docker VM 자원](https://docs.docker.com/desktop/settings-and-maintenance/settings/#vm-resources).

이번 빌드의 관측 행도 별도로 확인했다. 요청 진입·작업·Kafka consumer의 가상 스레드 여부는 MVC 가상 구성에서 참이고, MVC 일반·Netty 구성에서는 거짓이었다. 27개 실행·3개 단계의 81개 묶음이 각각 1,001개 입력과 해당 빌드 해시를 가졌다. 이는 이 Boot 설정의 결과다.

## 재현과 원시 근거

다음 명령은 기본값으로 본 비교 행렬을 실행한다. `TARGET_ROOT`는 고정 빌드가 있는 별도 대상이며, `PERF_OUTPUT`은 이 저장소의 `.local/` 아래에 새로 정한 출력 디렉터리다.

```sh
python3 -m experiments.execution_performance \
  --target "$TARGET_ROOT" --build-id method-agent-b1 \
  --agent "$OTEL_AGENT_JAR" --output "$PERF_OUTPUT" --run

python3 -m experiments.execution_performance \
  --target "$TARGET_ROOT" --output "$PERF_OUTPUT" --summarize
```

[측정기](../../experiments/execution_performance.py) · [실패 경계 검사](../../experiments/test_execution_performance.py). 재요약은 원시 해시와 현재 판정기를 확인하며 앱을 다시 기동하지 않는다. 설정·코드·아티팩트가 바뀌면 기존 실행에 덮어쓰지 않는다.

측정기 경계 검사 25개와 기존 회귀 검사 59개, 총 84개를 새로 실행해 통과했다.

독립 코드 검토에서 발견한 정리 예외와 자원 샘플링 오류 전파 문제 2건을 수정하고 재검에서 0건을 확인했다. 원래 pilot의 원시 기록·소스 해시·측정기 사본은 보존했다. 본 측정에는 수정한 측정기만 사용했다.

원시 지연·상태·자원 counter와 앱·에이전트·설정 해시를 보존했다. 공개 결과에는 소스·인수·반환 본문·SQL·인증정보·로컬 경로를 넣지 않는다. 실제 앱은 별도 로컬 저장소에 있으므로 공개 저장소만으로 대상 앱까지 재생성할 수 있다는 보장은 없다. 기존 컨테이너 11개는 보존하고 이번 임시 앱만 종료·제거했다.
