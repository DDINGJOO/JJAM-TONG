# Java v1 결과를 저장하면서 출력 상한을 검사하기

2026-11-14 · [#68](https://github.com/DDINGJOO/JJAM-TONG/issues/68)의 첫 하위 작업 [#70](https://github.com/DDINGJOO/JJAM-TONG/issues/70). [분석 작업 계약 실험](ANALYSIS-JOB-CONTRACT.md)과 [ADR 0010](../decisions/0010-analysis-job-publication.md)의 후속 구현이다.

기존 분석기는 결과 전체를 JSON 문자열로 만든 뒤 UTF-8 바이트 배열로 복사하고, 그제야 10 MiB(10,485,760바이트) 상한을 검사했다. 이번에는 단일 파일 형식을 유지하면서 직렬화, 즉 자료구조를 저장할 형식으로 바꾸는 도중에 출력 바이트를 검사한다.

## 변경한 경계

분석기 `0.2.2`는 기존 Gson으로 JSON을 같은 디렉터리의 임시 파일에 순서대로 쓴다. UTF-8 인코더 아래의 바이트 제한 스트림이 끝 개행까지 10 MiB에 포함한다. 제한을 넘을 쓰기는 파일에 전달하지 않는다. 인코더를 닫는 과정까지 성공해야 원자적 이름 교체를 시도하며, 실패하면 임시 파일을 정리한다. 원자적 이동을 지원하지 않는 환경에서 일반 복사로 우회하지 않는다.

`jjamtong.methods.v1`, 들여쓰기·이스케이프 설정, 끝 개행, 기본 출력 상한과 오류 문구는 유지한다. 분석기 버전과 생산자 JAR 해시가 달라지므로 정확 입력 재사용과 소비자의 설정 식별에도 새 버전이 반영된다. 출력 상한 확대와 분할 형식 도입은 이번 변경에 포함하지 않는다.

## 실행한 검증

새 발행 오라클은 올바른 결과와 실패를 판정하는 실행 검사다. 제한 이하·정확한 경계·1바이트 초과, 개행, 한글·이모지·잘못된 서로게이트·이스케이프, 반복 발행의 바이트 일치를 검사한다. 서로게이트는 UTF-16에서 일부 문자를 표현하는 코드 단위이며 잘못된 조합의 치환도 기존 방식과 대조했다. 기존 파일 보존, 없던 파일의 발행 거부, 직렬화 예외, 비어 있지 않은 디렉터리로의 이동 실패와 임시 파일 정리도 확인했다.

큰 첫 항목 뒤에 의도적으로 실패하는 항목을 둔 입력에서는, 바이트 제한이 다음 항목을 읽기 전에 직렬화를 중단하는지 확인한다. 이는 전체 결과를 다 만든 뒤 크기만 검사하는 구현을 구별한다. 기본 10 MiB에 정확히 맞는 결과의 성공과 1바이트 초과 거부도 실제 파일로 검사했다.

```sh
python3 tools/java-call-analysis/build.py
python3 tools/java-call-analysis/verify.py --java-home /path/to/jdk17
python3 tools/java-call-analysis/verify.py --java-home /path/to/jdk21
```

새 발행 검사 34개와 기존 호출·Boot 입력·소스 위치 오라클을 JDK 17과 21에서 각각 실행해 통과했다. 기존 재사용·메서드·저장·수집 경로의 회귀 검사 46개도 통과했다. Maven 빌드 성공과 오라클 실행은 별개로 판정했다. [공개 JSON](java-result-publication-results.json)에 실행 결과와 소스 해시를 기록한다.

## 실제 합성 Java 입력의 결과

기존에 생성한 10만 줄 합성 소스·JAR을 이전 분석기와 새 분석기로 각각 한 번 분석했다. JDK 21·힙 상한 1 GiB에서 같은 로컬 호스트를 사용했다. 시간은 프로세스 시작부터 종료까지, RSS는 운영체제가 보고한 프로세스 최대 상주 메모리다. RSS에는 힙 이외의 메모리도 포함되므로 힙 상한과 같지 않다.

| 입력·경로 | 종료 | 시간 | 최대 RSS | 결과 |
| --- | --- | --- | --- | --- |
| 10만 줄·기존 발행 | 0 | 6.224초 | 1,295,482,880바이트 | 3,361,137바이트 발행 |
| 10만 줄·제한 스트림 | 0 | 6.033초 | 1,294,532,608바이트 | 3,361,137바이트 발행 |
| 40만 줄·제한 스트림 | 1 | 29.872초 | 1,347,584,000바이트 | 상한 초과로 새 결과 거부, 이전 결과 보존 |

10만 줄의 두 결과는 분석기 버전 `0.2.1 → 0.2.2` 표시 한 곳을 제외하면 바이트까지 같았다. 새 결과를 기존 `create_index`에 넣어 저장·재조회하고 DB 입력 계약으로 검증했다. 색인은 3,651,712바이트, 고유 메서드는 2,291개였다. 이 검사는 DB에 쓰지 않았다.

40만 줄의 목적 파일에는 앞서 성공한 결과를 미리 두었다. 새 실행은 `analysis failed: IllegalStateException: analysis output exceeds 10 MiB`로 종료했고, 목적 파일의 이전 바이트는 같았으며 임시 파일은 남지 않았다. 남아 있는 파일을 새 입력의 성공 결과로 인정하면 안 된다.

단일 표본이고 분석 전체의 비용을 측정했으므로 이 수치로 속도나 메모리 개선율을 결론 내리지 않는다. 확인한 구현 효과는 발행 경로에서 전체 JSON 문자열·UTF-8 배열을 추가로 만들지 않고 직렬화 도중 바이트 상한을 적용한다는 것이다. 분석 결과 Map·입력 메타데이터·분석기 내부 자료구조의 메모리는 여전히 필요하다. 전체 힙이나 프로세스 메모리를 강제하는 기능도 아니다.

## 다음 검증과 확인한 원본

큰 결과를 끝까지 수용할 단일 파일 상한 확대와 분할 형식의 실제 소비자 변경 비용은 상위 #68에서 비교한다. DB 반영과 조회 화면의 정상·실패·부분 결과·다른 빌드·상한 표시는 브라우저 QA가 필요하다. 이번 변경에는 DB 쓰기, 화면 변경과 브라우저 QA가 없다. OS 자원 강제와 분산 실행 소유권은 [#37](https://github.com/DDINGJOO/JJAM-TONG/issues/37)의 경계다.

기존 [Gson 2.14.0 구현](https://github.com/google/gson/blob/gson-parent-2.14.0/gson/src/main/java/com/google/gson/Gson.java)의 Writer 출력 경로를 사용했다. 인코더의 버퍼·잘못된 문자 치환·닫기 동작은 [JDK 17 OutputStreamWriter 문서](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/io/OutputStreamWriter.html), 원자적 이동의 지원 조건과 기존 파일 처리는 [Files.move 문서](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/nio/file/Files.html#move(java.nio.file.Path,java.nio.file.Path,java.nio.file.CopyOption...))에서 확인했다. 로컬 파일 교체 검증을 전원 장애 내구성이나 분산 저장 보장으로 확대하지 않는다.
