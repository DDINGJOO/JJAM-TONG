# 버전 근거를 어디까지 보관하고 어떻게 조회할 것인가

상태: **공식 원문 확인·비교 조건 명세 / 보관 방식의 실제 실행·제품 채택 전 · 2026-11-12**.

[선행 실행 결과](HYBRID-RESULTS.md) · [공통 입력·예상 판정](evidence-query-cases.json) · [코드 분석·계측 비교 조건](CODE-ANALYSIS-COMPARISON.md) · [작업 이슈](https://github.com/DDINGJOO/JJAM-TONG/issues/38)

원본을 다시 확인해 현재 그래프를 복구해도, 확인 사이에 사라진 중간 버전은 남지 않을 수 있다. 앞선 실험에서도 세 갱신 방식 모두 중간 커밋을 놓쳤다. 이제 “어제 배포된 게시판 요청은 어떤 코드를 실행했는가?”에 답하려면 무엇을 보관해야 하는지 비교한다.

먼저 답할 질문을 고정한다. **과거 실행 경로, 그 요청의 상세 원문, 지금의 상태**는 서로 다른 질문이다. 한 질문에 답할 수 있다는 이유로 다른 질문까지 복원했다고 판단하지 않는다.

## 같은 입력에서 보관 범위만 바꾼다

이 문서에서 원본 연합 조회는 플랫폼이 여러 공급원의 근거를 조회 시점에 가져와 연결하는 방식이다. adapter는 공급원별 조회·변환을 담당하는 구성 요소다. 아래 세 대안은 같은 버전 식별·시간·권한 계약과 같은 원본을 사용한다. 특정 DB나 배포 구성의 비교는 별도다.

| 대안 | 플랫폼에 보관하는 본문 | 원본에서 가져올 내용 | 기대 이점과 부담 |
| --- | --- | --- | --- |
| 중앙 보관 `central` | 포함 범위의 코드 후보·선택된 요청 관계·배포 관계와 허용된 상세 원문 | 최신 상태 확인, 보존 범위 밖 정보 | 원본 장애 중 보관한 과거를 조회할 수 있다. 저장·민감정보·삭제·접근 통제 책임이 커진다. 전수 수집을 뜻하지 않는다. |
| 원본 연합 조회 `federated` | 관계 본문을 보관하지 않는다 | 질문에 필요한 버전별 본문 전부 | 중복 보관을 줄일 수 있다. 원본의 이력·가용성·위임 권한·호출 예산에 의존한다. |
| 최소 근거와 원본 조회 `minimum` | 같은 코드 후보·선택된 요청 관계·배포 관계. 상세 원문 제외 | 상세 원문, 최신 상태, 보존 범위 밖 정보 | 정해진 과거 경로 질문은 원본 없이 답할 수 있다. 그 밖의 질문은 원본에 의존하며 최소 범위를 바꾸면 비용·재현성도 바뀐다. |

관계 본문은 메서드 호출 후보·관측된 호출·배포와 자원 사이의 연결 데이터다. 상세 원문은 관계와 별도로 취급하는 원본의 추가 속성이며, 이번 합성 입력에서는 `detail-A`의 `fixture.operation` 같은 값이다. 실제 요청 인수나 응답 본문의 수집을 전제하지 않는다.

모든 대안은 수집 시점에 **관측한 근거의 목록(manifest)**을 남긴다. 목록에는 본문 대신 식별자·원본 참조·사건 시각·기록 시각·수집 범위·삭제 상태가 있다. 연합 조회도 이 목록을 보관하므로 저장량이 0인 대안은 아니다. 원본에서 나중에 발견한 근거를 플랫폼이 예전부터 알고 있었다고 표현하지 않기 위한 통제 조건이다.

세 대안의 정확한 보관 ID는 JSON의 `retention`에 고정한다. 본문 반환은 현재 권한 검사 후에만 허용한다. 원본 조회를 생략한 상태를 최신이라고 표현하거나, 실제로 보관하지 않은 본문을 목록에서 만들어내면 실패다.

## 커밋 하나로 실행 버전을 결정하지 않는다

같은 커밋도 의존 라이브러리·생성 코드·빌드 설정이 달라지면 다른 JAR 같은 산출물을 만들 수 있다. 공통 입력의 A·B는 이를 구분하기 위한 합성 빌드다. 저장소와 커밋은 같지만 빌드·산출물은 다르다. A2는 A의 산출물을 다른 포함 설정으로 재분석한 결과다. 이 JSON은 **실제 분석기나 실제 trace에서 추출한 데이터가 아니다.**

| 근거 | 구분할 정보 |
| --- | --- |
| 코드와 빌드 | 조회 범위, 저장소 식별, 커밋, 빌드, 산출물의 내용 식별자, 모듈 |
| 분석 | 분석 실행, 인덱스 내용 식별자, 분석기 버전, 스키마 버전, 설정 식별 |
| 실행과 배포 | 요청·관측 메서드, 실행 당시의 빌드·산출물, 배포 인스턴스·자원 참조 |
| 출처·시간 | 공급원 참조, 사건 시각 `event_at`, 플랫폼 기록 시각 `recorded_at`, 포함 범위·누락 정보 |

분석 결과는 빌드·산출물과 분석 조건까지 지정해 선택한다. 실행 기록에 없는 분석 실행 ID를 추측해서 붙이지 않는다. 같은 산출물의 분석 결과가 여러 개면 요청한 조건으로 고르거나 모호함을 반환한다. 이름·브랜치·최신 지도만으로 대체하지 않는다. JVM descriptor는 Java 비교 입력에서 메서드의 인수·반환형을 구분하는 표현이며, 모든 언어의 필수 식별 형식으로 정하지 않는다.

`event_before`는 사건 시각의 상한이고 `known_before`는 플랫폼이 알고 있던 시각의 상한이다. 두 조건을 모두 만족한 근거만 반환한다. 예를 들어 사건 시각 11, 기록 시각 30인 `late-A`는 `known_before=20` 조회에 들어가지 않는다. 이 숫자는 합성 입력에서 사건과 기록의 순서를 구분하는 값이다. 초 단위 시간이나 실제 운영 목표를 나타내지 않는다. 두 상한만으로 자산 상태의 연속적인 유효 구간을 증명하지 않는다.

## 권한 회수를 한 가지 실패로 합치지 않는다

| 조건 | 고정할 기대 행동 |
| --- | --- |
| 현재 플랫폼 조회 권한 회수 | 세 대안 모두 본문·관계·대상 식별자를 반환하지 않는다. 과거 권한으로 우회하지 않는다. |
| 현재 조회 정책을 확인할 수 없음 | `policy_unavailable`로 거부하고 본문을 반환하지 않는다. 원본 장애와 별개다. |
| 수집 연결 권한 회수 | 수집을 중단한다. 기존 보관 근거의 조회 가능 여부는 현재 보관·조회 정책으로 별도 판단한다. |
| 원본 위임 조회 권한 거부 | 원본 조회는 거부된다. 이미 보관한 과거 근거의 반환은 별도 정책이 명시적으로 허용한 경우만 가능하다. |
| 보관 금지·삭제 의무 발생 | 영향을 받는 본문·파생 관계·색인·캐시·복제본의 삭제 범위를 정한다. 중앙/최소 보관도 예외가 아니다. |

E06은 “수집은 중단됐지만 보관한 과거 조회는 현재 정책이 허용한다”는 입력이다. 모든 조직에서 허용된다는 뜻이 아니다. E08은 원본과 플랫폼 모두에 삭제가 적용된 입력이다. 실제 삭제 전파·정책 엔진·백업 처리는 아직 구현하지 않았다. 권한이 다른 근거를 잇는 간선도 조회 시 검사해야 하며, 허용된 노드 하나로 숨겨진 대상의 이름을 노출해서는 안 된다.

## 질문별 독립 예상 판정

예상 판정을 **oracle**이라고 부른다. 구현의 출력을 복사한 값이 아니라, 구현 전에 정한 기대 응답이다. JSON은 10개 합성 근거·20개 사례에 대해 세 대안의 **예상 응답 60개**를 고정한다. 실제 응답이나 실행 통과 수가 아니다.

| 사례 | 질문·입력 | 중앙 보관 | 연합 조회 | 최소 보관 |
| --- | --- | --- | --- | --- |
| E01 | 원본 정상, 과거 A 경로 | A 경로 | A 경로 | A 경로 |
| E02 | 원본 중단, 과거 A 경로 | 보관 경로 | 원본 중단 | 보관 경로 |
| E03 | 원본 중단, A 상세 원문 | 보관 원문 | 원본 중단 | 원문 미보관·원본 중단 |
| E04 | 원본에서만 A 이력 만료 | 보관 경로 | 만료 | 보관 경로 |
| E05 / E07 / E19 | 조회 권한 회수 / 정책 확인 불가 / 다른 범위 | 거부 | 거부 | 거부 |
| E06 | 수집 중단·원본 권한 거부, 보관 조회 허용 | 보관 경로·수집 중단 표시 | 원본 권한 거부 | 보관 경로·수집 중단 표시 |
| E08 | A 근거 삭제 의무 적용 | 삭제 상태 | 삭제 상태 | 삭제 상태 |
| E09 / E10 / E11 | B의 정확한 결합 / A 지도 없음 / artifact 미확인 | B만 결합 / 불일치 / 불일치 | 동일 | 동일 |
| E12 / E13 | 늦은 근거의 기록 전 / 후 | 당시 모름 / 단일 관계만 확인 | 동일 | 동일 |
| E14 | A2의 포함 설정이 다른 재분석 | 부분 그래프·제외 표시 | 동일 | 동일 |
| E15 | 관측하지 못한 중간 버전 | 이력 공백 | 이력 공백 | 이력 공백 |
| E16 | 원본 중단 중 현재 상태 | 현재 확인 불가 | 현재 확인 불가 | 현재 확인 불가 |
| E17 | 원본 정상, 상세 원문 | 보관 원문 | 위임 조회 | 위임 조회 |
| E18 | 응답 상한 1개 | 일부·잘림 표시 | 동일 | 동일 |
| E20 | 플랫폼·원본 모두 상세 원문 만료 | 만료 | 만료 | 만료 |

예상 응답은 상태·반환 근거 ID·이유를 포함한다. `available`은 **요청한 보존 범위 안의 질문에 필요한 근거가 있음**을 뜻한다. 모든 요청·메서드를 수집했다는 뜻이 아니다. `partial`은 단일 관계·제외 범위·응답 잘림을 구분하고, `unknown`·`not_known`·`expired`·`unavailable`·`version_mismatch`를 빈 정상 결과로 합치지 않는다. 권한 거부 시 내부 원본이나 숨겨진 근거 ID를 설명에 넣지 않는다.

기본 질문은 A의 `graph-A`, `request-A`, `deployment-A`를 요구한다. E09만 B로 바뀐다. 상태 변경은 플랫폼과 원본의 동일한 관측 기록에 적용한다. `absent_ids`는 애초에 해당 분석을 확보하지 못한 입력이고, `expired_ids`는 보존 후 만료된 입력이다. 사건·기록 시각과 현재 조회 정책을 먼저 적용하고, 정확한 버전 선택과 필요한 본문 확보를 확인한다. E18의 결과 순서는 그래프·요청·배포 순으로 고정한다.

정적 입력의 `relations`는 선언을 대상으로 한 호출 후보이며, 인터페이스가 선택할 수 있는 구현체는 별도의 `dispatch_candidates`에 둔다. 구현체 후보를 인터페이스 메서드가 실행 중 직접 호출한 관계로 표현하지 않는다. 실행 입력의 `relations`만 해당 요청에서 관측한 부모·자식 호출을 뜻한다. 세 목록 모두 합성으로 작성한 예상 입력이다.

## 실제 실행에서 무엇을 측정할 것인가

세 보관 정책은 같은 원본 adapter·조회 계약·직렬화·입력 순서·동일한 장애 일정으로 실행한다. 원본의 버전 조회가 가능하다는 전제를 검증할 별도 사전 점검을 둔다. 원본이 현재 상태만 제공하면 연합 조회의 과거 응답을 임의로 만들어내지 않는다.

| 측정 | 기록할 값과 실패 판정 |
| --- | --- |
| 근거 정확성 | 잘못된 빌드·설정의 결합, 현재 조회 권한을 벗어난 근거 노출, 미관측을 미실행으로 단정한 건수. 1건이라도 있으면 안전성 실패 |
| 질문 충족 | 상태·근거 ID·이유를 예상값과 비교. 설계대로 원본 장애를 반환한 경우와 과거 재현 목표 미달을 각각 기록 |
| 보관 부담 | 본문·목록·색인·캐시·삭제 표시의 실제 바이트 수. 압축·보존 기간·관계 수를 함께 기록 |
| 원본 부담 | 질문당 호출·페이지·전송 바이트·조건부 조회·권한 검사·오류·재시도 |
| 조회 비용 | 초기 조회(cold)와 준비된 상태의 조회(warm)를 구분. 동일 질문별 경과 시간·최대 메모리·반환 바이트·잘림을 기록. 로컬 시간으로 외부 운영 성능을 일반화하지 않음 |
| 복구·삭제 | 원본 복구 후 응답 변화, 삭제 이후 모든 조회 경로·캐시에서 대상이 사라지는지, 처리 지연과 미확인 복제본 |

다음 로컬 실험의 **예산 제안**은 질문당 총 5초·최대 원본 호출 5회·반환 100개/1MiB, 전체 60초·출력 20MiB다. 제한 도달은 `partial` 또는 `budget_exceeded`로 기록한다. 세 방식에 같은 상한을 적용하고 임계값은 실행 전에 고정한다. 이를 구현·강제하거나 성능을 측정한 상태는 아니다. 현재 JSON의 E18은 개수 상한만 다루며 시간·바이트·페이지 상한의 추가 입력도 실제 실행 전에 마련한다.

초기·준비 상태를 비교할 때는 캐시·연결 등 무엇을 초기화하거나 유지할지 실행 전에 정한다.

## 이번 판단과 다음 검증

**지금 하나의 보관 방식을 채택할 근거는 부족하다.** 과거 경로를 원본 없이 재현해야 한다면 그 질문에 필요한 관계를 보관하는 대안이 유리할 수 있다. 반대로 원본이 버전 이력과 권한을 충분히 제공하고 중복 보관·삭제 부담이 크다면 연합 조회가 유리할 수 있다. 상세 원문까지 필요한지에 따라 중앙/최소 보관의 비용 차이도 달라진다. 이 판단은 위 보존 경계에서 도출한 설계 예상이며 실측 우위가 아니다.

이번 검증은 JSON 구조·참조·예상값의 일관성과 문서/기존 명세 대응을 확인한다. 실제 대안 구현·권한 엔진·저장 엔진·보존/삭제 보장·메서드 분석은 실행하지 않았다. 기존 회귀 테스트의 통과도 이 새 대안의 동작 증거로 집계하지 않는다. [후속 실행 T24 #43](https://github.com/DDINGJOO/JJAM-TONG/issues/43)에서 실제 출력·입력 hash·환경·실패·미지원 항목을 남긴다.

이 계약은 관측성·코드·에이전트/SRE·MSA·Kubernetes·인프라·CMDB·SIEM 전체 구현 범위에 적용할 비교 출발점이다. 코드 호출과 자산 소유권·보안 사건은 서로 다른 의미와 보존 정책을 가진다. 이번 코드 입력을 이들 영역의 수집·권한 지원 완료로 취급하지 않는다.
