# 버전별 코드 그래프를 크게 만들면 DB 선택이 달라지는가

작은 입력에서 조회가 성공했다는 사실만으로는 DB를 정하기 어렵다. JJAM-TONG은 특정 빌드의 메서드 관계를 보관하고, 요청 분석이나 변경 영향 조회에 그 버전을 다시 사용할 수 있어야 한다. 그래서 PostgreSQL과 Neo4j에 같은 합성 그래프를 넣고 메서드 수·호출 밀도·탐색 깊이·동시 조회를 늘렸다.

이 문서는 실행 결과를 기록하는 비교 실험이며 제품 DB 채택 결정은 아니다. [앞선 네 엔진 비교](STORAGE-ENGINE-COMPARISON.md)와 [원본 책임별 16개 구성 비교](STORAGE-TOPOLOGY-COMPARISON.md)를 대체하지 않는다. 기존 #43·#44의 남은 인수 조건도 유지한다.

## 무엇을 같은 조건으로 맞췄는가

빌드당 메서드 1만·10만 개와 기본 정적 호출 2개·6개를 조합했다. 각 입력에 이전·새 빌드를 함께 저장하고, 다른 저장소·분석 설정·동일 커밋/빌드의 다른 artifact(빌드 산출물)도 작은 그래프로 추가했다. 모든 데이터는 합성이며 실제 회사 코드나 운영 요청을 사용하지 않았다.

분석 범위를 식별하는 `scope`에는 저장소·커밋·빌드·산출물·분석기·스키마·설정·모듈 목록 식별자와 합성 입력의 크기·밀도·생성기 버전이 들어간다. 서로 다른 입력의 분석 ID도 다르다. 다른 범위의 메서드 사이에는 간선을 만들지 않는다. 누락된 범위의 조회는 거부하고, 모르는 범위는 최신 빌드로 대체하지 않는다.

| 조건 | 실행 설정 |
| --- | --- |
| 서버 | PostgreSQL 17.11, Neo4j 5.26.33 Community |
| 자원 상한 | 각각 CPU 1개·메모리 1 GiB, 한 번에 서버 하나만 실행 |
| 그래프 | 256개 메서드의 순환 구간, 구간 사이 연결, 최대 128개 목적지로 분기하는 진입점 |
| 관계 | `STATIC`과 `OBSERVED`를 분리. 관측 관계도 계측 결과가 아닌 합성 입력 |
| 질문 | 순방향 1·3·6·12단계, 역방향 영향 6단계, 관측 관계 6단계 |
| 정확성 | 독립 메모리 BFS 결과와 시작점을 제외한 고유 메서드 ID 전체를 대조 |
| 반복 | 질문별 워밍업 2회 뒤 20회. 작은 별도 범위는 1회씩 검사 |
| 동시 조회 | 두 조회 방식 각각 클라이언트 1·4·8개, 클라이언트마다 여섯 질문을 1회씩 실행 |
| 시간 예산 | 서버 쿼리 10초, 애플리케이션 탐색 전체 10초 확인. HTTP 제한은 45초 |

BFS는 가까운 메서드부터 차례로 찾는 탐색이다. 이 실험은 모든 호출 경로를 나열하지 않고 도달할 수 있는 메서드의 집합을 구한다. 경로마다 호출 순서나 횟수를 반환하는 기능의 성능과는 구분한다.

## 조회 구현도 선택의 일부다

`native`는 DB가 여러 단계의 관계를 직접 찾는 방식이다. PostgreSQL은 재귀 CTE(이전 단계 결과를 다시 사용하는 SQL)에서 `(깊이, 메서드)`의 중복을 제거한다. Neo4j는 고유 목적지 조회를 사용하고, 실행 계획에서 pruning(중복 목적지로 가는 탐색을 줄이는 처리) 연산자가 선택되는지 확인한다. 1단계 조회는 다단계 pruning 검사에서 제외한다.

`frontier`는 두 DB 모두 한 단계씩 조회하고 애플리케이션이 이미 방문한 메서드를 제거하는 방식이다. 왕복 횟수·직렬화·애플리케이션 탐색 비용을 포함한다. 두 DB의 내부 알고리즘을 완전히 같게 만든 실험은 아니므로 각 질의 구현의 결과로 해석한다.

PostgreSQL은 Psycopg 연결, Neo4j는 요청마다 여닫는 HTTP 연결을 쓴다. 짧은 조회에서는 프로토콜 차이가 크게 작용할 수 있다. 서버 내부 연산만의 성능 순위로 읽으면 안 된다. 이 HTTP 연결은 실험용 구현이며 제품 클라이언트 선택은 별도로 검토한다.

## 실행 결과

[원시 결과](graph-scale-run.json)의 실행 ID는 `d26a48c07e3d4702882d0d5a1fdec7a5`이며, 측정 소스는 커밋 `25dcc2bfdb6b842a13ed4ee85952cf5639844ce2`로 고정했다. 2026-11-13 15:15:31~15:19:57 KST에 8개 조합을 실행했다. 검증기는 규모별 입력·소스/커밋·필수 질문·동시 조회 분포를 대조하고 `verified`를 반환했다.

순차 측정 3,888건과 동시 조회 1,248건이 모두 예상 ID 목록과 일치했다. 별도 워밍업 384건도 일치했으며, 최종 실행의 시간 예산 초과는 0건이었다. 입력 크기를 늘렸을 때의 결과이며 기업 환경의 수용량 목표를 통과했다는 뜻은 아니다.

### DB 안에서 찾을지, 여러 번 조회할지도 중요하다

빌드당 10만 메서드·기본 호출 6개에서 이전 빌드를 조회한 결과다. 각 칸은 **p50 / p95 밀리초**다. `native`는 정상 범위에서 DB 왕복 1회이며, `frontier`는 시작점 확인 뒤 필요한 단계만큼 왕복한다.

| 질문 | 도달 메서드 | PostgreSQL native | Neo4j native | PostgreSQL frontier | Neo4j frontier |
| --- | ---: | ---: | ---: | ---: | ---: |
| 진입점 1단계 | 134 | 1.05 / 1.58 | 1.94 / 5.95 | 1.09 / 2.02 | 3.71 / 4.78 |
| 내부 3단계 | 67 | 0.81 / 1.17 | 0.99 / 1.94 | 2.11 / 3.19 | 7.37 / 8.38 |
| 진입점 6단계 | 25,356 | 149.25 / 180.34 | 179.48 / 249.22 | 124.31 / 129.52 | 434.49 / 516.19 |
| 역방향 영향 6단계 | 368 | 2.68 / 3.03 | 3.58 / 4.86 | 5.63 / 6.59 | 11.63 / 13.55 |
| 내부 12단계 | 641 | 9.69 / 10.95 | 5.51 / 6.36 | 10.70 / 13.90 | 21.63 / 27.80 |
| 관측 관계 6단계 | 1 | 0.58 / 0.93 | 1.72 / 2.58 | 1.56 / 2.86 | 4.17 / 5.19 |

큰 입력의 내부 12단계에서는 Neo4j의 직접 조회가 빨랐다. 같은 DB도 단계별 HTTP 조회로 바꾸면 비용이 커졌다. PostgreSQL은 진입점 6단계에서 애플리케이션이 방문한 메서드를 제거하는 방식이 직접 재귀 질의보다 빨랐다. DB 이름과 조회 구현을 함께 선택해야 한다는 근거다.

관측 관계 질문의 결과는 1개뿐이다. 이 행은 관계 유형을 구분하는 정확성과 짧은 조회의 비용을 보여 주며, 복잡한 실제 분산 트레이스나 비동기 이벤트 연결의 성능을 입증하지 않는다.

### 동시 조회에서는 다른 결과도 나왔다

가장 큰 입력에서 이전 빌드의 여섯 질문을 섞었다. 표의 p95는 **성공한 혼합 질문 전체**의 값이며, 각 질문의 p95와 다르다. 동시 시험은 별도 연결을 사용하며 연결 준비 시간은 제외한다. 연결별 SQL 준비 상태와 두 DB의 질의 캐시 상태까지 같게 만들지는 않았다.

| 방식 | 클라이언트 | DB별 표본 | PostgreSQL p95(ms) | Neo4j p95(ms) | PostgreSQL 종료 시도/초 | Neo4j 종료 시도/초 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| native | 1 | 6 | 217.33 | 152.56 | 23.45 | 35.72 |
| native | 4 | 24 | 826.24 | 542.49 | 26.82 | 40.19 |
| native | 8 | 48 | 1,800.64 | 1,055.21 | 24.22 | 43.10 |
| frontier | 1 | 6 | 539.87 | 270.89 | 10.23 | 19.21 |
| frontier | 4 | 24 | 1,996.93 | 1,252.94 | 11.62 | 17.01 |
| frontier | 8 | 48 | 2,850.66 | 2,373.56 | 15.07 | 16.78 |

이 실행의 가장 큰 입력에서는 두 방식 모두 Neo4j의 혼합 질문 p95가 낮았다. 그러나 표본은 조합당 6~48건이며 오래 유지한 부하가 아니다. 종료 시도 수를 실행 시간으로 나눈 값은 이 짧은 시험의 처리율이다. 제품의 최대 QPS(초당 조회 수)나 안정적인 수용량으로 사용하지 않는다.

### 적재는 전체 빌드와 개수 대조까지 쟀다

적재 시간은 두 빌드와 작은 세 범위를 저장한 뒤 노드·관계 개수를 확인하는 시간이다. 그래프 생성·정답 계산·뒤이은 통계 갱신 시간은 제외한다. PostgreSQL은 일괄 적재 명령인 `COPY`와 외래 키 검사를 사용한다. Neo4j는 행 목록을 풀어 노드·관계를 만드는 `UNWIND`로 1,000행씩 적재한다. 순수 디스크 쓰기 성능 비교는 아니다.

| 빌드당 메서드 | 기본 호출 | 전체 메서드 | 전체 관계 | PostgreSQL(초) | Neo4j(초) |
| --- | --- | ---: | ---: | ---: | ---: |
| 1만 | 2개 | 20,192 | 42,085 | 0.67 | 7.39 |
| 1만 | 6개 | 20,192 | 122,085 | 1.67 | 3.03 |
| 10만 | 2개 | 200,192 | 413,375 | 9.23 | 7.33 |
| 10만 | 6개 | 200,192 | 1,213,375 | 41.21 | 16.12 |

Docker의 적재·조회 구간 자원 표본과 이미지 식별자도 원시 결과에 있다. 주기적으로 관측한 값이므로 순간 최대 자원 사용량이나 전체 비용을 확정하지 않는다.

### 실패한 첫 실행도 남긴다

첫 실행 `cb238ffab95141109047ec6ae87246d4`는 Neo4j의 클라이언트 4개·단계별 조회에서 `TransactionTimedOutClientConfiguration`을 받았다. 초기 측정기는 다른 시간 초과 코드만 허용했으므로 이 응답을 실행 실패로 기록했다. [실패 문맥과 소스 식별자](graph-scale-failure.json)에 해당 질문·분석 범위·진행 단계와 이후 미실행 조합을 남겼다. 첫 실행의 시간 표본은 최종 비교에 합치지 않았다.

두 시간 초과 응답을 정확한 코드로 분류하고, 구문 오류·HTTP 전송 시간 초과를 예산 초과로 바꾸지 않는 회귀 검사를 추가했다. 코드 이름으로 제한 설정의 기원을 단정하지 않는다. [Neo4j 5.26.0의 공식 상태 코드 정의](https://github.com/neo4j/neo4j/blob/5.26.0/community/common/src/main/java/org/neo4j/kernel/api/exceptions/Status.java)에서도 두 코드를 별도로 정의한다. 수정한 측정 소스를 커밋한 뒤 전체 조합을 새 실행으로 다시 측정했다.

## 이 결과로 어디까지 결정할 수 있는가

**첫 구현의 메타데이터 원본은 PostgreSQL을 우선 검토하고, 그래프 조회는 PostgreSQL과 Neo4j의 교체 가능한 경계로 둔다는 제안**을 유지한다. 제품 의존성을 채택한 결정은 아니다. 빌드당 10만 메서드·기본 호출 6개 조건에서 진입점 6단계를 순차 조회했을 때는 PostgreSQL을 검토할 근거가 있었고, 내부 메서드 12단계의 직접 조회와 여섯 질문을 섞은 짧은 동시 조회에서는 Neo4j를 계속 검토할 근거도 생겼다. 그래프 DB가 무조건 필요하거나 불필요하다는 결론은 내리지 않는다.

Neo4j를 별도 조회 모델로 추가하려면 실제 코드에서 추출한 그래프와 목표 지연을 사용해 이점이 유지되는지, 동기화·재구축·저장 비용을 추가로 부담할 가치가 있는지 확인해야 한다. Neo4j가 분석 그래프의 원본을 직접 맡는 대안도 배제하지 않는다. 관측 데이터의 ClickHouse, 검색·보안의 Elasticsearch 등 다른 영역은 이번 두 엔진 실험으로 채택 여부를 결정하지 않는다.

이번 입력은 기업의 큰 코드베이스를 가정한 합성 그래프다. 실제 메서드 수와 관계 분포를 추출한 운영 데이터는 아니다. 공유 호스트에서 PostgreSQL을 먼저 실행했고, OS·DB 캐시를 통제하지 않았다. 스모크 시험과 실패한 첫 실행에서 쓴 전용 볼륨도 재사용했다. 최종 비교는 하나의 완결된 실행이며 반복 실행 간 변동 폭을 평가하지 않았다. 짧은 동시 조회는 지속 수용량이나 오토스케일 검증이 아니다.

진입점의 12단계 탐색, 실제 라이브러리·프레임워크 경계의 대규모 연결, 한 빌드가 아닌 많은 빌드의 장기 보관, 실제 코드에서 추출한 관계 분포와 지속 도착률 부하는 앞으로 검증한다. 대상 Java 프로젝트의 정적 분석과 요청별 실행 흐름을 이 저장소의 합성 그래프 시험으로 대신하지 않는다.

볼륨을 재사용하므로 `allocated_*_after_volume_reuse`는 이전 실행의 파일 할당과 트랜잭션 로그도 포함한다. 이 값은 실행 환경 확인용이며 현재 그래프의 순수 저장량·압축 효율을 비교하는 근거로 사용하지 않는다. 부분 적재 상태의 발행, 증분 갱신·조회 중 쓰기·보존 기간별 삭제·실제 권한·고가용성·백업 복구와 수평 확장은 앞으로 검증한다.

## 재현과 공식 근거

[실험 구현과 명령](../../experiments/graph_scale_lab/README.md)을 따른다. 측정 전에 소스를 커밋하고, 실행 ID·커밋·소스 해시·이미지 ID/다이제스트를 기록한다. 검증기는 필수 규모와 질문·동시 조회의 질문별 횟수·입력·소스 일치를 검사한다. 시간 예산 초과는 성공 표본과 별도로 센다. 기타 오류가 발생하면 질문·분석 범위·조회 방식·오류 코드와 진행 단계를 남기고 실행을 실패로 처리한다. 실패한 실행을 성공 실행에 합치지 않는다.

- [PostgreSQL 17 재귀 질의](https://www.postgresql.org/docs/17/queries-with.html): `UNION`의 중복 제거와 재귀 평가 방식.
- [PostgreSQL 17 COPY](https://www.postgresql.org/docs/17/sql-copy.html): 클라이언트에서 행을 일괄 적재하는 방법.
- [PostgreSQL 17 statement_timeout](https://www.postgresql.org/docs/17/runtime-config-client.html): 연결별 쿼리 시간 제한.
- [Neo4j 5 실행 연산자](https://neo4j.com/docs/cypher-manual/5/planning-and-tuning/operators/): 가변 길이 확장과 pruning 연산자.
- [Neo4j 5 실행 계획](https://neo4j.com/docs/cypher-manual/5/planning-and-tuning/execution-plans/): 실행하지 않고 계획을 확인하는 `EXPLAIN`.
- [Neo4j 5 트랜잭션 제한](https://neo4j.com/docs/operations-manual/5/database-internals/transaction-management/): 서버 취소와 감시 주기.
- [Neo4j 5 HTTP 오류 처리](https://neo4j.com/docs/http-api/5/error-handling/): HTTP 성공 상태에서도 응답의 오류 배열을 확인해야 하는 이유.

공식 문서는 2026-11-13에 확인했으며, 실제 실행 버전과 이미지 식별자는 원시 결과에 보관한다.

## 검토와 정리

초기 독립 검토에서 분석 ID 충돌, 동시 조회 질문 누락을 허용하던 검증, 이전 볼륨의 할당량을 저장 효율로 오해할 가능성을 지적했다. 크기·밀도·생성기 버전을 ID에 포함하고, 질문별 횟수를 강제하는 회귀 검사를 추가했으며, 저장량 필드와 해석 범위를 명시했다. 두 조회 방식의 동시 시험과 구조화한 실패 문맥도 보완했다. 재검에서 기존 지적은 0건이었고 아키텍처 상태는 `CLEAR`였다.

시간 초과 코드 수정에 대한 별도 코드 검토에서도 남은 지적은 0건이었다. 새 단위 시험 19개와 기존 회귀 36개, 총 55개가 통과했다. Python 구문·컴파일과 Compose 설정도 검사했다. LSP(언어 서버 기반 정적 진단) 도구가 없어 코드 검토의 최종 상태는 `COMMENT`로 남기며 해당 진단의 통과를 주장하지 않는다. 실험 컨테이너·네트워크를 제거했고 기존 컨테이너 11개는 실행 상태를 유지했다.

별도 AI 국문 편집 검토에서는 Neo4j의 장점이 10만 메서드 조건 전체로 읽힐 수 있다는 두 문장을 지적했다. 본문과 위키에 기본 호출 6개·정확한 질문·짧은 동시 시험이라는 조건을 명시했다. 재검은 `APPROVE`·남은 지적 0건이었다. 최종 실행의 표본 수·표 수치·측정 커밋과 소스 해시·실패 실행 분리에 대한 독립 증거 검토도 `VERIFIED`였다.
