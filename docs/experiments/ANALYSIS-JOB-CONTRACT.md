# 분석 작업의 완료·자원 계약과 발행 비교 결과

2026-11-14 로컬 실험에서 **같은 합성 근거 6만 건을 단일 파일과 불변 조각·완료 명세로 발행하고 내용 해시를 대조했다.** 파일당 10 MiB 제한의 단일 파일은 새 결과를 발행하지 않았고, 분할 방식은 23개 조각과 완료 명세로 발행했다. 파일당 상한을 32 MiB로 바꾼 단일 파일도 성공했다.

작업은 [#64](https://github.com/DDINGJOO/JJAM-TONG/issues/64)다. [계약](../requirements/ANALYSIS-JOB.md), [ADR 0010](../decisions/0010-analysis-job-publication.md), [구현·재현](../../experiments/analysis_job_lab/README.md), [구조화한 실측값](analysis-job-results.json)을 연결한다. 기존 Java 분석기·DB·CI·화면의 전환이나 실제 기업 코드 수용량 검증은 아니다.

## 같은 입력과 명시적인 예산

macOS arm64·Python 3.9.6에서 각 구성을 별도 프로세스로 한 번 실행했다. 합성 선언·관계 레코드를 단계별 3만 건씩 생성했다. 선언 위치·descriptor(매개변수·반환 타입 식별)·정적 후보·합성 관측·미해결 종류를 보존하고, 발행 전 원본 스트림과 읽어 낸 결과의 순서·전체 내용 해시를 대조했다. 실제 Java를 분석하거나 실제 요청을 관측한 데이터는 아니다.

전체 발행 예산은 세 구성 모두 32 MiB다. 단일 파일의 머리말·레코드·완료 꼬리말, 분할 방식의 모든 조각과 완료 명세를 각각 포함한다. 기본 파일 상한은 10 MiB이며 세 번째 구성에서만 32 MiB로 바꾼다. 분할 방식의 조각은 1 MiB, 레코드는 128 KiB, 명세는 1 MiB, 조각 수는 4,096개로 제한했다. 실제 각 파일도 해당 파일 상한을 지켜야 한다. 실험 수치이며 제품 정책을 채택한 것은 아니다.

| 구성 | 파일 상한 | 발행 시간 | 검증·읽기 시간 | 발행 바이트 | 결과 |
| --- | ---: | ---: | ---: | ---: | --- |
| 스트리밍 단일 파일 | 10 MiB | 0.708초 | 실행하지 않음 | 새 발행 없음 | 출력 제한 |
| 불변 조각·완료 명세 | 10 MiB | 1.455초 | 1.758초 | 23,816,996 | 완료, 23개 조각·명세 3,266바이트 |
| 상한을 바꾼 스트리밍 단일 파일 | 32 MiB | 1.688초 | 1.585초 | 25,970,005 | 완료 |

두 성공 구성의 레코드 60,000건과 전체 내용 해시는 원본과 같았다. 저장 형식은 다르다. 단일 파일은 각 레코드에 단계·행 종류를 반복하고 분할 방식은 조각 머리말에 단계를 기록하므로 포장 비용과 실제 바이트 수가 다르다. 같은 의미와 전체 제한에서의 발행 계약 비교이며 동일한 바이트 배열의 저장 성능 비교는 아니다.

분할 방식은 Python 추적 할당 최대 2,702,225바이트·프로세스 최대 RSS 19,939,328바이트, 상한을 바꾼 단일 파일은 각각 342,306바이트·17,170,432바이트였다. Python의 `tracemalloc`은 발행·검증·읽기 동안 추적한 Python 할당이며 네이티브·분석기 전체 메모리가 아니다. RSS는 각 프로세스 시작 이후의 최대 상주 메모리다. OS 캐시·다른 작업을 통제한 반복 비교는 아니므로 속도·메모리 순위나 지속 수용량으로 일반화하지 않는다.

## 실패·중복·완료의 실제 검사

단위·파일·하위 프로세스 검사 24개가 통과했다. 같은 모양의 raw 명세로는 작업을 완료할 수 없고 모든 조각을 검증한 완료 증거 타입을 요구한다. 이 타입은 신뢰하는 프로세스 안의 오용 방지이며 인증 수단이 아니다.

- 조직·저장소·revision·빌드·모듈·분석기·스키마와 각 입력 해시가 바뀌면 입력 키가 바뀐다. 입력 순서만 바뀌면 같은 키를 유지하고 미확보·해당 없음은 구분한다.
- 필수 단계가 끝나도 결과 검증 전에는 부분 완료다. 취소·실패·자원 초과의 기록과 이유를 유지하고 새 시도로 재시도한다.
- 일부 조각 발행 뒤 중단하거나 완료 직전 취소·입력 변경을 검출하면 새 완료 명세가 없다. 같은 입력·시도의 재실행은 동일 결과를 발행할 수 있다.
- 레코드·조각·파일·전체·명세·조각 수의 상한을 초과하면 완료를 발행하지 않는다. 조각은 전체 예산에 맞더라도 명세까지 포함해 넘으면 거부한다.
- 누락·손상·다른 입력의 조각을 유효한 해시로 다시 포장한 경우·중복 참조·다른 시도·잘린 단일 파일·완료 뒤 추가 데이터도 거부한다.
- 로컬 스레드 네 개의 동일 발행은 완료 명세 하나만 새로 만든다. 같은 경로의 다른 내용은 충돌로 처리한다. 다중 호스트 소유권 시험은 아니다.
- 실제 하위 프로세스의 시간 초과를 완료 파일 생성 전·후에 주입했다. 파일 관측과 미검증 상태를 기록하고 나머지 구성을 계속 실행했다. 파일이 보였다는 이유로 성공 해시를 기록하지 않았다.

첫 독립 검토에서 raw 명세를 통한 완료, 명세가 빠진 전체 바이트 집계, 시간 초과 기록 누락을 지적했다. 이를 수정하고 위 검사를 추가한 뒤 규모 비교를 다시 실행했다. 지적·수정·독립 재검 결과는 #64와 PR에 기록한다. 모든 BDD 파일은 실행기 없는 Draft이며 실제 검사와 구분한다.

## 적용 판단과 다음 검증

파일당 10 MiB 상한을 유지하며 더 큰 논리 결과를 다루는 후속 후보는 조각·완료 명세 방식이다. 상한을 바꿀 수 있다면 스트리밍 단일 파일도 대안이다. 압축은 실행하지 않았으며 압축 전·후·복원 크기와 CPU·호환 비용을 별도로 검증해야 한다.

기존 Java의 401,023줄 입력을 새 방식으로 성공시킨 결과는 아직 없다. 기존 분석기·수집기·색인·DB·화면의 상한과 전환은 [#68](https://github.com/DDINGJOO/JJAM-TONG/issues/68)에서 실제 생산자·소비자·브라우저 QA로 확인한다. 큰 인코더 문자열·원본 레코드·분석기 메모리, OS 자원 강제·분산 소유권·실패 조각 정리·전원 장애는 이 발행 실험으로 해결한 범위가 아니다. [#37](https://github.com/DDINGJOO/JJAM-TONG/issues/37)의 실행 경계와 연결한다.
