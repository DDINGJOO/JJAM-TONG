# PostgreSQL을 전제하지 않는 저장 구성 비교

이전 비교는 네 DB의 조회를 실행했지만, 여러 DB를 연결하는 복구 파이프라인에서는 PostgreSQL만 원본을 맡았다. 그 결과로 PostgreSQL 중심 구성이 최선이라고 판단할 수는 없다. 이번에는 **원본을 맡는 DB도 변수로 바꾸어** 네 단독 구성과 방향이 있는 두 DB 조합 12개를 실행한다. Elasticsearch는 아래에서 ES로 줄여 쓴다. 제품 DB는 아직 선택하지 않는다.

## 먼저 원본과 조회 데이터의 책임을 정한다

이번 실험에서 원본 DB는 수락한 근거 묶음과 발행 목록을 보관한다. 조회용 DB를 지워도 이 원본만으로 복원할 수 있어야 한다. 두 역할을 같은 DB에 두면 단독 구성이고, 다른 DB에 두면 두 DB 구성이다. 따라서 `ES → PostgreSQL`과 `PostgreSQL → ES`는 다른 구성이다.

발행 목록인 **매니페스트**에는 데이터 조각의 해시·행 수·근거 식별 정보가 들어 있다. 조각만 저장하고 목록을 발행하지 않은 작업은 완료된 작업으로 조회하지 않는다. 같은 목록 ID를 다른 내용으로 덮어쓰려는 작업은 거부한다. ID는 가져온 근거 묶음의 개정을 뜻하며, 이벤트 추가나 삭제 표시는 새 개정으로 발행한다.

| 책임 | 보관할 것 | 장애·삭제 시 기준 |
| --- | --- | --- |
| 원본 DB | 변경하지 않는 데이터 조각, 매니페스트, 저장소·커밋·빌드·artifact(빌드 산출물)·모듈·분석 설정의 식별 정보 | 이 DB에 보관된 입력을 복구 기준으로 삼는다. 읽을 수 없으면 현재 결과의 완전성을 확인하지 못한 상태로 반환한다. |
| 조회용 DB | 코드·인프라 관계, 실제 관측 관계, 검색·집계용 행 | 원본과 다르면 `partial`, DB가 중단되면 `unavailable`이다. 지우고 원본으로 재구축할 수 있다. |
| 실험 실행기 | 고정 질문, 독립 예상값, 실패 주입과 판정 | 원본을 대신 저장하는 별도 PostgreSQL·Kafka·객체 저장소는 두지 않는다. |

서로 다른 원본 책임을 한 DB에 억지로 모을 필요도 없다. 예를 들어 분석 버전·권한 설정, 코드 관계, 보안 사건, 대량 관측 이력은 서로 다른 저장소가 각자의 원본을 맡을 수 있다. 이번 16개 구성은 **한 근거 묶음의 원본과 조회 모델**을 비교하며, 여러 도메인이 각각 원본을 갖는 전체 플랫폼 구성을 구현한 결과는 아니다.

원본 조각은 같은 규칙으로 직렬화한 JSON 문자열로 보관한다. PostgreSQL은 별도 테이블, Neo4j는 별도 라벨의 노드, ES는 별도 색인, ClickHouse는 별도 MergeTree 테이블을 사용한다. 조회 모델은 기존 SQL·그래프·문서·컬럼 모델을 재사용한다. 이 공통 원본 형식은 복구 책임을 비교하기 위한 조건이며, 각 엔진에서 가장 효율적인 원본 스키마를 찾아낸 결과는 아니다.

## 비교 대상과 판정

네 DB 모두 원본 후보로 둔다. PostgreSQL 전용 outbox나 잠금으로 다른 원본 DB의 부족한 기능을 보완하지 않는다. Outbox는 변경과 전달할 기록을 함께 보관하는 방식이며, [이전 실험](STORAGE-ENGINE-COMPARISON.md)에서 별도로 검증했다. 이번에는 변경하지 않는 근거 묶음을 다시 읽어 조회 모델을 복원한다.

기능 판정과 **동시 발행 능력**은 분리한다. 기능 시험은 발행자 하나로 실행한다. 동시 발행 시험은 연결 두 개를 동시에 출발시켜 같은 ID·같은 내용의 재시도와 같은 ID·다른 내용의 충돌을 확인한다.

| 원본 후보 | 이번 어댑터의 동시 발행 수단 | 판단 범위 |
| --- | --- | --- |
| PostgreSQL | 고유 키와 `INSERT … ON CONFLICT DO NOTHING`, 보관한 내용의 일치 검사 | 동일 ID를 두 내용으로 덮어쓰지 않는다. 여러 행을 함께 갱신하는 제품 업무 트랜잭션과는 별도다. |
| Neo4j | 고유 제약과 `MERGE … ON CREATE`, 보관한 내용의 일치 검사 | 고유 제약을 함께 사용한다. `MERGE`만으로 동시 중복 방지를 주장하지 않는다. |
| Elasticsearch | 결정적인 문서 ID와 `_create`, 409 응답 뒤 내용의 일치 검사 | 문서 하나의 생성 충돌을 처리한다. 여러 문서의 일괄 저장이 하나의 원자적 작업이 되는 것은 아니다. |
| ClickHouse | 일반 MergeTree에 추가한 뒤 같은 ID의 내용을 확인 | 현재 어댑터에는 원자적인 생성 충돌 방지가 없다. 단일 발행자 기능 시험과 여러 발행자의 안전성을 구분하고, 상충한 두 내용의 동시 보관을 반례로 남긴다. |

근거: [PostgreSQL 17 INSERT](https://www.postgresql.org/docs/17/sql-insert.html), [Neo4j 5 MERGE](https://neo4j.com/docs/cypher-manual/5/clauses/merge/), [ES 문서 생성 API](https://www.elastic.co/docs/api/doc/elasticsearch/operation/operation-create). ClickHouse는 특정 조건에서 원자적 삽입과 실험적 트랜잭션을 제공한다. 여기서 확인하는 제한은 **현재 일반 MergeTree 어댑터의 영구적인 ID 고유성·조건부 생성**이다. ClickHouse 전체가 트랜잭션을 제공하지 않는다는 뜻이 아니다. [ClickHouse 트랜잭션 설명](https://clickhouse.com/docs/concepts/features/operations/insert/transactions), [재시도 중복 제거의 범위](https://clickhouse.com/docs/concepts/features/operations/insert/deduplicating-inserts-on-retries).

## 같은 시나리오를 어떻게 대입하는가

| 조건 | 실행 | 기대 결과 |
| --- | --- | --- |
| 수집 중 프로세스가 끊겼다 | 조각을 저장하고 매니페스트를 발행하지 않는다. | 해당 개정은 `missing`이다. |
| 원본 발행과 조회 반영 사이에 간격이 있다 | 빈 모델, 노드만 있는 모델, 전체 모델을 순서대로 조회한다. | `partial → partial → ready`로 바뀐다. |
| 재시도에 다른 내용이 들어왔다 | 같은 목록 ID로 같은 내용을 재전송한 뒤 다른 내용을 전송한다. | 같은 내용은 허용하고 다른 내용은 거부한다. |
| 다른 버전이 섞였다 | 이벤트 하나의 artifact를 바꾸어 조회 모델에 넣는다. | 해당 결과를 `ready`로 반환하지 않는다. |
| 소비자가 처리 결과를 남기기 전에 종료됐다 | 반영 직후 실제 자식 프로세스를 코드 73으로 종료하고 다시 실행한다. | 중복·유실 없이 원본과 일치한다. 별도 ACK(처리 완료 확인) 저장소의 원자성을 검증하는 시험은 아니다. |
| 조회 DB가 중단됐다 | 두 DB 구성에서 조회 DB를 중단하고 새 원본 개정을 발행한다. | 조회는 `unavailable`, 원본 발행은 성공한다. 재시작 후 원본에서 따라잡는다. |
| 원본 DB가 중단됐다 | 원본 DB를 중단하고 기존 개정을 조회한다. | 캐시된 `ready`로 대체하지 않고 `unavailable`을 반환한다. |
| 조회 데이터가 사라졌다 | 재시작 후 조회 모델을 지우고 원본 DB의 조각만 읽어 재구축한다. | 원래 개정의 근거와 일치한다. |
| 삭제 뒤 오래된 변경이 도착했다 | 이벤트에 삭제 표시를 적용하고 이전 행을 재생한다. | 조회에서 되살아나지 않는다. |

추가로 기존 엔진 실험의 코드 호출·역방향 영향·인프라 연결·검색·집계·테넌트/빌드/설정 분리 질문을 같은 작은 입력에 적용한다. 정적 호출 후보와 실제 관측 관계도 구분한다.

## 어떤 조건에서 각 후보를 더 검증할 것인가

| 구성 계열 | 우리 플랫폼에서 대입할 요구 | 다음 비교에서 결정할 것 |
| --- | --- | --- |
| PostgreSQL 단독 | 버전 메타데이터·관계·이벤트를 한 저장소로 관리한다. | 데이터 증가·관계 깊이·검색 복잡도·보존 비용이 목표를 만족하는가. |
| Neo4j 단독 | 코드·서비스·인프라 관계를 중심으로 근거를 조회한다. | 이벤트 검색·대량 집계·원본 보관 비용과 배포판별 운영 조건을 감당할 수 있는가. |
| ES 단독 | 로그·보안 사건·검색을 중심으로 버전 근거와 관계를 함께 보관한다. | 관계 탐색 왕복·교차 문서 갱신·버전 목록·보존/복구 비용이 허용 범위인가. |
| ClickHouse 단독 | 대량 실행 이력과 시간별 분석을 중심으로 구성한다. | 여러 발행자의 목록 충돌을 어떤 계약으로 제어할지, 재조회·관계 탐색·삭제 비용이 맞는가. |
| 각 원본 + 다른 조회 DB | 원본 보관과 주요 조회 방식의 비용을 분리한다. 12개 방향을 모두 후보로 둔다. | 추가 DB의 이익이 복제 지연·장애·삭제·복구·운영 부담보다 큰가. |
| 여러 도메인별 원본 또는 3개 이상 DB | 카탈로그·코드 관계·관측 이력·SIEM 사건이 서로 다른 원본 책임을 갖는다. | 도메인 간 버전·권한·삭제·복구 경계는 어떻게 합칠 것인가. 이번 실행 대상 밖이다. |

ES를 원본으로 쓰면서 권한·설정만 별도 DB에 둘 수도 있고, ClickHouse에 관측 이력을 보관하면서 코드 관계를 그래프 DB에 둘 수도 있다. 그때는 어느 DB 이름이 앞에 오는지가 아니라 **각 데이터의 수락·변경·복구 권한이 어디에 있는지**를 먼저 정한다. 이 선택지를 PostgreSQL 기반 조합으로 한정하지 않는다.

## 실측의 한계와 앞으로 검증할 항목

기본 입력은 323행이다. 노드 134개, 관계 157개, 합성 로그 20개, 관측 span 12개를 포함한다. 테넌트와 빌드는 각각 두 개이며, 별도 분석 설정의 작은 그래프도 들어 있다. 두 DB 구성은 조회 DB 중단 중 이벤트 한 행을 추가하고, 모든 구성에서 마지막으로 이벤트 한 행에 삭제 표시를 적용한다. 기본 입력 해시와 이 변경 절차를 코드·실행 기록에 함께 고정한다.

이번 검증은 고정된 작은 합성 데이터, 단일 발행자·단일 소비자, DB별 단일 노드를 쓴다. 고유성 시험도 작성자 두 개의 한정된 동시 실행이다. 단독 구성은 원본과 조회 모델이 같은 장애 영역에 있으며 두 DB 구성도 같은 장비 위에 있다. 실제 서버는 정상 중단·같은 볼륨 재시작을 수행한다. 강제 장애·디스크 손상·별도 장비 복원·복제본 승격을 입증하지 않는다.

조회 판정마다 원본과 관련 범위의 조회 데이터를 모두 읽어 비교한다. 시간 표본은 이 검증 경로의 비용이다. 이전 엔진 비교의 작은/중간 입력 수치와 합쳐 엔진 순위를 만들지 않는다. CPU 상한·메모리 상한·접속 방식도 기존 어댑터의 조건을 따른다.

중간 실행에서는 ES를 재시작하는 동안 ClickHouse의 유휴 HTTP 연결이 닫혀 후속 재구축이 실패했다. 이 실행은 최종 집계에서 제외했다. 수정 후 HTTP 어댑터는 요청마다 연결을 닫아 오래된 연결을 재사용하지 않는다. 자동 재시도는 추가하지 않았으며, 성공·실패 때의 연결 정리와 재시도 부재를 회귀 시험으로 확인한다. 최종 시간 표본에는 이 연결 비용도 포함된다. PostgreSQL은 기존 Psycopg 연결을 사용한다.

가져온 근거 묶음의 개정과 제품의 분석 식별 규약은 별도다. 기존 fixture의 키는 저장소·모듈·artifact 전체를 포함하지 않으므로 여러 저장소의 충돌 검증은 남아 있다. 읽기 모델에서 artifact를 바꾼 반례는 이번에 실행하지만, 동시 변경 중 분산 스냅샷·프로덕션 권한 검증으로 확대하지 않는다.

삭제 시험은 이벤트 한 행을 조회에서 숨긴 뒤 오래된 행이 복원되지 않는지 확인한다. 원본에 보관한 과거 조각, 백업, SIEM 보존 자료까지 지우는 전체 삭제는 앞으로 검증한다. 기업 권한·감사·테넌트 격리, 지속 수용량·자동 확장, 긴 이력과 복잡한 관계, 여러 소비자의 인계, 라이선스·운영 비용을 같은 목표로 비교한 뒤 채택 ADR을 작성한다. #43·#44의 열린 상태와 기존 인수 조건은 유지한다.
