# ADR 0008 정확 입력 분석 결과의 로컬 재사용

- 상태: 한정된 로컬 도구에 적용. 메서드 단위 증분 분석은 미결이다.
- 날짜: 2026-11-14
- 작업: [#61](https://github.com/DDINGJOO/JJAM-TONG/issues/61), 상위 [#44](https://github.com/DDINGJOO/JJAM-TONG/issues/44)
- 선행: [ADR 0004](0004-method-evidence-comparison.md), [ADR 0007](0007-local-boot-method-evidence.md)

## 문제와 결정

커밋이 바뀌었다는 이유만으로 동일한 입력을 다시 분석할 필요는 없다. 그러나 파일의 수정 목록만으로 재사용 범위를 정하면 구현체 추가·상속 변경·시작점 변경이 다른 파일의 호출 후보를 바꾸는 경우를 놓칠 수 있다.

첫 구현은 **분석 입력 전체가 같은 단위의 완전한 결과**를 재사용한다. 단위는 현재 분석기에 전달하는 소스 집합과 원본 JAR 전체다. Gradle 모듈이나 패키지가 그 자체로 안전한 분석 경계라는 가정은 두지 않는다. Spring Boot의 중첩 라이브러리 변경은 원본 JAR 해시 변경으로 재분석을 유발한다. 일반 JAR 모드에는 임의의 외부 앱 클래스패스를 전달하는 계약이 아직 없다.

재사용 키는 조직·저장소·모듈, 전체 소스·JAR, 분석 범위·시작점·입력 형식, 분석기·의존 도구·JDK를 포함한다. 현재 빌드 명세와 바이트를 전후 대조하고, 재사용 결과에는 현재 빌드·커밋·명세 해시를 붙인다. 메타데이터를 계산 입력으로 사용하도록 분석기를 바꾸면 이 분리 계약도 재검토한다. 과거 빌드의 이름을 그대로 새 빌드로 내보내지 않는다.

## 대안 비교

| 방법 | 장점 | 부담과 선택 |
| --- | --- | --- |
| 빌드마다 전체 재분석 | 비교 기준이 단순하고 영향 계산 오류가 적다 | 변경이 없어도 비용을 반복한다. 정확성 대조 기준으로 유지한다 |
| 입력이 같은 전체 단위 재사용 | 기존 분석기의 의미를 유지하며 중복 실행을 줄인다 | 작은 변경도 큰 단위 전체를 다시 분석한다. 첫 구현으로 선택한다 |
| 의존 관계와 ABI를 이용한 증분 분석 | 변경 영향이 작은 경우 분석량을 줄일 수 있다 | ABI는 외부에 드러난 타입·메서드 구조다. 구현체·계층·생성 코드·반사 호출의 영향과 삭제 전파를 검증해야 한다. 후속 설계 대상이다 |
| 컴파일러·언어 서버 색인 재사용 | 빌드가 해석한 심볼·클래스패스를 활용할 수 있다 | 언어·도구별 계약과 라이선스·정확성 대조가 필요하다. 언어 서버 진단만으로 호출 그래프를 대신하지 않는다 |

WALA의 클래스 계층 분석(CHA)은 입력 계층에서 가능한 호출 대상을 계산한다. 패키지 제외는 출력 필터이며 계층 분석의 자원 사용을 독립된 작은 문제로 나누는 수단이 아니다. 거대한 공통 모듈의 내부 변경 비용은 이번 재사용만으로 해결되지 않는다.

## 발행과 실패

캐시에는 입력 키·완전한 분석 본문·내용 해시를 불변 파일로 보관한다. 성공 상태와 두 분석기의 필수 컬렉션을 확인하고, 손상·부분 결과는 거부한다. 키별 파일 잠금으로 같은 입력의 분석을 직렬화하고, 기다린 요청은 완료된 캐시를 검증해 읽는다. 입력을 발행 전에 다시 확인하며 출력은 새 파일에 배타적으로 생성한다.

도구는 기존 JVM·시간·출력 상한을 유지한다. 이번 로컬 파일 재사용은 DB의 버전 명세나 GitHub 수집 정책을 바꾸지 않는다. 모든 결과는 정적 후보이며 실제 실행 증거로 바뀌지 않는다. [실측 결과](../experiments/ANALYSIS-REUSE-RESULTS.md)와 [BDD-UPD-005~010](../../specs/features/03-graph-refresh.feature)이 검증 경계를 설명한다.

## 다음 설계의 통과 조건

모듈을 나눌 때는 외부 타입·전체 클래스패스와 의존 모듈의 해시를 보존해야 한다. 역방향 의존 색인, 구현체 추가·삭제와 ABI 변화, 순환 묶음의 영향, 프레임워크·생성 입력 변경을 대조하고 같은 빌드의 전체 분석과 관계 집합이 같아야 한다. 큰 단위를 무작정 쪼개서 성공한 결과를 원래 전체 그래프의 성공으로 표시하지 않는다.

분석 작업 큐·조직별 자원 상한·취소·재시도·분석 단위별 불변 저장과 빌드 명세의 원자적 발행은 후속 설계다. 화면에서는 빌드별 `대기 / 분석 중 / 재사용 / 실패 / 부분 완료`와 누락 범위를 보여주는 흐름을 검토한다. 이번 변경에는 작업 큐나 화면 구현이 없다.

## 공식 비교 근거

[SonarQube Server 2025.5의 증분 분석](https://docs.sonarsource.com/sonarqube-server/2025.5/analyzing-source-code/incremental-analysis/introduction)은 언어별 최적화와 캐시 조건을 구분한다. [Java 분석 문서](https://docs.sonarsource.com/sonarqube-server/analyzing-source-code/languages/java)의 변경되지 않은 파일 최적화를 전체 호출 그래프의 증분 알고리즘으로 해석하지 않는다.

고정해서 확인한 [WALA CHA 소스](https://github.com/wala/WALA/blob/ab3bd3b2b9291e047b203cddd248cbbcfcff6f1e/core/src/main/java/com/ibm/wala/ipa/callgraph/cha/CHACallGraph.java)에서는 계층에 람다를 추가한 뒤 호출 대상 캐시를 지우고 다시 계산한다. 이 구현의 특정 SHA와 실행에 쓰는 배포 바이너리 1.9.0의 태그 동일성을 이번 조사로 별도 증명하지는 않았다. 정확한 버전의 동작은 실제 입력의 전체 분석 대조로 함께 검증한다.
