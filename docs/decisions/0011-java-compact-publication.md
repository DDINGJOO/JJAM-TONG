# ADR 0011: Java v1의 공백을 줄이고 단계별 상한을 보존한다

- 상태: 실제 결과 비교에 따른 다음 로컬 구현안. 생산자·소비자 전환과 DB·브라우저 검증 후 적용 범위를 확인한다.
- 날짜: 2026-11-14
- 작업: [#72](https://github.com/DDINGJOO/JJAM-TONG/issues/72), 상위 [#68](https://github.com/DDINGJOO/JJAM-TONG/issues/68)
- 선행: [ADR 0010](0010-analysis-job-publication.md), [실제 Java 비교](../experiments/JAVA-PUBLICATION-COMPARISON.md)

## 문제와 판단 기준

401,023줄 합성 Java 입력의 결과는 들여쓰기를 포함하면 13,372,075바이트다. 격리된 32 MiB 생산자에서는 분석 결과 발행에 성공하지만, 기존 색인 저장은 14,526,183바이트로 10 MiB를 넘어 실패한다. 생산자의 상한 확대만으로는 전체 경로가 연결되지 않는다.

같은 결과의 공백을 줄이면 분석 파일 7,647,618바이트, 색인 8,433,407바이트가 된다. 기존 DB 입력 검증도 이 결과를 수락한다. 이 표본에 필요한 변경과 자원 경계를 근거로 다음 단계를 정한다. 전체 제품의 전송 규격과 임의 크기 입력의 해법을 동시에 확정하지 않는다.

## 대안 비교

| 대안 | 장점 | 이번 선택에서의 비용 |
| --- | --- | --- |
| 단일 파일 상한 확대 | 하나의 완료 파일과 기존 JSON 구조를 유지한다 | 생산자 외의 여러 상한도 함께 변경해야 한다. 수신 메모리와 전체 결과 재처리 비용이 늘 수 있다 |
| 기존 v1의 공백 제거 | 같은 JSON 구조와 기존 판독기를 유지하면서 이번 실제 결과를 기존 파일 예산에 넣을 수 있다 | 출력 바이트가 바뀌므로 분석기 출처 버전·파일 해시·회귀 근거를 갱신해야 한다. 더 큰 입력에는 충분하지 않다 |
| 조각·완료 명세 도입 | 파일당 제한을 유지하며 더 큰 논리 결과를 표현하고 조각별 검증을 할 수 있다 | 명세·부분 수신·정리·완료 전 공개 방지와 소비자 전환이 필요하다. 전체 색인을 재구성하는 현 소비자의 상한은 그대로 남는다 |

공백 제거는 압축이 아니다. 압축·해제 도구를 추가하지 않으며 JSON 구조와 기존 판독기를 유지한다. 단순 반복 생성 코드의 크기 감소율을 모든 입력에 일반화하지 않는다.

## 선택과 적용 조건

다음 로컬 구현은 기존 `jjamtong.methods.v1`과 메서드 색인의 공백을 줄이는 방식으로 진행한다. Java 생산자는 분석기 출처 버전을 `0.2.3`으로 올린다. 기존 분석 정렬에 쓰는 `Model.JSON`은 그대로 두고 발행 전용 직렬화 설정을 사용한다. 출력 형태 변경 때문에 정적 관계의 정렬이나 의미까지 달라지는 일을 막는다.

분석 파일·색인 파일·CI 색인 포장의 10 MiB 상한을 유지한다. 생산자는 직렬화 도중 UTF-8 바이트와 끝 개행을 검사하고, 임시 파일을 닫은 뒤 원자적으로 교체한다. 기존 DB `prepare`의 기본 공백을 포함한 직렬화 예산도 바꾸지 않는다. 따라서 공백을 줄인 파일이 10 MiB 이하여도 DB 입력의 별도 예산에서 거부될 수 있다. 모든 경계를 통과해야 새 결과를 발행한다.

기존 들여쓰기 JSON도 계속 읽어야 한다. 파일 바이트 해시는 새 바이트로 다시 계산하며 논리 색인 해시는 기존 정규화 규칙을 유지한다. 생산자 버전·설정·입력·빌드가 바뀐 결과를 이전 분석으로 섞지 않는다. CI 모듈·출처 허용 범위를 확대하지 않는다.

## 검증과 보류한 경계

전환의 완료 조건은 JDK 17/21 회귀, 공백 전후의 논리 결과·소스 위치·해시 대조, 실제 40만 줄 이전·새 빌드의 발행·재조회, 실패 시 이전 파일 보존, 다른 빌드·해시의 거부와 DB·브라우저 QA다. 파일 크기 개선만으로 완료 처리하지 않는다.

분할 방식은 탈락한 제품 목표가 아니다. 실제 결과나 단일 메타데이터 레코드가 기존 상한을 넘거나 부분 재처리가 필요해지면, 색인·DB 소비자를 포함한 전환을 별도 하위 작업으로 진행한다. 분석 중 전체 Map, 소비자의 전체 결과 보관, 분산 소유권·OS 자원 강제와 지속 수용량은 이번 선택으로 해결되지 않는다. 특히 소스 줄 수는 결과 크기나 메서드·관계 밀도를 대신하는 지원 한도가 아니다.
