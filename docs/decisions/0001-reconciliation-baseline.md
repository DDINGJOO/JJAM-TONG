# ADR 0001 — 관계 갱신의 검증 기본안

날짜: 2026-11-12. 상태: **실험 기본안 채택 / 운영용 기술·주기·보존 정책 미결**.

연결: [T20 #36](https://github.com/DDINGJOO/JJAM-TONG/issues/36), [설계·반례](../experiments/HYBRID-RECONCILIATION.md), [결과](../experiments/HYBRID-RESULTS.md).

## 문제와 확인한 방향

사람이 코드·서비스·인프라 관계를 계속 수정하면 최신 상태와 분석 당시 버전을 보존하기 어렵다. 알림만 의존하면 누락이 남고, 주기적 현재 snapshot만 읽으면 빠른 반영과 중간 이력이 부족하다. 사용자는 폴링과 이벤트 비교 후 원본 재확인과 변경 알림을 결합하는 안의 검증 진행에 동의했다.

## 결정

코드·카탈로그·인프라의 **현재 관계 갱신**은 원본 재확인 작업을 공통 경계로 두고 주기 확인과 변경 알림을 연결하는 안을 우선 검증한다. 변경 알림은 확인을 앞당기는 힌트다. 원본 버전·수집 범위·분석기/스키마/설정을 확인한 뒤 완전한 결과만 게시한다. unchanged 확인과 관계 재생성을 분리한다.

정상 수신 ACK는 durable receipt 뒤에 반환한다. 중복·동시 요청을 병합하되 처리 중 새 요청을 남기고, 실패·부분 수집·권한 회수 때 마지막 성공 결과를 새 성공으로 위장하지 않는다. 버전별 결과와 관측 이력을 보존하고 commit을 build/artifact 식별로 대체하지 않는다.

이번 구현은 완전한 tree에서 포함 경로의 파일·blob 인덱스를 만들고 이전 결과와 추가·삭제·내용 변경 경로를 비교한다. 같은 버전이면 tree 조회와 인덱스 생성을 생략한다. 메서드 그래프의 증분 재분석과 변경 범위의 언어별 전파는 별도 검증이다.

trace·보안·감사 사건은 발생 이력의 수집·보존이 별도로 필요하다. Kubernetes는 list/watch와 필요한 relist, 다른 공급원은 제공 API·변경 알림·권한·연결 제약에 맞는 adapter를 검증한다. 단일 공통 폴링 주기나 모든 이벤트의 전역 순서를 강제하지 않는다.

## 대안과 영향

| 대안 | 유리한 조건 | 부담·한계 |
| --- | --- | --- |
| 폴링 중심 | 알림 미지원·내부망·느슨한 지연 예산 | 불필요한 확인, 주기 전 지연, snapshot 사이 이력 공백 |
| 알림 중심 | 빠른 변경 감지, 높은 조회 비용 | 알림 누락·재전송·초기 상태 확인 필요 |
| 알림과 원본 재확인 | 빠른 감지와 확인 가능한 현재 상태 복구 | 두 트리거·중복 병합·재시도·호출 예산 관리; 중간 이력은 추가 원장 필요 |

모노레포의 논리 모듈과 프로세스 경계는 별도 결정이다. 첫 비교는 같은 계약의 in-process와 one-shot worker이며, 후자의 시작 비용과 단일 머신 공유 저장소 조건을 드러낸다. 실험 Python/SQLite는 제품 채택이 아니다. 새 패키지·broker·클러스터를 추가하지 않았다. 시스템 도구를 사용하고 소스를 번들하지 않으며 프로젝트/제품 라이선스는 별도로 결정한다.

## 검증과 재검토

정상·누락·역순·중복·원본 중단·부분 tree·프로세스 종료·동시 worker·lease 만료·연결 회수·상한·설정 변경을 [실험실](../../experiments/reconciliation_lab/README.md)에서 확인한다. 실제/주입/미실행 경계는 결과표가 기준이다. 앞선 합성 실험의 이력 손실 결과도 유지한다.

실제 공급원별 갱신 지연·호출 제한·복구 범위·운영 부담을 측정한 뒤 운영 기본값을 결정한다. 알림 미지원, 원본 이력 만료, 호출 제한, 대규모 목록 비용 때문에 목표를 만족하지 못하면 adapter·보존·스케줄링 방식을 재검토한다. 전체 플랫폼 설계·기술이 확정되었다고 해석하지 않는다.
