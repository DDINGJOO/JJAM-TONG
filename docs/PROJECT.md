# 요구사항 명세: 에이전트·SRE의 근거 기반

에이전트와 SRE가 서비스의 지연·실패·운영 및 보안 문제를 빠르고 정확하게 분석하도록, 메서드 관계·실제 실행·배포·인프라·자산·보안 이벤트를 같은 대상과 시점의 근거로 조회하게 만든다. 관계를 수동으로 갱신하거나 분석마다 원본을 다시 모으는 부담을 줄인다.

## 현재 상태

새 퍼블릭 저장소에서 **BDD 시나리오와 이슈로 요구사항부터 작성하는 단계**다. 실행 가능한 제품과 지원 조합은 아직 없다. 이전 실습의 코드·테스트 결과를 이 저장소의 구현 또는 검증 완료로 집계하지 않는다.

[VISION](VISION.md)의 관측성·코드·에이전트·SRE·MSA·Kubernetes·인프라·CMDB·SIEM은 모두 구현 범위다. 코드 관측성의 작은 PoC를 검증 출발점으로 제안하며, 전체 범위를 축소하거나 구현 순서를 확정한 것은 아니다. 지금은 플랫폼의 기대 결과·경계·실패 조건을 명세한다.

진행 순서는 **요구사항·BDD 초안 → 함께 토론·검증 기준 정리 → 오픈소스·인프라 PoC → 아키텍처 ADR → 구현**이다. [요구사항·BDD](requirements/README.md)가 명세와 시나리오의 시작점이다.

## 사용자와 첫 시나리오 후보

첫 소비자는 Java 서비스의 문제를 조사하는 에이전트와 SRE다. 첫 실험으로 “배포 이후 왜 느려졌는가?”에 답할 근거를 조회하는 시나리오를 제안한다. 이는 원인을 자동 확정하는 기능의 약속이 아니다.

1. 빌드한 코드의 메서드와 호출 가능 관계를 분석한다.
2. 요청을 실행해 실제 호출 순서·부모 관계·시간·오류를 관측한다.
3. trace·실행 메서드·일치하는 빌드·소스 근거를 구조화된 읽기 결과로 연결한다.
4. 메서드 추가·삭제·이름 변경 후 자동 분석 결과가 바뀌는지 확인한다.
5. 이전·새 배포를 구분하고 출처·수집 시점·신선도·수집 범위·불확실성을 조회한다.

두 앱 버전과 하나의 느린 요청으로 시작하는 작은 통합 실험을 후속 PoC로 제안한다. 먼저 BDD의 전제·행동·기대 결과와 반례를 함께 검토한다. 조회 형식·파이프라인·스택은 [설계 토론](DISCUSSIONS.md)의 미결 대안이며, 아직 승인된 구현 설계는 없다.

## 명세할 범위와 결정할 경계

| 포함할 결과 | 구현 전 결정·검증할 사항 |
| --- | --- |
| 메서드 식별과 정적 후보 관계 | 분석 입력, 진입점, classpath, overload·인터페이스 처리 |
| 런타임 메서드 관측 | 앱 패키지 범위, private/self-call, 재귀·비동기·프록시의 지원 수준 |
| 자동 갱신과 버전 결합 | CI 이벤트, 실제 빌드 revision, snapshot 보존·배포 식별 |
| 에이전트·SRE 근거 조회 | 버전·출처·시점·신선도·수집 범위·불확실성, 읽기 범위·응답 상한 |
| 사람의 탐색 | 같은 근거 조회 계약을 사용하는 관계·요청 표현 |
| MSA·Kubernetes·인프라 관계 | 분산 context, 서비스·배포·워크로드·호스트 식별, 시점별 관계와 수집 범위 |
| CMDB 자산·소유권·변경 이력 | 공급원별 식별, 유효 시간, 동기화·충돌·소유권과 조회 권한 |
| SIEM 보안 근거 | 이벤트 수집·연결·분석의 행동, 출처·시간·민감정보·권한과 대응 경계 |
| 재사용과 품질 | 소비자 설정, 계측 비용·상한, 오류 격리, 지원 조합 |
| 이식성 | 플랫폼 설치와 관측 대상의 환경, 언어별 기능 수준, CI·도구 교체, 데이터 이동과 호환성 |

코드 분석의 첫 검증 fixture로 Java와 JDK 21을 제안한다. 이는 플랫폼 전체를 Java 전용으로 확정하거나 다른 언어의 동등한 관측 수준을 보장하는 결정이 아니다. 지원 언어·런타임별 정적·실행 분석 수준을 따로 정하며, 특정 분석기·agent·Spring 조합의 호환성을 확인한 것으로 표현하지 않는다. 새 의존성은 소유자의 명시적 선택 뒤 채택한다.

## 기대 결과와 검증 기준 후보

- overload와 모듈을 구분하는 메서드 식별 계약이 정적·실행 양쪽에서 일치한다.
- 분석에 저장소·커밋·빌드·분석기·스키마·설정 식별자가 남아 결과를 재현한다.
- 동일 메서드 이름이 있어도 다른 빌드의 결과를 묵시적으로 합치지 않는다.
- 코드 추가·삭제·이름 변경이 분석 재실행에 반영되며 실패한 분석을 최신 성공 결과로 표시하지 않는다.
- 에이전트가 trace·메서드·일치하는 빌드·소스를 읽기 조회로 얻고 원본 근거를 추적한다.
- 응답은 관측 사실·정적 후보·가설을 구분하고 출처·수집 시점·신선도·수집 범위·불확실성을 포함한다.
- 근거 누락·샘플링·버전 불일치·오래된 결과를 정상·완전 수집이나 확정 원인으로 표현하지 않는다.
- 계측이 원래 업무 결과·예외·비동기 동작을 바꾸지 않고 수집 자원이 제한된다.
- 합성 데이터로 설치·분석·실행·탐색·업그레이드 과정을 재현한다.
- 서비스·배포·인프라·자산·소유자·보안 이벤트를 출처·유효 시간·권한에 맞춰 연결하고 누락·충돌을 설명한다.
- 제안한 지원 환경에서 CI·수집 도구를 교체해도 공통 근거의 의미를 보존하고, 이식할 수 없는 정보와 설정·성능 차이를 드러낸다.

각 결과를 BDD 시나리오와 요구사항 이슈에 연결해 구체적인 판정 조건과 반례를 검토한다. 현재 시나리오는 명세 초안이며 실행 테스트나 기능 지원의 증거가 아니다. 실제 실험 결과는 후속 단계에서 별도 기록한다.

| E02 자동 갱신·에이전트 근거 요구사항 | 변경 반영·freshness와 기계 조회·출처·수집 범위·불확실성 명세 |

현재 구조는 4개 에픽·8개 스토리·16개 태스크이며 모두 명세·토론·검증 계획을 위한 작업이다. 실제 부모·자식 관계와 선행 조건은 [ROADMAP](../ROADMAP.md)에 연결된 GitHub 이슈에서 관리한다. milestone은 명세 목표 구간이며 출시 버전이나 확정 날짜를 뜻하지 않는다.

## 진행·완료 규칙

열린 실행 이슈에는 `status:backlog`, `status:ready`, `status:in-progress`, `status:in-review`, `status:blocked` 중 하나를 둔다. 전환할 때 이전 상태 라벨을 제거하며, 닫힌 완료 이슈에는 열린 상태 라벨을 남기지 않는다.

개인 진행 leaf 태스크는 동시에 1개다. 명세 태스크는 시나리오·반례·미결 질문·검증 계획의 검토 근거를 확인한 뒤 닫는다. 명세 완료를 기능 구현 완료로 표현하지 않는다. 스토리와 에픽도 요구사항 검토·출구 조건을 확인해 별도로 닫는다.

아키텍처·설계·파이프라인은 대안과 판별 실험을 놓고 함께 토론한다. 제안·미결 선택·승인된 결정을 구분하고, 기술 선택과 인프라 도입 결정은 ADR로 기록한다. 조사 결과에 따라 백로그도 조정한다. 계획 작성 자체를 구현 완료로 집계하지 않는다.

GitHub Issues의 실제 계층·milestone·상태 라벨이 상태의 기준이다. GitHub Projects v2 보드는 현재 인증 범위에서 생성하지 않았으며, 보드가 추가되어도 기존 이슈를 연결한다.

작업·검증 규칙은 [CONTRIBUTING](../CONTRIBUTING.md)에 있다. 블로그 작성·발행, 실제 고객 데이터 수집, 즉시 운영 배포는 현재 명세 작업의 범위에 포함하지 않는다.
