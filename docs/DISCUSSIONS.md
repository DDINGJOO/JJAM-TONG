# 설계 토론: 에이전트·SRE의 근거 조회

상태: **OPEN**. 현재는 [요구사항·BDD](requirements/README.md)의 기대 결과·반례·미결 질문을 먼저 작성하고 토론한다. 아래 대안·그림·실험은 이후 설계의 토론 제안이며 승인된 아키텍처·스택·파이프라인은 없다. 요구사항 초안, PoC, 토론 자료와 채택한 ADR을 구분한다.

코드 관측성·에이전트 근거 조회·SRE·MSA·Kubernetes·인프라·CMDB·SIEM은 모두 구현 대상이다. 전체 범위를 유지하면서 의존성에 따른 구현 순서와 각 영역의 지원 수준을 토론한다.

## 먼저 맞출 분석 질문

- “배포 이후 왜 느려졌는가?”를 조사할 때 어떤 trace·메서드·빌드·소스 근거가 필요한가?
- 실행 중인 버전의 영향 범위를 어디까지 확인했고, 어디부터 정적 후보나 미확인인가?
- 이 근거는 언제 수집됐고 얼마나 최신이며, 샘플링·제외·유실로 무엇이 빠졌는가?

첫 질문의 조회 결과로 느린 trace, 실제 호출 메서드, 일치하는 빌드·소스, 비교 시간 범위와 조건을 제안한다. 사실과 가설을 나누며, 배포 뒤 발생했다는 이유로 배포를 원인으로 확정하지 않는다.

## 근거 계약 후보

각 근거는 식별자·버전·출처·원본 참조·대상 시간 범위·수집 시점·조회 기준 시점·freshness·coverage·불확실성을 설명한다. 미수집·오래됨·버전 불일치도 조회 결과의 일부다. 신선도 계산, 필수 필드, 보존·권한·조회 상한은 아직 결정하지 않았다.

## D01. 근거를 한곳에 모을 것인가, 원본을 연결해 읽을 것인가

상태: **OPEN**.

| 대안 | 장점 후보 | 부담·한계 |
| --- | --- | --- |
| 중앙의 버전별 근거 저장·조회 | 반복 질의와 시점 재현을 한 계약으로 관리 | 복제·정합성·수집 지연·보존 비용을 운영 |
| 원본 도구의 연합 조회 | 원본과 기존 권한을 활용하고 중복 보관을 줄임 | 도구 장애·응답 지연·시점 차이와 API 변경에 영향 |
| 최소 관계만 보관하고 원본을 참조 | 결합 키를 유지하면서 큰 원본은 재사용 | 두 경로의 freshness·권한·원본 만료를 함께 처리 |

판별 실험 제안: 같은 분석 질문을 반복 조회하면서 응답 시간·재현성·누락 설명을 비교한다. 원본 하나가 지연·중단되거나 과거 자료가 만료되는 조건도 포함한다.

## D06. 이식성의 책임과 지원 범위를 어떻게 나눌 것인가

상태: **OPEN**. 이식성은 전체 영역의 공통 품질 요구다. 플랫폼이 설치되는 환경과 관측 대상이 실행되는 환경은 별도 지원 표로 다룬다. 언어·런타임별 메서드 분석의 표현력도 서로 다를 수 있다.

| 결정할 경계 | 대안·토론할 부담 | 판별 실험 제안 |
| --- | --- | --- |
| 플랫폼 설치 환경 | 로컬·서버·클러스터 설치 범위와 필수 외부 서비스; 배포 단위·권한·운영 비용 | 같은 합성 근거를 두 설치 구성에서 조회하고 설치·업그레이드·제거 절차와 비용 비교 |
| 관측 대상 환경 | 지원 대상인 AWS EKS·ECS·일반 Kubernetes와 온프레미스 자원 매핑; 환경별 수집 수준·권한·지원 버전 | 같은 앱 빌드의 코드·실행 근거를 비교하고 ECS에 Pod나 미확인 호스트를 생성하지 않는지 확인 |
| 언어·런타임 | 언어별 분석기·계측기의 지원 선언과 공통 근거·언어별 상세 계약; 구현·호환성 유지 비용 | 지원·부분 지원·미지원 조합에서 같은 질문의 결과와 누락 설명 비교 |
| CI·자동 갱신 | 공통 분석 실행 계약에 CI별 연결을 두는 안과 CI 종속 실행; 인증·입력·revision 차이 | 같은 빌드 입력·도구·설정으로 로컬과 두 CI 입력을 비교; 의미상 결과와 실행 출처 구분 |
| 관측·CMDB·SIEM 공급원 | 공통 근거에 connector를 연결하는 안과 공급원 기능 직접 노출; 정규화로 잃는 정보·운영 부담 | connector 교체에서 원본 ID·출처·유효 시간·권한·누락 설명 보존 확인 |
| 서비스 영향과 데이터 이동 | 도입·비활성화·제거 시 수정량, 장애 격리; export/import·스키마 변환·권한 이관 | 수집 연결 중단·복구, 제거 후 업무 재현; 호환·비호환 합성 자료의 이동·복구 비교 |

후보 구조로 **공통 근거 계약 + 언어·환경·도구별 adapter**를 논의한다. 공통 계약만으로 각 언어의 정적 호출 해석이나 비동기 관측 수준이 같아지는 것은 아니다. 공급원에서 변환할 수 없는 정보는 지원 한계로 남기고, 권한 변환이 불확실한 근거의 접근을 확대하지 않는 행동을 검토한다.

관측 대상의 범위는 AWS EKS·ECS와 일반 Kubernetes, 카탈로그의 자원 매핑 범위는 온프레미스·AWS로 정했다. 플랫폼 설치 대상·지원 버전·언어·CI·공급원, 앱 수정량과 자원 예산, 스키마 호환 기간·데이터 이동 범위는 아직 미결이다. 현재 실행 지원이나 특정 adapter 구조 채택이 완료된 상태는 아니다. [이식성 BDD 초안](requirements/README.md#공통-품질-요구-이식성)을 기준으로 지원 수준과 실험 조건을 함께 정한다.

## D07. 카탈로그와 실제 자원의 매핑을 어떻게 유지할 것인가

상태: **OPEN**. 카탈로그 기반으로 온프레미스·AWS 자원을 매핑하고 AWS EKS·ECS와 일반 Kubernetes를 지원한다는 사용자 요구를 구체화한다. 카탈로그의 논리 서비스와 환경별 배포·실제 자원, 수집한 관계와 선언한 관계를 구분한다. 카탈로그 제품·저장 형식·수집 파이프라인은 아직 채택하지 않았다.

| 결정할 경계 | 대안과 판단할 부담 | 판별 실험 제안 |
| --- | --- | --- |
| 카탈로그의 책임 | 서비스·시스템·소유자·저장소를 직접 관리하거나 기존 카탈로그와 연동; 소유권·식별·변경 관리 비용 | 같은 게시판 서비스의 두 배포와 공유 DB를 등록·조회하고 카탈로그 수정 이력 확인 |
| 자원 식별과 다중 환경 | 논리 서비스의 안정적 식별과 공급원별 실제 자원 식별, 공유 자원의 다대다 관계 | 온프레미스에서 ECS로 이동한 서비스, 여러 클러스터의 같은 이름, AWS·Kubernetes 수집원의 같은 객체를 비교 |
| 매핑 선언과 자동 발견 | 명시적 선언·수집 사실·태그·IaC 등의 후보를 조합; 확정 권한·충돌 우선순위·오연결 비용 | 이름·태그가 같은 다른 자원, 수동 선언과 수집 결과 충돌, 미등록 자원을 입력해 후보·확정·충돌 구분 |
| 시간과 버전 | 카탈로그·매핑 revision과 유효 시간·수집 시점·코드 및 빌드 버전을 별도로 추적; 보존·수정 비용 | 담당자·배포·자원 변경 뒤 과거 요청 당시의 관계를 조회 |
| 갱신과 장애 | 주기적 조회·이벤트·전체 재조정의 조합과 원본 권한·지연·삭제 정책 | 이벤트 누락·순서 변경·권한 거절·공급원 단절·태그 누락에서 기존 사실·신선도·삭제 근거 보존 |
| 권한과 원본 접근 | 카탈로그·자원·관계별 읽기 권한, 제한 설명의 공개 범위 | 카탈로그만 읽을 수 있는 사용자가 제한된 자원 이름·연결·보안 근거를 얻지 않는지 확인 |

카탈로그를 공통 탐색 기준점으로 사용하는 안을 검토한다. 전체 인벤토리와 사고 시점의 관계 이력을 CMDB·수집 근거와 어떻게 나눠 관리할지, 외부 ID와 내부 식별을 어떻게 연결할지 토론한다. [Backstage의 시스템 모델](https://backstage.io/docs/features/software-catalog/system-model/)은 소프트웨어와 자원을 구분하는 참고 모델이며 채택한 제품이나 완성된 시간·권한 계약으로 취급하지 않는다.

시나리오는 [카탈로그 매핑 BDD](../specs/features/09-catalog-mapping.feature)와 [인프라 BDD](../specs/features/06-infrastructure.feature), 실행 작업은 [로드맵](../ROADMAP.md)에 연결한다. 전체 요구를 유지하면서 확정된 요구·행동 초안·미결 선택을 구분한다.

## D08. OSS의 어떤 구조를 재사용하고 무엇을 직접 소유할 것인가

상태: **OPEN**. [공식 문서 기반 비교](OSS-ARCHITECTURE-COMPARISON.md)와 [릴리스·라이선스 원문 기록](OSS-SOURCE-SNAPSHOT.md)을 토론 입력으로 추가했다. Backstage와 OpenChoreo를 포함한 기존 플랫폼의 기능을 낮춰 평가하지 않고 동일 질문·연동 범위·custom 구현량으로 비교한다. 문서 조사와 PoC·채택 결정을 구분한다.

| 결정할 경계 | 대안·현재 제안 | 판별할 근거 |
| --- | --- | --- |
| 제품 중심 | 기존 IDP 기반 확장, 전체 원본 중앙 적재, 자체 근거 backend와 원본 adapter 조합 | UI 없이 조회, EKS·ECS·온프레미스 연결, 구현량·업그레이드·운영 비용 |

## D09. 자동 발견·등록과 지속 동기화의 기준은 무엇인가

상태: **OPEN**. 제품의 중심은 자동화이며 첫 온보딩 경로는 GitHub 기반으로 구체화한다. 모노레포와 영역·연동 경계는 제품 방향으로 기록하고, 아래 선택은 [자동화 제품 기획](requirements/AUTOMATION.md)과 BDD-ONB-001~010을 검토하며 결정한다.

## 작은 통합 실험 제안

두 앱 버전과 하나의 느린 합성 요청으로 시작한다. 분석·실행 결과를 만들고 “배포 이후 지연 증가” 질문에 trace·메서드·일치하는 빌드·소스와 출처·시점·수집 범위를 반환해 본다. 불일치·오래됨·누락을 넣어 과도한 원인 확정을 막는지도 확인한다.

실험의 대상 기술·데이터 계약·합격 기준은 위 대안과 함께 토론할 미결 항목이다. 현재는 실행하거나 채택하지 않았다. 실제 작업·상태·선행 조건은 [ROADMAP](../ROADMAP.md)의 이슈가 기준이다.
