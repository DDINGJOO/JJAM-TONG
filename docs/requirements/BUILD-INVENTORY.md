# 빌드 명세와 기준선 비교

상태: **로컬 도구의 검증 계약**. [#78](https://github.com/DDINGJOO/JJAM-TONG/issues/78)은 [#65](https://github.com/DDINGJOO/JJAM-TONG/issues/65)의 하위 작업이다. 서비스 배포·런타임을 자동 발견하거나 전체 코드 그래프를 증분 분석하는 기능까지 완료했다는 뜻은 아니다.

목적은 저장소마다 다른 빌드 구성을 공통 명세로 연결하고, 명시적으로 고른 두 기록에서 무엇이 바뀌었는지 설명하는 것이다. 모듈, 산출물, 컴파일 입력과 분석본의 버전을 구분한다. 동일한 서비스 이름이나 커밋만으로 같은 실행 코드라고 판단하지 않는다.

## 발견 후보와 검증한 명세

발견기는 Maven의 POM(Project Object Model, 빌드 설정 파일)과 Gradle의 설정 파일을 읽어 모듈 후보를 만든다. 빌드 스크립트를 실행하지 않으므로 실제 평가된 classpath, 생성 소스, 최종 JAR이나 서비스 배포를 확정하지 않는다. classpath는 컴파일·분석에서 참조하는 클래스와 라이브러리의 경로다.

Maven에서는 루트와 하위 POM의 문자 그대로 적힌 모듈 경로를 찾는다. 설정 파일은 UTF-8만 지원한다. 속성·프로필·상속·플러그인은 실제 빌드 평가가 필요한 조건으로 남긴다. Gradle에서는 최상위의 리터럴 `include`와 `projectDir` 할당을 제한적으로 읽는다. 변수·조건문·플러그인·composite build는 미해결로 표시한다. 모듈에 별도의 build 파일이 없더라도 모듈 부재로 확정하지 않는다. 두 빌드 체계가 함께 있으면 자동 선택하지 않고 adapter 지정을 요구한다.

이 후보를 곧바로 검증 명세로 승격하지 않는다. 소유자가 실제 빌드에서 얻은 입력·산출물을 별도의 공통 명세로 제공하고, 도구는 명시한 루트 아래의 파일을 읽어 SHA-256 해시를 확인한다. SHA-256 일치는 읽은 파일의 내용에 대한 검사다. 컴파일러 입력의 완전성, 소스에서 JAR로 이어지는 신뢰 가능한 출처나 과거 수집 시각의 증명은 아니다.

## 공통 형식

명세 schema는 `jjamtong.build-manifest.v1`이다.

| 필드 | 의미 |
| --- | --- |
| `repository`, `revision`, `build` | 저장소, 소스 버전, 빌드 식별자. 서로 대체하지 않음 |
| `recordedAt` | 생산자가 선언한 기록 시각 |
| `producer.name`, `producer.version` | 명세를 만든 도구와 버전 |
| `moduleCoverage` | 모듈 목록이 `complete`인지 `partial`인지에 대한 생산자 선언 |
| `modules[].id`, `descriptor` | 안정적으로 선택할 모듈 ID와 루트에 대한 빌드 파일 상대 경로 |
| `dependencies` | 소비 모듈에서 의존 모듈로 향하는 선언 관계와 가용 상태 |
| `artifacts` | 산출물의 상태와 명시적 경로·해시 목록 |
| `inputs` | `sources`, `generatedSources`, `classpath`, `toolchain`, `conditions` 다섯 입력 집합 |

산출물과 각 입력 집합은 `{state, files}`를 사용한다. `present`는 목록을 제공했다는 뜻이며 명시적인 빈 목록도 허용한다. `not-applicable`은 해당 없다는 소유자 선언이고, `unavailable`은 근거가 없다는 뜻이다. 마지막 두 상태의 파일 목록은 비어 있어야 한다. 의존 관계는 `{state, modules}`이며 `present`와 `unavailable`을 구분한다. 완전한 모듈 목록에서는 의존 ID가 목록 안에서 해석되어야 한다.

알 수 없는 필드와 중복 키·ID·같은 집합 안의 중복 경로를 거부한다. 경로는 절대 경로나 상위 이동이 없는 정규 POSIX 상대 경로다. JSON 객체 키를 정렬하고 UTF-8로 직렬화하되, 배열 순서는 유지한다. 특히 classpath 순서를 정렬해 버리면 실제 분석 입력의 차이가 사라질 수 있다.

시각은 `2026-11-14T03:00:00.000000Z`처럼 소수점 이하 여섯 자리의 UTC 형식만 받는다. `recordedAt`을 플랫폼이 당시 알았던 시각으로 바꾸어 해석하지 않는다.

## 파일 검사와 불변 기록

파일은 POSIX 디렉터리 파일 디스크립터를 따라 열며 심볼릭 링크와 일반 파일이 아닌 입력을 거부한다. 연 파일의 메타데이터를 읽기 전후에 확인한다. 필요한 OS 기능이 없으면 약한 검사로 대체해 검증 성공으로 표시하지 않는다. 이는 파일별 검사이며 전체 디렉터리의 원자적 스냅샷이나 실제 인증·인가의 구현은 아니다.

기본 상한은 명세 10 MiB, 빌드 파일 하나 1 MiB, 모듈 1,000개, 의존 항목 10,000개, 파일 참조 50,000개, 파일 하나 256 MiB, 총 읽기 2 GiB다. 전체 프로세스의 메모리·수용량 보장과는 구분한다.

저장 기록에는 원본 명세의 `manifestSha256`과 별도 검사 기록의 `verificationSha256`이 있다. 검사 기록은 도구 버전, 검사 시각 `verifiedAt`, 방식, 읽은 파일 수와 바이트 수, 한계를 포함한다. 두 카운터는 음이 아닌 JSON 정수이며 불리언을 허용하지 않는다. 다른 명세 값은 문자열·배열·객체로 제한한다.

기록은 기존 파일을 덮어쓰지 않고 저장한다. 불러올 때는 내부 형식과 두 해시를 확인하며, 현재 파일 시스템을 과거 파일 대신 재검사하지 않는다. 자체 해시 검사는 외부 서명이나 위조 방지의 보장이 아니다.

기존 분석 연결에는 모듈과 산출물 경로를 직접 지정한다. 다섯 빌드 필드와 분석 색인·설정 해시가 모두 일치해야 메타데이터 연결을 반환한다. 이 연결부는 메서드·Trace·서비스를 새로 수집하지 않는다.

## 기준선을 고정한 차이와 영향 경로

비교에는 같은 조직·저장소의 기준선과 현재 기록, 각각의 정확한 명세 해시가 필요하다. 최신 빌드나 이름으로 대체하지 않는다. 응답에는 두 검사 기록의 해시와 선언 시각·검사 시각도 함께 남긴다.

모듈 ID를 기준으로 빌드 파일 경로, 산출물, 입력 집합, 의존 관계의 차이를 계산한다. 영향 경로는 **선언된 모듈 의존 관계**에서 의존 대상을 사용하는 모듈로 거슬러 올라간 결과다. 삭제한 연결의 영향도 남기기 위해 기준선과 현재 그래프를 모두 탐색한다. 순환을 제한하며 경로와 어느 쪽 그래프에서 얻었는지 표시한다.

부분 목록에서 사라진 모듈은 삭제 확정 대신 누락 가능성으로 남긴다. 입력이나 산출물·의존 관계가 미수집이면 결과는 `PARTIAL`이다. 가용 근거가 같다는 판정도 실제 실행이 모두 같거나 변경의 영향이 없다는 보장이 아니다. 비교 결과의 `DECLARED` 표시는 요청의 실제 실행 경로나 인과 분석과 구분하기 위한 것이다.

기본 표시 상한은 100개이며 최대 1,000개까지 받는다. 경로 깊이 32와 전체 edge 검사 10,000회도 제한한다. edge는 두 모듈을 잇는 방향 있는 연결이다. 제한에 닿으면 잘린 결과를 완전한 목록처럼 제시하지 않는다.

## 화면과 QA 판정

화면에서는 기준선과 현재 기록을 각각 선택하고 저장소·소스·빌드·명세 해시·검사 시각을 확인할 수 있어야 한다. 모듈 차이에서 이전·현재 의존 경로를 열고, 실제 Trace는 별도 화면으로 이동한다. 후보 발견을 실제 배포 목록처럼 표시하지 않는다.

후속 화면 QA에서는 정상 변경, 가용 근거에 차이 없음, 명시적 빈 집합, 부분 수집, 해시 불일치, 삭제·순환 경로, 표시 상한, 좁은 화면을 확인한다. 이 작업의 CLI·단위 시험은 웹 화면의 상호작용·가독성 검증을 대신하지 않는다. 웹 UI 연결과 브라우저 QA는 별도 구현 대상이다.

## 과거 정답표와 제품 비교

과거 에이전트 판정에는 당시 조회할 수 있던 근거와 나중에 확인한 정답표를 분리해야 한다. 이 기능은 [#79](https://github.com/DDINGJOO/JJAM-TONG/issues/79)에서 다룬다. 이번 비교기는 실행 기록이 없는 과거 호출을 만들어 내지 않는다.

[Datadog·Elastic 비교](../OSS-ARCHITECTURE-COMPARISON.md#9-datadog과-elastic은-코드와-실행을-어떻게-연결하는가)에서 서비스 버전 태깅과 메서드 계측의 재사용 후보를 확인했다. 이번 형식은 특정 관측 backend를 요구하지 않는다. 소유자가 실행할 Maven·Gradle 명세 생산기, 빌드 출처 증명, 영구 보관과 전체 정적 그래프의 증분 분석은 후속 작업이다.
