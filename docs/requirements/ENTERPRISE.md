# 엔터프라이즈 운영 요구사항

날짜: 2026-11-12. 상태: **제품 품질 요구·BDD Draft / 운영 검증 미실행**.

[프로젝트 #1](https://github.com/DDINGJOO/JJAM-TONG/issues/1) · [수용량 계획](../experiments/CAPACITY-VALIDATION.md) · [BDD-ENT-001~009](../../specs/features/11-enterprise-operations.feature).

JJAM-TONG은 기업에서 여러 조직·팀이 여러 환경·AWS 계정·클러스터·온프레미스 자원을 연결해 운영하는 환경을 대상으로 한다. 코드·실행·인프라·CMDB·SIEM의 전체 구현 범위에 **접근과 데이터 격리, 지속 수용량, 장애·변경·복구와 운영 책임**을 공통 요구로 적용한다.

아래는 검증할 제품 요구다. 현재 구현된 기능·지원 규모·가용성 보장이나 보안 인증 취득을 뜻하지 않는다. 특정 제품·프로토콜·클라우드·데이터베이스와 수치 목표는 함께 비교·검증한 뒤 결정한다.

## 조직 경계와 설치 경계를 먼저 구분한다

**테넌트**는 접근·데이터·자원 정책을 적용할 격리 단위다. 기업·부서·팀과 어떻게 대응시킬지는 정해야 한다. GitHub 조직·AWS 계정·클러스터 식별자를 테넌트와 자동으로 같은 것으로 취급하지 않는다.

기업별 전용 설치와 여러 고객이 공유하는 설치를 비교 대상으로 둔다. 어느 방식을 택해도 설치 내부의 팀·환경·서비스별 접근 범위, 수집 연결의 권한과 사용자·에이전트 조회 권한을 구분한다. 공유·전용 저장소나 실행 단위의 분리는 아직 선택하지 않았다.

장애 영역은 같은 원인으로 함께 중단될 수 있는 범위다. 여기서 소유권 전환은 작업을 맡은 구성 요소가 바뀌는 과정을 뜻한다.

작업 소유권이 전환된 뒤에는 현재 소유권이 확인된 쓰기만 수락한다. 전환한 작업에 대한 이전 소유자의 뒤늦은 쓰기와 소유권 미확인 쓰기는 거절한다. 이를 위반한 수락·게시가 있으면 가용성 목표를 만족해도 해당 요구 실패로 판정한다. 구체적인 검증·거절 기술은 미결이다.

역할 기반 접근 제어(RBAC), 속성 기반 정책, OIDC·SAML 같은 기업 인증 연동 방식은 비교 대상이다. 정확한 지원 조합과 권한·정책 저장 방식은 미결이다. 플랫폼 읽기 권한이나 신뢰하지 않은 수집 속성을 운영 변경 실행 권한으로 확대하지 않는다.

## 수용량 계약에 기업 운영 조건을 넣는다

다음 조건을 [도착률·적체·복구 계획](../experiments/CAPACITY-VALIDATION.md)의 실행 설정에 추가한다.

- 조직·팀·사용자·에이전트·서비스 계정 수, 조직별 서비스·저장소·메서드·관계·빌드 이력 규모와 부하 분포.
- 계정·리전·클러스터·사이트·공급원 수, 사이트별 전송 속도·연결 중단 시간과 재연결 시 밀린 입력의 양.
- 조직별 할당량·동시 분석/조회·이력 보존 기간과 이벤트 크기. 큰 조직 하나와 작은 조직 다수의 혼합 부하.
- 인증·정책 검사·암호화·감사·보존 작업을 켠 정상 부하와 재분석·업그레이드·장애·복구 중 부하. 구성 차이도 결과에 남김.
- 전체 평균과 함께 조직·서비스별 p95/p99·거절·업무 완료·반영 지연·유실·자원·저장량을 기록.

**권한 우회·조직 간 정보 노출·다른 버전의 오연결을 성능과 교환하지 않는다.** 이런 반례가 발생한 실행은 빠르더라도 해당 요구 실패다. 부하 발생기 제한, 미발행 요청과 미완료 입력도 기존 수용량 계약대로 보존한다.

처리량뿐 아니라 장애 영역 하나를 잃거나 배포 중일 때 유지할 목표, 뒤늦은 입력의 회복 시간, 데이터 신선도와 보존 비용을 같이 정한다. 수치·측정 시간·정상/폭주/복구 부하 규모는 미정이다. 어떤 규모부터 지원할지는 이 계약의 조건·목표를 채운 검증 설정과 실제 결과로 선언한다.

[자동 확장·축소 요구](AUTOSCALING.md)는 이 기업 운영 조건을 유지하면서 단계별 신호·후속 병목·기동 지연·종료 중 인계·예산과 조직별 공정성을 검증한다. 플랫폼 자체의 용량 조절과 관측 대상의 확장 관측을 구분한다. 자동 확장이 고정 자원의 수용량 측정·장애 중 여유·재해복구를 대신하지 않으며 현재 구현·지원 규모의 근거로 집계하지 않는다.

## 장애 대응과 재해복구를 각각 검증한다

고가용성은 정한 장애 중에도 허용한 서비스를 이어 가는 요구다. 재해복구는 복제본이나 운영 저장소를 사용할 수 없는 상황에서 별도 복구 절차로 돌아오는 요구다. 복제본이 있다는 사실이나 백업 파일 생성 성공만으로 어느 쪽도 통과 처리하지 않는다.

실제 복구 보고서에는 장애 시점·관측 시작점·복원 기준 시각·복구 완료 조건, 손실·중복·누락 범위와 원시 근거를 남긴다. 장애 기준 시각부터 정한 기능과 서비스 목표를 회복할 때까지의 시간, 복구한 최신 정상 데이터의 시각을 목표와 대조한다. 허용 데이터 손실과 복구 시간은 수집·관계 갱신·보관·조회 등 기능별로 정한다. 재생성 가능한 현재 그래프와 다시 얻을 수 없는 trace·보안 사건 이력을 구분한다.

복원 데이터의 예전 권한으로 접근을 열지 않는다. 현재 접근 정책을 확인할 수 없는 범위는 접근을 차단하고 미확인 상태를 드러낸다. 권한 회수·삭제 기록과 키 가용성까지 대조한다. 재처리로 원래 업무를 다시 실행하거나 현재 관계 조회로 사라진 사건 이력을 복원했다고 판단하지 않는다.

## 변경·연동의 운영 조건

설정과 정책에도 버전·작성자·대상 범위·배포 결과를 남긴다. 이전 설정을 쓰는 구성 요소와 새 설정을 쓰는 구성 요소가 섞이는 구간, 잘못된 설정·권한 축소·인증서 만료·외부 공급원 장애를 각각 재현한다. 지원하지 않는 조합은 명시적으로 거절하고 마지막 정상 근거와 상태를 보존한다.

분석 입력과 외부 플러그인은 신뢰 범위를 선언한다. 원본 저장소의 빌드 스크립트·임의 코드를 자동 실행할지, 실행한다면 어디에서 어떤 권한으로 격리할지는 별도 결정 대상이다. 분석 시간·메모리·디스크·네트워크 상한과 결과 검증, 패키지 출처·라이선스·취약점·변조 확인을 릴리스 검증에 포함한다. 특정 스캔·서명 도구를 채택한 것은 아니다.

플랫폼 자신의 수집 거절·유실·분석 실패·오래된 근거·큐·저장량·인증/인증서 만료·백업·복구 상태를 외부 운영자가 확인할 수 있어야 한다. 경보·대응 절차·책임자와 실험 중단·되돌리기 조건을 남긴다. 플랫폼 자체 장애로 관측까지 중단되지 않도록 독립된 운영 경로에서도 상태를 확인한다.

조직 격리의 검증 항목은 [OWASP 다중 테넌트 보안 지침](https://cheatsheetseries.owasp.org/cheatsheets/Multi_Tenant_Security_Cheat_Sheet.html), 고가용성과 실제 복원 구분은 [재해복구 계획 지침](https://docs.cloud.google.com/architecture/dr-scenarios-planning-guide)을 참고했다. [OTel gateway 구성](https://opentelemetry.io/docs/collector/deploy/gateway/)과 [수집기 확장 지침](https://opentelemetry.io/docs/collector/scaling/)은 공유 수집 경로의 비용·장애와 상태를 유지하는 처리의 분산 조건을 검토할 근거다. 이 자료를 우리 요구에 적용한 제안이며 해당 제품·배포 방식의 채택이나 검증 완료를 뜻하지 않는다.

| --- | --- | --- |
| 격리·신원·정책·감사 | 데이터 흐름별 신뢰 경계, 역할·위임·권한 회수 반례, 감사 실패·민감정보 비노출 결과 | #14/#15/#26/#29 |

기능별 상태를 **미설계·설계 검토·구현·로컬 검증·목표 운영 조건 검증**으로 구분해 근거와 연결한다. 이는 요구사항의 검증 수준이며 실제 이슈 상태는 GitHub가 기준이다. 일부 로컬 시험 성공을 전체 엔터프라이즈 운영 적합성으로 확대하지 않는다. 조직별 허용 범위·실제 배치·운영 책임과 미검증 항목을 검토한 뒤 운영 투입 여부를 결정한다.

기존 코드 관측성·에이전트·SRE·인프라·CMDB·SIEM 범위는 유지한다. 이 문서는 새 의존성·실제 고객 연결·클러스터/클라우드 배포·실제 장애 주입을 승인하거나 제품 구현을 완료하지 않는다. 전용/공유 설치·격리 단위·기업 인증 방식·서비스 수준 목표(SLO)·RPO/RTO·보존과 지원 조합은 [D11 설계 토론](../DISCUSSIONS.md#d11-엔터프라이즈-운영-조건을-어떻게-검증할-것인가)에서 다룬다.
