# 분석 작업의 입력·자원·완료·실패 계약

[#64](https://github.com/DDINGJOO/JJAM-TONG/issues/64)의 비교 가능한 계약 제안이다. [로컬 실험](../../experiments/analysis_job_lab/README.md)에서 일부 상태·발행 경계를 검증했다. 언어·CI·설치 환경을 바꾸어도 보존할 의미를 정하며, 전체 플랫폼의 전송 형식이나 실행기를 확정하지 않는다.

## 입력과 실행 시도를 구분한다

| 구분 | 계약과 판정 |
| --- | --- |
| 조직·저장소·소스 revision | 원본의 범위를 식별한다. revision을 Git SHA 형식으로 한정하지 않는다 |
| 빌드·모듈·산출물 | 소스와 실제 빌드를 구분한다. 모듈을 배포 서비스와 동일시하지 않는다 |
| 소스·의존성·생성 입력 | 정렬·정규화한 입력 명세의 해시를 보존한다. 실제 명세의 생성·검증은 공급 어댑터의 책임이다 |
| 설정·도구 체인 | 분석 범위·언어 수준·지원 능력의 버전·진입점 정책·관련 환경 조건을 설정 명세에 포함한다. 도구 바이너리·런타임·설정이 바뀌면 입력 식별도 바뀐다 |
| 분석기·결과 스키마·계약 | 각각의 버전을 식별한다. 형식이 같아도 해석 정책이 다르면 같은 분석으로 재사용하지 않는다 |
| 입력 키·실행 시도 | 입력 키는 위 조건을 해시한다. 실행 시도는 재시도마다 바꾸고 이전 시도를 참조한다. 실패한 기록을 성공한 시도로 고쳐 쓰지 않는다 |

입력마다 `present`와 해시, `not-applicable`(해당 없음), `unavailable`(확보하지 못함)을 구분한다. 실제 빈 집합을 확인한 해시도 별개다. 어떤 입력이 없어도 분석할 수 있는지는 어댑터의 지원 선언과 필수 단계가 결정한다. 해당 정보가 없다는 사실을 결과에서 지우거나 확보된 것으로 바꾸면 실패다. 소스·산출물 해시의 일치가 신뢰하는 빌드 출처의 증명은 아니다.

작업 입력 키에는 현재 빌드·revision도 포함한다. [정확 입력 재사용](../../tools/analysis_reuse/README.md)의 계산 키는 같은 계산 결과를 다른 빌드에 다시 연결하기 위해 일부 출처 필드를 제외한다. 두 키의 목적이 다르므로 혼용하지 않는다. 여러 분석기를 한 작업에 묶으면 설정 명세에서 각 도구와 정책 버전을 모두 식별해야 한다.

## 실행 상태와 해석 범위를 구분한다

| 상태 | 의미와 허용 행동 |
| --- | --- |
| `QUEUED` | 대기 중이다. 실행 전 지원 확인·입력 검증·취소가 가능하다 |
| `RUNNING` | 이번 시도가 실행 중이다. 단순 파일 존재로 완료를 판단하지 않는다 |
| `PARTIAL` | 하나 이상의 필수 단계가 끝났다. 모든 단계가 끝나도 완료 명세의 검증 전에는 이 상태다 |
| `COMPLETE` | 선언한 필수 단계와 완료 명세·모든 결과 조각이 같은 입력·시도에 속함을 검증했다 |
| `UNSUPPORTED` | 요청한 필수 동작을 현재 지원 능력으로 수행할 수 없다. 같은 조건의 무한 재시도 대상이 아니다 |
| `RESOURCE_EXCEEDED` | 명시한 자원 예산을 초과했다. 종류·제한값·강제 주체·측정 유무를 남긴다 |
| `CANCELLED` | 취소가 완료 전에 수락됐다. 뒤늦은 완료가 취소 상태를 바꾸지 않는다 |
| `FAILED` | 입력 변경·손상·실행 오류 등으로 완료 조건을 충족하지 못했다. 원인과 마지막 확인 범위를 남긴다 |

완료는 선언한 작업 범위의 완료다. 정적 후보·실제 관측·미해결·제외·부분 수집은 결과의 별도 축으로 보존한다. 작업이 완료됐다고 모든 메서드를 해석하거나 실제 실행을 관측했다는 뜻은 아니다. 빈 단계도 유효한 지원 범위라면 명시적으로 0건을 기록한다. 어댑터가 필수로 요구하는 결과가 비어 실패한 경우와 구분한다.

실패·자원 초과·취소 후 재시도는 새 시도 식별자를 받는다. 같은 입력의 동일한 완료 발행은 멱등적으로 처리하고, 이미 사용한 불변 경로에 다른 내용을 쓰면 충돌이다. 완료·미지원 기록을 재시도로 변조하지 않는다. 재시도 횟수·대기·영구 실패 격리·소유권의 분산 강제는 [#37](https://github.com/DDINGJOO/JJAM-TONG/issues/37)에서 이어서 검증한다.

## 예산의 값과 강제 주체를 함께 기록한다

| 예산 | 요청·측정 정보 | 강제 주체와 이번 범위 |
| --- | --- | --- |
| 힙 | 바이트 제한·런타임 옵션·실패 원인 | 언어 런타임. 이 Python 발행 실험에는 JVM 힙 제한이 없다 |
| 프로세스 메모리 | 상한·RSS 등 측정 종류·측정 구간·누락 | OS·컨테이너·실행기. 이번에는 측정만 하며 상한을 강제하지 않는다 |
| 대기·실행 시간 | 각 단계의 제한과 시작·종료·초과 | 큐·감독 실행기. 비교 하위 프로세스에는 180초 외부 제한이 있고 작업 모델에는 강제 실행기가 없다 |
| 결과 표현 | 레코드·조각·파일·전체·명세의 바이트와 조각 수 | 직렬화·발행·수신 검증기. 이번 실험에서 실제 강제한다 |
| 동시 실행·임시 디스크 | 조직별·호스트별 제한·현재 사용량·대기·거절 | 스케줄러·할당량·파일시스템. 실험에서는 설정·운영 강제하지 않는다 |

요청한 제한, 실제 적용된 제한, 측정값은 서로 다른 정보다. 측정되지 않았거나 강제하지 않은 값은 `unknown`·`not-enforced` 등으로 명시하며 0이나 무제한 지원으로 해석하지 않는다. 검사 전에 큰 레코드·문자열 조각이 메모리에 만들어질 수 있으므로 출력 바이트 상한을 전체 메모리 상한으로 표현하지 않는다.

플랫폼의 설치 환경과 관측 대상의 실행 환경은 별도로 기록한다. AWS·Kubernetes 식별자나 특정 언어의 프로세스 옵션을 공통 식별자의 필수 조건으로 삼지 않는다. 수용량·동시 실행·자동 확장과 격리는 [#19](https://github.com/DDINGJOO/JJAM-TONG/issues/19)·[#37](https://github.com/DDINGJOO/JJAM-TONG/issues/37)의 검증과 연결한다.

## 결과 발행과 실패의 경계

단일 파일은 임시 파일에 직렬화하며 바이트를 검사하고 완료 후 불변 경로로 발행한다. 실패하면 이번 시도의 새 결과가 없다. 기존 파일이 남아 있어도 현재 요청의 입력·시도를 검증하기 전에는 재사용하지 않는다.

분할 방식은 조각마다 입력 키·시도·단계·순서를 넣고 바이트·해시·건수를 기록한다. 모든 필수 단계와 조각을 확인한 뒤 완료 명세를 발행한다. 조각 일부만 남았거나 누락·손상·다른 버전·다른 시도·중복 참조가 있으면 완료를 인정하지 않는다. 조각으로 나누어도 전체 바이트 예산은 유지한다.

소비자는 완료 명세와 모든 조각을 검증하고 전체 읽기를 마친 뒤 파생 색인·저장 상태를 반영한다. 읽다가 실패한 일부 레코드를 새 빌드의 성공한 최신 결과로 노출하지 않는다. 실제 DB의 트랜잭션·대형 색인 수신 경로·서명/출처 검증·화면 표시의 전환은 후속 통합에서 확인한다.

이번 로컬 모델의 불변 경로는 신뢰하는 단일 파일시스템 안의 계약이다. 원격 저장소·분산 소유권·취소와 완료의 동시 경합·전원 장애·실패 조각의 정리 정책은 별도 구현과 검증이 필요하다. [ADR 0010](../decisions/0010-analysis-job-publication.md)과 [실험 결과](../experiments/ANALYSIS-JOB-CONTRACT.md), BDD-UPD-013~018을 연결한다.
