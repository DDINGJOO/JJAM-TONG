# 자동화 중심 제품 기획

상태: **제품 방향 확인 / 세부 행동 Draft · 2026-11-12**. 사용자가 확인한 중심은 “가시성을 자동으로 유지하고, 그 근거로 분석과 운영을 자동화하는 플랫폼”이다. 아래 온보딩·동기화·판정은 토론할 요구사항 초안이며 구현·지원 완료나 기술 채택을 뜻하지 않는다.

## 확인한 방향과 검토할 제안

- 코드 관측성·에이전트·SRE·MSA·인프라·카탈로그·CMDB·SIEM은 모두 구현 대상이다.
- GitHub 기반 자동 발견·등록·변경 동기화를 첫 온보딩 경로로 구체화한다. 허용한 저장소를 연결한 뒤 관계를 반복 입력하는 일을 줄인다.
- 모노레포에서 시작하고 영역·연동별 경계를 둔다. 별도 릴리스·접근 권한·운영 책임이 필요해지면 저장소 분리를 검토한다.
- 자동 발견과 사실 확인을 함께 다룬다. 선언한 서비스는 정책에 따라 자동 등록하고 추정한 담당자·관계는 확인할 후보로 제시하는 안이다.
- GitHub는 첫 연동 대상이다. 공통 서비스·빌드 식별 계약은 특정 Git 공급원이나 Actions 실행 번호에 종속시키지 않는다.

GitHub App의 구체적 권한, 서비스 선언 형식, 자동 확정 정책, 동기화 주기, 실행 승인 정책과 모듈 계약은 아직 미결이다. 현재 GitHub App 설치·조직 생성·클라우드 연결·운영 변경을 수행하지 않는다.

## 사용자 흐름과 자동화 책임

| 단계 | 플랫폼이 맡을 행동 초안 | 사람이 제공하거나 확인할 내용 |
| --- | --- | --- |
| 연결 | 허용한 저장소·클라우드·클러스터·근거 공급원의 연결 상태와 범위를 기록 | 접근 범위·서비스 선언·필요한 인증과 계측 설정 |
| 발견·등록 | 저장소의 서비스·모듈 선언과 빌드·배포 설정을 읽고 출처가 있는 카탈로그 생성 | 추정한 서비스 경계·담당자·충돌 관계 확인 |
| 지속 갱신 | 변경 감지와 원본 재확인으로 코드·배포·자산·보안 관계 및 이력을 갱신 | 지원 범위·갱신 예산·보존 정책 설정 |
| 분석 | 같은 대상·시점·빌드의 근거를 사람과 에이전트에게 제공 | 조사 질문·시간 범위와 가설 검토 |
| 운영 실행 | 정책이 허용한 알림·이슈 생성·대응 작업을 요청·추적 | 실행 권한·대상·조건·승인 방식과 되돌리기 정책 |

운영 실행도 기획 범위에 포함한다. 읽기·분석 권한과 외부 시스템을 변경하는 실행 권한을 구분하고, 제안·실행 요청·실제 완료·실패의 근거를 남긴다. 알림·이슈·배포·복구별 행동과 멱등성·재시도·감사는 별도 명세가 필요하다. 현재 외부 변경을 실행하는 기능은 없다. 기존 [보안 대응 경계](../../specs/features/08-security.feature)의 BDD-SEC-003과 함께 구체화한다.

## 첫 온보딩: GitHub 연결부터 지속 갱신까지

1. GitHub App에서 허용한 저장소와 기능별 접근 범위를 확인한다. 제품의 공통 식별과 공급원의 원본 식별을 함께 남긴다.
2. 저장소별 서비스 선언과 빌드·배포 설정을 발견한다. 한 모노레포에 여러 서비스·라이브러리·모듈이 있을 수 있고 한 서비스가 여러 저장소를 참조할 수 있다. 폴더나 저장소 하나를 서비스 하나로 가정하지 않는다.
3. 유효한 선언과 합의한 등록 정책이 충족되면 카탈로그에 자동 반영한다. 충돌·미지원 형식·추정 관계는 출처와 함께 검토 대상으로 구분한다. 커미터를 담당자로 확정하지 않는다.
4. 실제 빌드 입력과 산출물을 기준으로 정적 코드 지도를 만든다. PR head·merge revision·기본 브랜치 HEAD와 실제 빌드 revision을 구분하고, 같은 commit의 서로 다른 build·artifact도 구분한다.
5. 별도 공급원에서 확인한 실제 배포 artifact·build와 실행 근거를 연결한다. CI 성공이나 배포 선언만으로 실행 중인 버전·인프라·보안 수집 완료를 확정하지 않는다.
6. 이벤트를 검증·중복 처리하고 지연·역순 완료를 다룬다. 이벤트만으로 변경 이력을 완전하게 복구한다고 약속하지 않는다.
7. 주기적으로 허용 범위의 원본을 재확인한다. 누락된 이벤트 이후에도 현재 원본의 확인 가능한 상태에 수렴하고, 복구할 수 없는 과거 구간은 공백으로 남긴다. 부분 페이지·접근 거절·장애는 삭제 근거가 아니다.

선언의 수정·삭제가 발생하면 선언 관계의 유효 기간을 닫고 이력을 보존하는 안을 검토한다. 선언에서 사라졌다는 이유로 실제 실행 자원이나 과거 분석을 삭제하지 않는다. 저장소의 이동·이름 변경과 서비스 식별 충돌, 여러 공급원의 우선순위는 [D09](../DISCUSSIONS.md#d09-자동-발견등록과-지속-동기화의-기준은-무엇인가)에서 결정한다.

## 자동화 상태와 접근 권한

아래 상태 구분은 의미 계약의 제안이며 API 필드명·상태 머신을 확정한 것은 아니다.

| 구분할 상태 | 사용자가 판단할 수 있어야 할 내용 |
| --- | --- |
| 연결·권한 | 허용한 기능과 대상, 마지막 접근 확인, 권한 축소·연결 해제의 영향 |
| 발견·확정 | 선언으로 등록한 서비스, 추정 후보, 충돌·미지원·미연결 범위 |
| 갱신 | 마지막 시도·성공·원본 확인 시각, 목표 revision, 적용 revision, 실패·부분 완료·오래됨 |
| 연결 범위 | 카탈로그, 코드 분석, 실제 배포, 실행 계측, 인프라, CMDB, SIEM 각각의 준비·누락 |
| 실행 | 요청한 작업·대상·정책·권한·멱등성 식별·시도·실제 결과와 감사 근거 |

GitHub 설치 권한은 플랫폼 조회자의 권한을 대신하지 않는다. 연결 범위를 축소하거나 권한을 회수하면 새 수집과 재시도를 멈추고 캐시·과거 관계·조회 응답에도 현재 접근 정책을 적용한다. 이전 관계의 존재·식별자가 제한된 조회자에게 노출되지 않아야 한다. 이력 보존과 접근 허용은 별도 판단이며, 보존·삭제 정책은 미결이다.

## 게시판 검증 시나리오

합성 저장소 `community`에 `board-api`와 `board-worker`가 선언되어 있고, API의 build-A와 build-B가 함께 실행되는 예시를 사용한다. 두 서비스와 기존 서비스 식별·출처를 기대값으로 미리 정하고, 미확인 상태만 반환하는 결과를 성공으로 인정하지 않는다.

1. 최초 연결로 선언된 두 서비스가 자동 등록되고, 명시한 담당자와 선언 출처가 연결되는지 확인한다.
2. 서비스 이름·폴더가 바뀌어도 확인된 동일 서비스 식별과 이전 관계를 유지한다.
3. 게시글 목록 조회가 build-B 배포 후 느려지는 입력에서 해당 실행·메서드·정적 지도·실제 배포 artifact를 연결한다. build-A 실행은 build-A 근거에 연결한다.
4. 변경 이벤트를 중복·역순·누락시키고 일부 페이지 조회를 실패시킨다. 정상 재확인 후 현재 관계를 회복하고, 확인하지 못한 기간·실패·이전 성공을 구분한다.
5. GitHub 권한을 축소하고 클라우드·런타임 미연결 상태를 넣는다. 서비스 등록 성공과 다른 영역의 수집 완료를 구분하고 현재 권한을 지킨다.

판정할 관측값은 등록한 서비스·관계 집합, 확인 출처·revision·시각, 잘못 합친 build 수, 중복 서비스 수, 실패 후 유지한 성공 결과, 제한된 정보 노출 여부다. 발견·갱신 지연과 수작업 횟수도 측정하되 수치 목표·지원 조합·측정 규모는 후속 실험 전에 정한다. 현재 fixture나 실행 결과는 없다.

## 공식 참고 근거와 미검증 범위

- Backstage는 GitHub 조직 또는 App에서 설정 경로의 카탈로그 엔터티를 발견하는 provider와 이벤트 연동을 제공한다. 자동 등록 자체를 새 기능의 우위로 주장하지 않는다. [GitHub Discovery](https://backstage.io/docs/integrations/github/discovery/) (2026-11-12 확인).
- GitHub는 webhook secret을 통한 검증과 delivery ID 활용을 안내한다. 재전송에도 같은 delivery ID를 쓰므로 수신 기록과 처리 성공을 구분하고 실패한 처리를 다시 시도할 수 있어야 한다. [Webhook best practices](https://docs.github.com/en/webhooks/using-webhooks/best-practices-for-using-webhooks) (2026-11-12 확인).
- GitHub가 실패한 webhook을 자동 재전송하지 않는다는 문서에 따라 재전송·주기적 재확인을 비교할 필요가 있다. 원본 재확인으로 복원할 수 있는 현재 상태와 유실된 과거 이벤트의 복구 범위는 구분한다. [Redelivering webhooks](https://docs.github.com/en/webhooks/testing-and-troubleshooting-webhooks/redelivering-webhooks) (2026-11-12 확인).

위 근거는 설계 입력이다. Backstage 채택, App 구현, webhook 신뢰성·호환성·성능 검증이나 실행 수락 테스트를 수행한 상태는 아니다.
