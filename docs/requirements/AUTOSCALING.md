# 자동 확장과 축소의 운영 요구사항

날짜: 2026-11-12. 상태: **품질 요구·BDD Draft / 자동 확장 구현·실험 미실행**.

[기업 운영 요구](ENTERPRISE.md) · [수용량 검증 계획](../experiments/CAPACITY-VALIDATION.md) · [BDD-ASC-001~009](../../specs/features/12-autoscaling.feature) · [T10 #19](https://github.com/DDINGJOO/JJAM-TONG/issues/19) · [T21 #37](https://github.com/DDINGJOO/JJAM-TONG/issues/37).

입력이 몰린 뒤 복제본 수만 늘려서는 기업 운영 목표를 지켰다고 할 수 없다. 새 실행 단위가 일을 시작하기 전까지 적체가 쌓이고, 저장소가 이미 포화됐다면 증설로 연결·재시도만 늘 수 있다. 축소할 때는 처리 중 입력과 분석 결과, trace 상태와 작업 소유권도 보존해야 한다.

이 문서는 **어떤 신호로 무엇을 늘리고 줄일지, 목표를 지켰는지 어떻게 판정할지**를 명세한다. 자동 확장은 수용량·가용성·복구를 지원하는 수단이다. 고정 자원의 한계 측정이나 별도 재해복구를 대신하지 않는다. 도구·설치 환경·복제본 범위·수치 목표는 아직 정하지 않았다.

## 플랫폼의 확장과 관측 대상의 확장을 구분한다

| 구분 | 책임과 검증할 결과 |
| --- | --- |
| JJAM-TONG 자체 | 수집·갱신·분석·보관·조회가 정한 부하·자원·비용 안에서 목표를 유지하도록 실행 단위를 조절. 설치 환경을 정한 뒤 해당 제어기와 연동 |
| 관측 대상 서비스 | EKS·ECS·일반 Kubernetes의 확장·축소·재배치와 실행 자원 교체를 관측해 당시 배포·빌드·인프라 관계와 연결 |
| 관측 대상의 운영 변경 | 조회·수집 권한과 별도의 변경 권한·대상 범위·정책·감사 필요. 대상 서비스의 복제본 수를 바꾸는 기능·자동 실행 정책은 별도 설계 |

플랫폼을 Kubernetes에 설치할지, ECS나 온프레미스에 설치할지는 미결이다. 공통 계약에는 처리 목표·입력과 상태·권한·예산·판정 근거를 두고, 환경별 연동에서 지원 신호·확장 수단·제약을 설명한다. AWS 계정이나 Pod를 모든 설치의 필수 식별자로 요구하지 않는다.

## 처리 단계마다 신호와 상한을 다르게 둔다

**적체 시간**은 아직 완료되지 않은 입력이 얼마나 오래 기다렸는지 나타낸다. 큐 길이가 같아도 입력 크기와 처리 비용이 다르므로 개수·bytes·최고 대기 시간·단위 시간당 유입·완료 건수·처리 오류를 함께 본다. 아래 신호는 검증 후보이며 실제 지표 이름·단위·집계·수집 주기와 목표는 실행할 버전에서 고정한다.

| 처리 단계 | 판단에 사용할 신호 후보 | 함께 지킬 제약 |
| --- | --- | --- |
| 수신·수집·전송 | 유입량, 거절·유실, 큐 사용량·대기 시간, CPU·메모리 | 네트워크·외부 전송 한도, 후속 저장소 수용량, 상태를 가진 처리의 분배 |
| 공급원 확인·관계 갱신 | 공급원별 갱신 지연, 대기 작업·최고 대기 시간 | API 호출 예산·재시도 시점을 알리는 응답 헤더(Retry-After), 같은 대상 작업 병합·소유권, 조직별 공정성 |
| 코드 분석 | 대기 시간, 작업별 예상 크기·처리 시간, CPU·메모리·디스크 | 분석기/설정/빌드 버전, 동시 작업·개별 작업 상한, 신뢰하지 않은 입력 격리 |
| 이벤트 처리 | 파티션별 대기량·최고 대기 시간·단위 시간당 완료 건수, 재시도·재균형 | 파티션과 소비자 할당 방식, 편중된 키, 순서·중복·업무 효과와 소비 진행 위치(offset) 확정 경계 |
| 근거 조회 | 조직별 지연·거절·동시 요청, CPU, 캐시·DB 대기 | 조회 비용·응답 상한, DB 연결 총량, 권한·캐시 일관성 |
| 저장·색인·보존 | 쓰기 지연·IO·용량 증가, 색인·보존 작업 적체 | 저장소별 복제·분할·확장/축소 가능 여부와 시간, 복원·보존 비용 |

Kafka를 사용하는 구성에서는 같은 소비자 그룹의 파티션 할당과 실제 병렬 처리 범위를 먼저 확인한다. 소비자 수만 늘려 모든 적체를 해소한다고 가정하지 않는다. 파티션 증가나 저장소 구조 변경은 일반 worker 증설과 구분하며, 순서·재분배·비용·호환성을 별도로 검증한다. RDS·Redis·Kafka는 부하·병목을 고려할 대상이지 플랫폼 필수 제품으로 확정한 목록이 아니다.

**후속 처리 단계가 포화되면** 수신부 증설과 동시에 연결 수·재시도·저장 압력이 증가하는지 확인한다. 입력 속도 제한, 제한된 큐와 재시도, 조직별 거절·작업 지연, 운영자 경보를 비교한다. 의도한 샘플링과 유실을 구분하고, 수집 범위를 바꿔 부하를 낮춘 실행은 같은 정확성·수용량 결과로 집계하지 않는다.

## 확장 결정부터 실제 처리 가능 시점까지 측정한다

부하 증가 → 지표 수집 → 판단 → 실행 단위 요청 → 자원 배치 → 기동·설정/정책 로딩 → 준비 완료 → 실제 처리 → 적체·신선도 회복의 시각을 남긴다. 요청한 복제본 수, 실행 중인 수, 준비된 수, 실제 일을 처리한 수를 나눈다. Pod·task 증설과 이를 배치할 노드·실행 자원의 증설도 나누어 본다.

기동 지연, 캐시 준비, 이미지·분석기 입력 다운로드, 자원 부족·할당량·주소 부족, 준비 상태 검사 실패, 특정 장애 영역의 자원 부족을 검증 후보로 둔다. 배치 불가 상태가 오래 지속되면 목표 위반과 원인을 기록하고 상한 없는 증설 요청·재시도를 막는다. 예측한 행사·대량 재분석은 일정 기반 사전 확보와 여유 용량을 유지하는 방법도 비교한다.

지표 누락·오래된 값·단위 오류·공급원 단절을 부하 0으로 바꾸지 않는다. 지표 신선도·품질과 제어기 상태, 유지·확장 제한·축소 금지 등 상황별 처리 규칙을 사전에 정하고 결과를 남긴다. 모든 오류에서 무조건 증설하거나 마지막 값을 무기한 신뢰하는 정책도 채택하지 않는다.

수평 확장은 실행 단위의 수를, 수직 확장은 개별 실행 단위의 CPU·메모리 등을 바꾸는 방식이다. 두 방식을 비교할 때 전체 자원 합계와 개별 제한, 배치 조건·재기동·작업 인계의 영향을 함께 남긴다. 자원 변경으로 확장 지표의 기준도 달라지는지 확인하고 서로 다른 제어가 반복 증감을 만들면 실패 원인으로 기록한다. 수직 확장 도구나 무중단 변경 지원은 아직 선택하지 않았다.

같은 실행 단위의 복제본 수를 변경하는 주체를 명확히 한다. 자동 제어기·선언형 배포 설정·예약 작업·운영자 수동 변경이 충돌할 때 소유권·우선순위·일시 중지·재개와 정책 버전을 기록한다. 증감 속도, 유지 시간, 최소/최대 실행 수와 자원·비용 상한을 비교해 잦은 증감 반복을 평가한다. 구체 값은 미정이다.

## 축소·교체 중에도 처리 결과를 검증한다

**드레인**은 새 작업 수신을 멈추고 이미 맡은 작업을 완료하거나 안전하게 넘기는 절차다. 종료 시작 → 신규 라우팅·작업 할당 중지 → 진행 중 작업 처리/인계 → 결과 영속화와 확인/offset 확정 → 종료를 추적한다. 실제 순서와 허용 시간, 강제 종료 시 재처리·손실 규칙은 처리 단계별로 정한다. 준비 상태 전환이나 종료 hook만으로 모든 송신자가 즉시 전송을 멈췄다고 가정하지 않는다.

큐·재시도·영속 보관 전 수신 확인, 메모리에 남은 span과 tail sampling 판단, 파티션 재할당·재전달, 긴 분석·조회와 정책 변경 중 상태를 확인한다. tail sampling은 관련 span을 모은 뒤 보관 여부를 판단하는 처리다. 구성원이 바뀔 때 라우팅과 상태의 이동·잔존·유실을 검증하고, 보존되지 않은 trace를 현재 그래프에서 복원했다고 표시하지 않는다.

작업 인계는 [ENT-004](../../specs/features/11-enterprise-operations.feature)의 현재 소유권 확인·이전 소유자 쓰기 거절 조건을 지킨다. 이전 분석 작업이 뒤늦게 완료돼 새 결과를 덮어쓰거나, 재전달로 업무 효과가 중복되거나, 다른 빌드에 결과가 게시되면 해당 정확성 요구 실패다. 무손실·분산 exactly-once를 주장하지 않고 입력 ID별 수락·보관·완료·재처리·유실/측정 불가를 대조한다.

복제본 하한, 장애 영역 분산, 교체 중 여유와 종료 예산을 함께 정한다. Kubernetes의 PDB(PodDisruptionBudget)는 일부 자발적 중단에서 최소 가용 Pod 수 또는 최대 중단 Pod 수를 지정하는 장치이며 모든 장애·직접 삭제·워크로드 축소를 방어하는 보장이 아니다. 강제 종료·노드 장애도 별도 실험으로 남긴다.

## 0개까지 축소할지는 별도로 결정한다

실행 단위를 0개로 줄이는 기능은 선택지다. 외부에서 관측 가능한 활성화 신호, 제어기와 지표 경로의 독립 가용성, 첫 입력의 보관·응답/완료 기한과 기동 비용을 먼저 정한다. 실행 중인 worker가 직접 만들어야만 존재하는 지표로는 0개 상태의 수요를 확인할 수 없다.

첫 입력 폭주, 지표 장애, 유휴 상태에서 새 입력 도착, 시작 실패를 재현한다. 수신·경보·보안 사건의 연속성이 필요한 경로에는 최소 실행 수나 별도 상시 수신 경로를 비교한다. 0개 상태를 항상 지원하거나 비용이 언제나 줄어든다고 약속하지 않는다.

## 같은 입력으로 고정 용량과 자동 확장을 비교한다

고정 자원의 기준 수용량을 먼저 확인하고 **고정 복제본 / 부하 반응형 / 일정 기반 사전 확보 또는 여유 용량**을 비교한다. 같은 입력·데이터·버전·정확성·기업 정책과 공통 자원/비용 상한을 사용한다. 모든 시점의 복제본 수를 같게 맞추는 비교와 자동 확장 결과를 혼동하지 않는다. 실제 사용 자원·동작·비용은 결과로 남긴다. 비용은 단가·청구 단위·추정/실측 구분과 계산 근거를 남기며 컴퓨팅 외 저장·IO·전송·로그 보관과 재처리 비용도 비교 범위에 포함한다. 소프트웨어의 확장 상한만으로 청구액 전체의 절대 상한을 보장하지 않는다.

| 시나리오 | 자극과 확인할 실패 | 연결 |

| ASC-03 | 노드/task 배치 지연·자원 부족·준비 실패에서 요청한 실행 단위 수와 실제 처리 가능한 실행 단위 수를 구분 | ASC-003 · CAP-07 |
| ASC-04 | DB·전송·호출 예산·파티션 병목에서 증설의 효과와 연결·재시도 증가를 비교 | ASC-004 · CAP-03/05 |

| ASC-09 | 관측 대상의 확장·축소·이름 재사용 중 배포/자원/빌드 연결과 수집 공백을 확인 | ASC-009 · INF-004~006/CAT-002 |

조직별 예정·발행·미발행·수락·거절·미완료·늦은 완료와 독립 기대값을 [기존 수용량 계약](../experiments/CAPACITY-VALIDATION.md)에 따라 보존한다. p95/p99·오류·업무/비동기 완료·갱신 지연·유실, 단계별 대기 시간·지표 신선도·결정 이유/정책 버전·실행 수·노드/task·자원·연결·비용·회복 시간을 함께 보고한다. 큐 길이 감소가 입력 삭제·샘플링 변경·미완료 폐기 때문인지 대조한다.

실행 전에 목표·관측 창·완료/실패/중단 조건·최대 자원·비용·실험 시간을 고정한다. 할당량·예산에 도달했을 때의 제한·거절·경보·복구 절차도 시험한다. 한도를 지킨 결과 목표를 놓쳤으면 양쪽 결과를 기록하며 성공으로 바꾸지 않는다. 권한 우회·조직 간 노출·잘못된 버전 연결은 처리량과 무관하게 실패다.

공통 계약은 소유한 격리 로컬 자원에서 검증할 수 있는 범위부터 시작한다. 제어기·환경 고유 동작은 해당 지원 조합에서 별도 실행해야 한다. 로컬의 모의 판단·복제본 변경을 HPA(Pod 복제본 수를 자동 조절하는 제어기)·ECS·노드의 실제 자동 확장 검증으로 집계하지 않는다. 이번에는 명세만 추가하며 기존 공유 컨테이너·클러스터·클라우드를 변경하지 않는다.

## 공식 동작과 우리 요구를 구분한다

다음은 2026-11-12에 확인한 공식 문서의 동작이다. 위 판정 계약은 이를 JJAM-TONG에 적용한 설계 제안이며 도구 채택이나 실제 검증 결과가 아니다. 실행 시 환경·버전·지표 의미를 다시 확인한다.

| 공식 근거 | 확인한 동작과 이 문서에서의 적용 경계 |
| --- | --- |
| [Kubernetes HPA](https://kubernetes.io/docs/concepts/workloads/autoscaling/horizontal-pod-autoscale/) | 누락 지표를 보수적으로 처리하고 여러 지표의 권고 중 큰 실행 수를 선택. 일부 지표 조회 실패와 나머지 지표의 축소 권고가 겹치면 축소를 건너뛰지만 유효한 증설 권고는 적용할 수 있음. `behavior`의 증감 속도·안정화 설정과 지표 오류를 검증하며 모든 오래된 값의 자동 거절을 보장한다고 해석하지 않음 |
| [Pod 종료 수명주기](https://kubernetes.io/docs/concepts/workloads/pods/pod-lifecycle/) · [중단과 PDB](https://kubernetes.io/docs/concepts/workloads/pods/disruptions/) | 종료 hook·애플리케이션 종료는 종료 유예 시간의 영향을 받으며 강제 종료될 수 있음. PDB가 비자발적 장애·Pod 직접 삭제·워크로드 롤링 업데이트를 모두 막지 않으므로 드레인과 업무 결과를 별도로 대조 |
| [EKS 노드 확장 사례](https://docs.aws.amazon.com/eks/latest/best-practices/cas.html) | Cluster Autoscaler는 배치되지 못한 Pod 등을 바탕으로 노드 용량 조절. workload 복제본 증가와 노드 확보를 구분할 근거이며 해당 도구 채택을 뜻하지 않음 |
| [ECS Service Auto Scaling](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/service-auto-scaling.html) · [EC2 cluster auto scaling](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/cluster-auto-scaling.html) | 서비스 task 수 조절과 EC2 capacity provider의 실행 용량 조절은 별도. 실행 방식별 대기·자원 부족을 확인하며 EC2 노드 설명을 Fargate에 그대로 적용하지 않음 |
| [Kafka 4.1 설계](https://kafka.apache.org/41/design/design/) | 일반 소비자 그룹에서는 파티션을 그룹 내 한 소비자에 할당. 병렬성·편중·재할당 중 영향을 client/broker 버전과 재균형 방식별로 검증 |
| [OTel Collector 확장](https://opentelemetry.io/docs/collector/scaling/) | 상태를 모으는 처리와 구성원 갱신 시점의 차이, 후속 단계 병목을 고려. trace와 집계 결과, 전송 거절·유실을 입력과 대조하며 Collector 증설만으로 해결된다고 판단하지 않음 |
| [KEDA 2.18 Kafka scaler](https://keda.sh/docs/2.18/scalers/apache-kafka/) | topic 미지정·commit 이력 없음·최소 실행 수 0인 조합에서 재활성화하지 못하는 조건을 명시. 0개 축소의 외부 활성화·최초 입력과 신규 소비자 그룹 조건을 검증할 근거이며 KEDA 채택이나 최신 버전 선언이 아님 |

## 남아 있는 결정과 추적

제어기·지표 전달 도구, 설치 환경별 지원 방식, 저장소 확장 전략, 지표/예산·목표·최소/최대 실행 수·종료 시간, 0개 축소 허용 경로, 수동 운영과 자동 제어의 경계는 [D12 설계 토론](../DISCUSSIONS.md#d12-자동-확장과-축소를-어떤-신호와-경계로-제어할-것인가)에서 비교한다. 기술 채택은 실제 호환성·라이선스·운영 부담과 판별 실험을 확인한 뒤 ADR로 남긴다.

요구와 판정은 #19, 공급원·상시 worker·제어 연동은 #37, 저장·조회 병목은 [#43](https://github.com/DDINGJOO/JJAM-TONG/issues/43), 외부 앱 계측의 비용·정확성은 [#44](https://github.com/DDINGJOO/JJAM-TONG/issues/44)에 연결한다. 새 스토리·태스크를 중복 생성하거나 기존 완료 조건·진행 상태를 바꾸지 않는다.
