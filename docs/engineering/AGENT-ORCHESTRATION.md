# 에이전트 병렬 개발과 SRE 사용 평가

JJAM-TONG은 에이전트가 빠르고 정확하게 근거를 찾고, 사람이 전체 흐름을 믿고 판단하도록 돕는다. 개발에서도 같은 기준을 적용한다. 구현자는 담당 티켓의 결과를 만들고, 독립 평가자는 실제 조사 시나리오로 결과를 사용한다. 중앙 조율자는 의존성·문서·검증 근거를 연결하고 통합 결과를 판정한다.

[작업 계약](../../AGENTS.md)과 GitHub Issues가 기준이다. 이 문서는 [병렬 작업 스토리 #86](https://github.com/DDINGJOO/JJAM-TONG/issues/86), [공통 스킬·훅 #87](https://github.com/DDINGJOO/JJAM-TONG/issues/87), [Trace(요청 실행 기록) 후속 작업 #88](https://github.com/DDINGJOO/JJAM-TONG/issues/88), [두 소비자의 사용 평가 #89](https://github.com/DDINGJOO/JJAM-TONG/issues/89)를 연결한다. 별도 상주 스케줄러나 운영용 에이전트 서비스의 구현 범위는 이 문서에서 확정하지 않는다.

## 작업 배정과 책임

에픽은 전체 사용자 결과, 스토리는 검증할 사용 흐름, 태스크·서브태스크는 독립적으로 검증할 결과로 나눈다. 기존 이슈를 먼저 확인하고 새 작업이 필요할 때만 분리한다. 티켓 수나 코드 수정량을 성과로 사용하지 않는다.

| 담당 | 책임 | 인계할 결과 |
| --- | --- | --- |
| 중앙 조율자 | 작업 분해·우선순위·선행 조건·파일 소유권·문서화·통합 평가 | 티켓 그래프, 판단 근거, 검증 결과와 다음 안전한 작업 |
| 구현 에이전트 | 담당 최하위(leaf) 태스크 하나의 구현·수정·관련 검증 | 변경 파일, 입력·버전, 실행한 검증, 결과·한계 |
| 독립 평가 에이전트 | 구현자와 다른 관점에서 실제 사용·반례 검증 | 재현한 결함, 관찰·가설·제안의 구분, 재검증 조건 |

각 에이전트는 진행 중인 최하위 태스크 하나를 담당한다. 조율자는 선행 조건과 파일 소유권이 독립적인 작업을 병렬 배정한다. 예를 들어 A가 정적 분석을 마무리하는 동안 B는 Trace 입력·출력 계약을 검증할 수 있다. 함께 수정해야 하는 서버·식별 계약이 생기면 소유자를 지정하고 인계 순서를 정한다. 같은 파일을 동시에 고치거나 검증하지 않은 선행 결과를 사용하는 방식으로 병렬성을 늘리지 않는다.

작업 지시에는 티켓·소유자·역할·수정 허용 파일·선행 조건·기대 결과·검증 명령·중단/인계 조건을 담는다. 설치된 역할과 실행 도구를 사용한다. Codex·Claude에 같은 역할 이름이나 모델이 있다고 가정하지 않는다.

## 사람 화면과 에이전트 조회

원본 근거와 표시 정책을 분리한다. `getId()`·생성자·private 메서드도 수집했다면 원본에 보존한다. 사람 화면은 API·업무 흐름을 중심으로 필요한 정보를 먼저 보여 주고, 보조 항목은 접거나 필터링한 뒤 검색·전체 보기·펼치기로 복구한다. Java의 private 접근 제한은 플랫폼의 조회 권한과 별개의 개념이다.

사람 화면의 표시 정책은 원본 보존 및 에이전트의 허용 범위 조회와 독립적이다. 개별 구현은 제공하는 조회 경로와 권한 경계를 별도로 밝힌다.

에이전트는 허용된 원본 근거를 식별자·페이지·범위 지정으로 조회할 수 있어야 한다. 큰 그래프를 한 번에 문맥에 넣기보다 목록 → 관심 경로 → 상세 근거 순서로 확장한다. 부분 결과에는 상한·전체 수·다음 조회 방법을 제공하고, 지원하지 않는 조회는 한계로 밝힌다.

| 상태 | 사람과 에이전트가 구분할 의미 |
| --- | --- |
| 표시에서 접힘 | 수집한 근거가 있으며 현재 화면의 표시 정책 때문에 보이지 않는다. 펼치기·검색 경로가 있다. |
| 권한 제한 | 해당 소비자에게 제공할 수 없는 범위다. 표시 필터를 해제해도 권한은 확대되지 않는다. |
| 미수집·이력 없음 | 요청한 시점·대상의 기록이 없다. 실행되지 않았다는 증거로 해석하지 않는다. |
| 미해결 | 근거는 있으나 대상이나 관계를 확정하지 못했다. 원인과 지원 범위를 남긴다. |
| 상한·부분 수집 | 범위나 자원 제한 때문에 일부만 제공했다. 빈 결과나 완전한 결과로 바꾸지 않는다. |

정적 후보, 관측한 부모·링크, 추정 인과 관계를 구분한다. Trace를 최신 소스에 묵시적으로 연결하지 않는다. 서비스·저장소·커밋·빌드/산출물·모듈·분석기·스키마·설정·환경·시각의 해당 필드를 대조하고, 누락·불일치는 그대로 반환한다.

## 다섯 관점의 사용 평가

아래 역할은 AI의 검토 관점이다. 실제 전문가 참여나 해당 영역의 지원 완료를 뜻하지 않는다. 변경한 경계에 맞는 역할을 선택하며, 모든 작은 수정마다 다섯 역할을 전부 실행하지 않는다.

| 관점 | 사람이 확인할 조사 질문 | 에이전트가 확인할 계약 |
| --- | --- | --- |
| 플랫폼 개발자 | 서비스·API에서 실제 코드와 관계의 근거를 찾을 수 있는가? 보조 메서드를 접어도 핵심 흐름을 이해하는가? | 안정적인 식별자, 버전별 조회, 원본 복구, 지원·미해결 범위 |
| SRE | 어느 요청·구간이 느리거나 실패했는지, 어떤 근거가 부족한지 알 수 있는가? | Trace·정적 후보의 구분, 부모/링크·부분 수집·시간의 의미 |
| DevOps | 변경한 빌드가 어떤 환경에 반영됐는지, 이전 결과와 비교·복구할 수 있는가? | 소스·빌드·배포 식별, 재전송·역순·실패·재시작의 처리 |
| 보안 엔지니어 | 조회 권한과 민감정보 경계가 명확하며 관련 사건을 근거로 설명하는가? | 허용 필드, 조직·권한 경계, 감사 가능성, 출처와 오연결 방지 |
| 인프라 엔지니어 | 서비스·워크로드·네트워크·자원이 어느 환경·시점에 연결됐는지 알 수 있는가? | 논리/실제 자원 구분, 공유 자원·유효 시간·수집 신선도·수용량 한계 |

아직 연결하지 않은 영역도 시나리오와 미지원 상태로 평가할 수 있다. 화면·API에 기능이 없는데 통과했다고 기록하지 않는다. 구현 검증과 설계 검토 결과를 구분한다.

## 시나리오와 이슈의 순환

평가자는 조사 질문, 소비자, 역할, 허용 입력·버전·시점, 기대 결론, 필요한 근거·한계, 조회 예산, 판정 방법을 먼저 정한다. 예상값은 평가 대상이 만들어 낸 결과와 독립적인 합성 정답표나 확인한 원본에서 가져온다.

1. 사람이 화면을 조작하는 흐름과 에이전트가 API를 조회하는 흐름을 각각 수행한다. 화면 검증을 API 응답 확인으로 대신하지 않는다.
2. 기대/실제 결과, 사용한 버전, 실행 명령·관찰 범위와 실패 지점을 남긴다. 같은 질문·버전에서 두 소비자가 받는 근거와 한계의 의미를 대조한다.
3. 기존 이슈를 검색한다. 같은 원인이면 기존 이슈에 근거를 추가하고, 독립된 결과·책임·재검증이 필요할 때 하위 티켓을 발행한다.
4. 조율자가 영향·확신 수준·의존성으로 우선순위를 정한다. 재현한 결함, 직접 확인하지 못한 가설, 개선 제안을 구분한다.
5. 수정 뒤 해당 시나리오를 재실행하고 결과를 티켓에 연결한다. 새 반례는 다음 평가의 회귀 입력으로 보존한다.

이슈에는 상위 작업·중복 확인·조사 질문·재현·기대/실제·영향·우선순위 이유·버전 근거·재검증 조건을 담는다. [사용 평가 템플릿](../../.github/ISSUE_TEMPLATE/sre-evaluation.md)을 사용한다. 공개 자료는 합성 예제를 사용하며 비공개 원본·식별자·경로·캡처는 로컬 ignored 영역에 보관한다.

## 문서와 완료 판정

중앙 조율자는 요구사항을 BDD 시나리오에, 대안·판단을 이슈와 토론에, 채택한 결정을 ADR에, 실제 실행·실패·측정값을 실험 결과에 연결한다. 같은 변경에서 관련 위키 요약·링크를 맞춘다. GitHub의 작업 상태를 위키와 로컬 장부에 중복해서 운영하지 않는다. 로컬 장부는 현재 실행·검증을 복구할 근거다.

완료 판정에는 입력·코드 버전, 검증 명령·종료 결과, 소비자별 평가, 독립 검토, 문서 영향과 남은 한계가 필요하다. 해당하지 않는 평가는 이유를 적고 조율자가 판단한다. 구현자의 완료 선언과 검토자의 판정을 분리한다. 근거가 오래됐거나 변경한 입력과 다르면 다시 검증한다.

작업 시작·종료, 의존성 대기, 검토, 재작업 원인·횟수를 기록한다. 준비된 작업이 승인 가능한 근거를 갖출 때까지의 시간과 같은 범위의 순차 기준을 비교한다. 작은 합성 입력의 속도를 엔터프라이즈 수용량으로 확대하지 않는다.

훅은 짧은 문맥 안내와 로컬 근거 확인에 사용한다. 테스트·LLM 호출·GitHub 쓰기·업무 앱 실행을 훅 안에서 반복하지 않는다. 훅 실행은 제품 검증 통과를 뜻하지 않는다. 권한·개인 설정·새 의존성·병합·Notion 반영은 기존 승인 경계를 따른다.

## 공통 스킬과 로컬 훅 사용

공통 스킬 원본은 [병렬 작업 조율](../../.agents/skills/jjamtong-orchestrate/SKILL.md)과 [SRE 사용 평가](../../.agents/skills/jjamtong-sre-qa/SKILL.md)다. Codex는 `.agents/skills`의 원본을 읽고, OMX용 `.codex/skills` 별칭도 같은 원본을 가리킨다. Claude는 `.claude/skills`의 진입 문서에서 원본을 읽는다. [CLAUDE.md](../../CLAUDE.md)는 [AGENTS.md](../../AGENTS.md)를 함께 읽게 한다.

프로젝트 훅은 Codex의 [`.codex/hooks.json`](../../.codex/hooks.json)과 Claude의 [`.claude/settings.json`](../../.claude/settings.json)에 둔다. `SessionStart`·`UserPromptSubmit`은 짧은 안내를 추가한다. `SubagentStop`은 상위 세션의 완료 정책을 자식에게 적용하지 않는다. `Stop`의 완료 확인은 세션과 태스크를 명시적으로 연결했을 때만 적용한다. 반복 훅 요청에서는 재차 중단하지 않으며, 로컬 상태 파일을 읽을 수 없을 때는 에이전트 종료를 막지 않는다. 개인 전역 설정은 바꾸지 않는다.

실행 장부는 Git에 올리지 않는 `.local/agent-workflow/run.json`에 둔다. 최소 예시는 아래와 같다. 예시의 상태는 아직 시작하지 않은 계획이며 검증 통과 기록이 아니다.

```json
{
  "run": {
    "id": "local-example",
    "version": "workflow-v1",
    "revision": "replace-with-the-reviewed-commit",
    "source_scope": "workflow-helper"
  },
  "tasks": [{
    "id": "workflow-helper",
    "ticket": "#87",
    "lane": "implementation",
    "owner": "executor-a",
    "role": "executor",
    "scopes": ["tools/agent_workflow.py", "tests/test_agent_workflow.py"],
    "dependencies": [],
    "state": "planned",
    "acceptance": ["실제 형식의 훅 입력으로 세션 격리와 종료 동작을 검증한다"],
    "result": {"state": "unknown"}
  }]
}
```

```sh
python3 tools/agent_workflow.py check --manifest .local/agent-workflow/run.json
python3 tools/agent_workflow.py fingerprint --manifest .local/agent-workflow/run.json --task workflow-helper
python3 tools/agent_workflow.py status
python3 tools/agent_workflow.py bind --manifest .local/agent-workflow/run.json --task workflow-helper --tool codex --session-id SESSION_ID
```

`check`는 소유 파일의 현재 해시로 검증 기록을 다시 확인한다. `status`는 마지막 확인 기록을 읽으므로 이후 파일 변경을 반영하지 않을 수 있다. `ok: true`는 장부의 형식·관계가 유효하다는 뜻이며, 남은 작업은 `pending`에 별도로 반환한다. `bind`는 `--tool codex` 또는 `--tool claude`와 세션 ID의 조합에만 완료 확인을 연결한다. 같은 세션 ID라도 다른 도구의 종료에는 적용하지 않는다. 이 도구는 에이전트를 실행하거나 티켓을 자동 발행하는 상주 스케줄러가 아니다.

완료 기록의 `validation`에는 `status: pass`, 실제 실행한 `command`, 정수 종료 코드 `exit_code: 0`, 실행의 `version`·`revision`, 현재 소유 파일의 `fingerprint`, 실행 시각 `timestamp`, 근거 위치 `reference`가 필요하다. 주요 통합 결과를 `milestone: true`로 표시하면 사람·에이전트 각각의 `assessments`에 같은 버전·리비전·해시와 작성자와 다른 검토자를 기록한다. 해당하지 않는 평가는 `status: na`, 구체적인 `reason`, 구현자와 다른 `coordinator`를 기록한다. 이 정보는 작업자가 남기는 근거이며 명령 실행의 위변조 방지 증명은 아니다.

확인은 태스크·소유 범위를 각각 최대 128개, 해시 대상 파일을 최대 512개·4 MiB로 제한하고 시간 예산을 둔다. Git·로컬 실행 기록·빌드 캐시는 제외하며 심볼릭 링크를 소유 범위로 사용하지 않는다. 상한을 넘으면 범위를 좁히고 검증을 다시 수행한다. 전체 저장소를 매번 해시하는 용도로 사용하지 않는다.

설정 형식은 [Codex 훅](https://learn.chatgpt.com/docs/hooks)·[스킬](https://learn.chatgpt.com/docs/build-skills), [Claude 훅](https://code.claude.com/docs/en/hooks)·[스킬](https://code.claude.com/docs/en/skills)의 공식 문서를 기준으로 확인한다. 클라이언트의 실제 발견·실행 확인과 Python 어댑터 계약 시험은 서로 다른 검증으로 기록한다.
